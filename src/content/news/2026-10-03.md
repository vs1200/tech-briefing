## 1. Apple、AI Agentを理由にmacOSの「Full Disk Access」を締める

10月2日、[Apple](https://www.apple.com/) がmacOSの **Full Disk Access** に追加Controlを導入すると明らかにしました。

Full Disk Accessを許可すると、ApplicationはFilesだけでなくMail、Messages、Browser Historyなどにも広くアクセスできます。Appleは、AI Agentの高機能化によってこの権限のRiskが大きくなったとして、今後は**ユーザーによる非常に明示的な操作なしには付与できない方向**へ変更します。([TechCrunch](https://techcrunch.com/2026/10/02/apple-says-its-tightening-macos-full-disk-access-controls-due-to-new-risks-from-ai-agents/))

背景にはDesktop Agentが広範なDataへアクセスする事例が増えていることがあります。

**開発者目線:** かなり重要です。

今週ずっと、

`Agent → broad filesystem access`

がSecurity問題になっていましたが、ついに**OS Vendor自身がPermission ModelをAgent時代向けに変え始めました**。

Coding Agentでも、

> Repositoryを読むためにHome Directory全部を見せる

のではなく、Repository / Credential / Messages / Browser DataなどをCapability単位で分離する設計が必要になります。

macOS上でClaude Code / Codex / CopilotのようなAgentを使うDeveloperには今後直接関係してきそうです。([TechCrunch](https://techcrunch.com/2026/10/02/apple-says-its-tightening-macos-full-disk-access-controls-due-to-new-risks-from-ai-agents/))

## 2. PS5にもAI Upscaling — QSSRで「Pro専用」だったNeural Graphicsを下ろす

[PlayStation公式：AI upscaling is coming to PS5](https://blog.playstation.com/2026/10/01/ai-upscaling-is-coming-to-ps5/)

Sony Interactive Entertainment が **Quick Spectral Super Resolution（QSSR）** を発表しました。

PS5 ProのPSSRと同様にNeural Networkで画像をUpscaleしますが、Network Architectureを軽量化し、Base PS5向けにHand-tuneしたことで通常PS5でも動作可能にしています。([PlayStation.Blog](https://blog.playstation.com/2026/10/01/ai-upscaling-is-coming-to-ps5/))

最初の対応タイトルは『Marvel's Wolverine』と『Ghost of Yōtei』で、10月1日からPatch提供済み。今後は一般のPlayStation DeveloperにもLibraryを提供します。([PlayStation.Blog](https://blog.playstation.com/2026/10/01/ai-upscaling-is-coming-to-ps5/))

**ゲーム開発目線:** これはかなり面白い変化です。

Neural Renderingが、

`高価な最新GPU向け特殊機能`

から、

**既存Consoleの固定Hardware上でもSoftware更新で利用する普通のRendering Technique**

へ下りてきています。

Unityでも今後、

`native rendering resolution`

より**Neural Reconstruction込みでTarget Resolution / Frame Budgetを決める**考え方がさらに一般化しそうです。

## 3. NVIDIA DGX Spark 64GB — Local AI Machineがかなり現実的な価格帯へ

[NVIDIA公式：DGX Spark 64GB](https://blogs.nvidia.com/blog/local-ai-dgx-spark-64gb-sync/)

NVIDIA が10月2日、DGX Sparkの**64GB Unified Memory版**を発表しました。10月23日からAcer / ASUS / Dell / Gigabyte / HP / MSIなどから発売されます。([NVIDIA Blog](https://blogs.nvidia.com/blog/local-ai-dgx-spark-64gb-sync/))

GB10 Grace Blackwell、DGX OS、CUDA Stackは128GB版と同じ。単体で**最大100B Parameter級**のModelを扱えるとしています。

さらに2台をConnectX-7で直結すると128GBとしてCluster化でき、最大200B級へ。NVIDIAのQwen 3.8 27B Testでは2台構成で単体比最大**1.7倍**のPerformanceを記録しています。([NVIDIA Blog](https://blogs.nvidia.com/blog/local-ai-dgx-spark-64gb-sync/))

Ollama / vLLM / PyTorchに加えてAgent Toolkitも標準対応です。

**開発者目線:** Local LLM Machineが、

`一台買ったら固定`

ではなく、

```text
64GB
 ↓
足りなくなる
 ↓
+ 64GB node
 ↓
128GB cluster
```

と増設できるのが面白いところ。

Local Coding Agent用途では、Apple Silicon MacとCloud GPUの間にかなり現実的な選択肢が増えてきました。

## 4. Microsoft、音声認識を100ms級へ — Agentが「話し終わる前」に考え始める

[Microsoft AI公式：MAI-Transcribe-2-Streaming](https://microsoft.ai/news/our-first-streaming-transcription-model/)

[Microsoft](https://www.microsoft.com/) が **MAI-Transcribe-2-Streaming** と **MAI-Voice-2.1 / Voice-2.1-Flash** を公開しました。

Transcribeは60言語に対応し、Audioを受け取り始めてから**約100ms強で最初のPartial Transcript**を返します。話者が話し終える前からTranscriptを更新し続けます。([Microsoft AI](https://microsoft.ai/news/our-first-streaming-transcription-model/))

Voice-2.1-Flashは45秒分の音声をEnd-to-End約150msで生成可能とMicrosoftは説明しています。

**開発者目線:** Voice Agentでは、

```text
speech
 ↓
STT
 ↓
LLM reasoning
 ↓
tool
 ↓
TTS
```

全部のLatencyが積み上がります。

Streaming STTなら、ユーザーが、

> 「明日の午後3時に……」

と言っている途中からAgent側でIntent解析を始められる。

**「発話終了を待ってからReasoning」しなくてよい**ので、Voice UIの体感Latencyをかなり変えられます。

## 5. SupabaseがTursoを買収 — 「AgentごとにDatabase」が現実のArchitectureへ

[Supabase](https://supabase.com/) が10月2日、$150Mの追加資金調達と同時に **[Turso](https://turso.tech/) の買収**を発表しました。

TursoはlibSQLをベースに、大量の軽量Database Instanceを扱うことを得意としています。Supabaseは買収理由として**Agentic Workloadで非常に多数のDatabaseが必要になる**ことを明確に挙げています。([PR Newswire](https://www.prnewswire.com/news-releases/supabase-announces-150m-in-new-funding-and-turso-acquisition-302896752.html))

Turso自体は当面独立Serviceとして継続し、将来的にSupabase Ecosystemへ統合する方針です。

**開発者目線:** AgentのState管理が、

`全Agent → 一つの巨大DB`

ではなく、

```text
agent A → db A
agent B → db B
agent C → db C
...
```

という**Database-per-Agent / Database-per-Task**へ向かう可能性があります。

SandboxをProcess単位で分けるのと同じように、Data StateもIsolationする発想です。

Tursoが目指していた「10億Database」というArchitectureがAgent時代に急に意味を持ってきました。([PR Newswire](https://www.prnewswire.com/news-releases/supabase-announces-150m-in-new-funding-and-turso-acquisition-302896752.html))

## 6. Copilot Code ReviewをREST / GraphQL APIから起動可能に

[GitHub公式：Copilot code review API](https://github.blog/changelog/2026-10-02-copilot-code-review-api-support-and-new-default-effort-level/)

[GitHub](https://github.com/) が10月2日、Copilot Code Reviewを**REST / GraphQL APIからRequest可能**にしました。

Reviewごとに`Lite / Balanced`などのEffort Levelも指定できます。Balancedは9月28日からDefaultになっています。([The GitHub Blog](https://github.blog/changelog/2026-10-02-copilot-code-review-api-support-and-new-default-effort-level/))

これによりGitHub UIを使わず、

```text
CI
 ↓
risk analysis
 ↓
if high risk:
   Copilot review (Balanced)
else:
   Copilot review (Lite)
```

のようなWorkflowを組めます。

**開発者目線:** 先週から追っている**Inference BudgetをTask Riskに応じて変える**設計が、かなり実装しやすくなりました。

例えばUnityなら、

`*.cs UI変更 → Lite`

`Addressables / AssetBundle / 課金 / Save Data → Balanced`

のようにPathでReview Costを変えることもできます。

## 7. DeepSeek + Huawei、CUDA代替StackをOpen Source化

DeepSeek と Huawei が、Ascend 950向けのAI Programming Tool群をOpen Source公開しました。

中心は、

**DeepGEMM-Ascend** → Matrix計算
**DeepEP-Ascend** → MoEなどのGPU間Communication
**TileLang** → High-level Kernel Programming

です。([Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/deepseek-and-huawei-release-open-source-ascend-ai-programming-tools-to-reduce-reliance-on-nvidia-ecosystem-tools-include-compute-and-communication-libraries-as-well-as-ascend-support-for-tilelang))

DeepGEMMはBF16 / FP8 / FP4へ対応し、既存DeepGEMMとAPI互換。TileLangはAscend 950向けCode Generation / Scheduling / SynchronizationをNative対応しました。([Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/deepseek-and-huawei-release-open-source-ascend-ai-programming-tools-to-reduce-reliance-on-nvidia-ecosystem-tools-include-compute-and-communication-libraries-as-well-as-ascend-support-for-tilelang))

**開発者目線:** NVIDIAの強さはGPU Hardwareだけではなく、

**CUDA + NCCL + cuBLAS + TensorRT + Tooling**

というSoftware Moatです。

Huawei側が本気で競争するならHardware Benchmark以上に、**DeveloperがCUDA並みに楽にKernelを書けるか**が重要。

TileLangのようなHardware-neutral DSLが育つなら、AI Kernel DevelopmentがCUDAから少しずつ分離する可能性があります。

## 8. GitHub Security Advisory API、RESTなしで情報を完結しやすく

[GitHub公式：SecurityAdvisory GraphQL更新](https://github.blog/changelog/2026-10-02-new-fields-for-securityadvisory-graphql-api/)

小さいDeveloper Tool更新です。

GitHubの`SecurityAdvisory` GraphQL Objectへ、

`cveId`
`sourceCodeLocation`
`githubReviewedAt`
`nvdPublishedAt`
`repositoryAdvisoryUrl`

の5 Fieldが追加されました。([The GitHub Blog](https://github.blog/changelog/2026-10-02-new-fields-for-securityadvisory-graphql-api/))

これまでは一部情報を取るためGraphQL → RESTへ切り替える必要がありました。

**開発者目線:** Security BotやDependency Dashboardを作る場合に地味に便利です。

特に`sourceCodeLocation`があるとAgentへ、

> Advisoryを読む → 該当Sourceを見る → Fix候補を作る

というFlowを組みやすい。

Security Data自体も**Agentが機械的に消費しやすいSchemaへ整備**されてきています。

## 9. Jev、「Decision Model」が研究ネタから企業導入フェーズへ

昨日Clef / Strands Deciderを紹介しましたが、元祖側にも大きな続報です。

TypeSafe AI の **Jev** は9月15日の公開からわずか約3週間ですが、WSJによると既にSilicon Valleyでかなり大きな注目を集め、競合Modelが次々登場しています。([The Wall Street Journal](https://www.wsj.com/tech/ai/startup-typesafe-ais-jev-model-sparks-copycats-talk-of-llm-alternatives-e39ff57d))

Jevは文章を生成せず、

`yes/no`
`score`
`candidate A/B/C`

のような有限候補を直接判断するModelです。

**開発者目線:** このDaily Briefingではかなり頻繁に扱ってきましたが、今週だけで、

`Jev`

→ `OpenAI Decisions`

→ `Cloudflare Clef`

→ `AWS Strands Decider`

まで一気に出てきました。

もはや「面白い小型Model」ではなく、

> **Generative LLMとは別のInference Primitive**

として扱った方がよさそうです。([The Wall Street Journal](https://www.wsj.com/tech/ai/startup-typesafe-ais-jev-model-sparks-copycats-talk-of-llm-alternatives-e39ff57d))

2027年のAgent Frameworkでは`llm.generate()`だけでなく、`decide(candidates)`が標準Primitiveになるかもしれません。

## 10. 小ネタ：Barclays、Claude Codeを開発者の半数へ展開

[Anthropic公式：Barclays scales Claude](https://www.anthropic.com/news/barclays-scales-claude)

Barclays がClaudeの社内展開を拡大し、**2026年末までにDeveloperの50%がClaude Codeを利用**する計画を明らかにしました。2027年には過半数へ広げます。([Anthropic](https://www.anthropic.com/news/barclays-scales-claude))

用途には新規開発だけでなく、Legacy System Modernizationも含まれます。

**開発者目線:** Coding Agentの導入事例自体はもう珍しくありません。

面白いのは、金融のような規制産業でも、

`数人が試す`

ではなく、

**Developer Populationの50%以上を前提とした標準Tool**

へ移り始めたことです。

これから企業側の差になるのは「Copilot / Claude / Codexを導入したか」より、**Agentに渡す社内Knowledge・Permission・Eval・Workflowをどれだけ整備したか**になりそうです。

## 👀 今日ならこの3つ

**今日一番重要なのはAppleのFull Disk Access変更です。** Agent SecurityがAI Vendorだけの問題ではなく、**OSのPermission Architectureそのものを変え始めた**という意味で大きいです。Desktop Coding AgentはShell / Repository / Browser / Credentialへアクセスしたがるので、macOS側が今後どんなFine-grained Capabilityを用意するのかはかなり注目です。([TechCrunch](https://techcrunch.com/2026/10/02/apple-says-its-tightening-macos-full-disk-access-controls-due-to-new-risks-from-ai-agents/))

**ゲーム開発ならQSSR。** Neural UpscalingがPS5 Pro専用ではなく、2020年発売世代のBase PS5まで降りてきました。今後Rendering Budgetは「何pでNative描画するか」より、**どこまで低Resolutionで描いてNeural Reconstructionへ任せられるか**で考える比重がさらに増えそうです。([PlayStation.Blog](https://blog.playstation.com/2026/10/01/ai-upscaling-is-coming-to-ps5/))

**Architectureとして面白いのはSupabase × Turso。** Agentを大量生成するとCompute SandboxだけでなくState Isolationも必要になります。**「1 Agent = 1軽量DB」**を安価に数百万単位で作れるInfrastructureが本当に必要になるなら、TursoのArchitectureがかなり綺麗にハマります。([PR Newswire](https://www.prnewswire.com/news-releases/supabase-announces-150m-in-new-funding-and-turso-acquisition-302896752.html))
