## 1. VS Code 1.145 — リモートAgentの開発サーバーをAgents画面から直接プレビュー

**11月4日公開｜公式一次情報**

11月4日に公開されたVisual Studio Code 1.145では、遠隔のAgent Hostで実行した開発サーバーを、Agentsウィンドウ内のブラウザで表示するPreview機能が加わった。エージェントがクラウドや別マシンでアプリを修正しても、結果を見るために手元へコードを同期したり、ポート転送を別途設定したりする負担が生じていた。今回の機能は、ブラウザのアクセスをリモートホスト経由にすることで、その確認工程を短くする。公式の[11月4日リリースノート](https://code.visualstudio.com/updates/v1_145)に手順が掲載されている。

設定は`workbench.browser.enableRemoteProxy`。さらに`chat.canvases.enabled`を有効にすると、リモートホスト上のCanvasも利用できる。画面に見えるプレビューが手元のローカルサーバーなのか、Agent Host上のサーバーなのかを区別できることが重要だ。UIの目視確認を会話の延長で行える一方、ネットワーク接続先や認証状態はリモート側の環境に依存する。ブラウザの表示に成功しても、実ユーザーの端末での動作保証にはならない。

例えばフロントエンドの変更をエージェントに任せ、遠隔環境で起動したページを開き、崩れた箇所を同じセッションへ指示する流れが考えられる。手元に依存パッケージを展開しなくても反復できる点は、複数の作業ブランチを並行させる際に効く。ただしPreviewであり、利用可能な接続方式や機能フラグは更新され得る。

**開発者目線:** 導入時はログイン画面、WebSocket、ホットリロード、画像などの静的アセット、APIへの通信を順番に確認したい。表示だけではなく、サーバー再起動後の再接続やエラー時の情報が取得できるかを検証することで、ローカル確認から置き換えられる範囲を判断できる。

## 2. VS Code 1.145 — Nested SessionでClaude・Codex・Copilotを同じ作業に並列投入

**11月4日公開｜公式一次情報**

同じ11月4日のVS Code 1.145では、親のチャットセッションに紐づくNested Sessionで、親と異なるAgent Harnessを選べるPreviewが導入された。以前は子セッションが親のHarnessを引き継ぐため、別のエージェントにレビューさせるには会話のまとまりを分ける必要があった。今回の変更により、例えばCopilotで作った設計をClaudeにレビューさせ、Codexでも代替案を検討するという構成を一つのセッション内に置ける。

試用する設定は`chat.agentHost.multipleChatProviders.enabled`。子セッションごとにモデル、エージェント、権限レベルが独立し、別の子セッションへ設定変更が波及しない。子を移動しても履歴とHarnessの選択を保持し、Forkした場合も同じ構成を引き継ぐと[公式更新情報](https://code.visualstudio.com/updates/v1_145)は説明する。複数のモデルを使えること自体よりも、異なる作業方針や権限を混同せずに比較できることが設計上の価値だ。

ただしHarnessを分けたからといって、共有ファイルへの競合が自動で解消されるわけではない。各Agentの実行環境、同じワークツリーを編集するかどうか、レビュー結果を誰が採用するかは運用上の判断として残る。親子セッションのUI上の整理と、実際のコード変更の分離は別の問題である。

**開発者目線:** 最初は「実装役」「反証役」「テスト観点役」を分け、同一課題の提案の重複と相違を比較するとよい。作業ディレクトリの分離、権限の最小化、差分を統合する担当を決めておけば、複数Agentが同じ変更を上書きする事故を避けやすい。

## 3. VS Code 1.145 — MCP管理Allowlistの優先順位を修正、組織ポリシーを明確化

**11月4日公開｜公式一次情報**

11月4日のVS Code 1.145では、企業管理下のMCPサーバー許可ルールが、Registry限定設定より優先されるようになった。従来は管理者が`allowedMcpServers`で許可していても、そのサーバーが組織Registryに掲載されていないと起動できない場合があった。今回の変更は、承認済みの社内MCPサーバーをRegistryへ登録しない運用でも扱えるようにするものだ。

[公式リリースノート](https://code.visualstudio.com/updates/v1_145)によると、管理Allowlistに一致するサーバーはRegistry未掲載でも起動でき、逆にRegistry掲載済みでもAllowlistに一致しなければブロックされる。空配列`[]`は全件拒否、設定が存在しない場合は従来のRegistry制限が適用される。さらに`deniedMcpServers`やMCPそのものの無効化はAllowlistより強い。ユーザー・ワークスペース側のAllowlistから管理ルールへ例外を追加することはできない。

サーバーの識別には`serverUrl`や`serverCommand`を優先し、任意に名付けられる`serverName`だけに頼らないよう公式が勧める。重要な境界として、この変更はVS Codeが起動するMCPサーバーに適用され、Agent Hostが管理するサーバーには直接適用されない。画面に同じMCPツールが見えても、どちらの経路で起動したかによって管理範囲が違う可能性がある。

**開発者目線:** 組織導入では「許可」「拒否」「未登録」「名前だけ一致」を組み合わせたテスト表を作りたい。特にAgent Host側の経路を別途確認し、Allowlistがあるから全経路で同じ制限がかかると推測しないことが重要だ。

## 4. Claude Code 2.1.318 — Forkのeffort指定と設定保存・MCP接続の競合修正

**11月4日公開｜公式一次情報**

11月4日公開の[Claude Code 2.1.318](https://github.com/anthropics/claude-code/releases/tag/v2.1.318)では、Modの`$.model.fork`に`effort`指定が追加された。親セッションが高い推論強度で動いていても、短い補助作業だけ`low`にして実行できる。結果にも実際に送ったeffortが含まれるため、意図したコスト・推論強度の設定が反映されたかを後から調べやすい。Mantle経由のAWS利用では`assume_role`も追加され、別AWSアカウントのロール利用や開発者別の費用帰属に関係する。

信頼性の修正も多い。`--continue`で不正なツール呼び出しの再試行が尽きた後に過去の会話が失われることがあった問題、macOSでBashコマンドが多数走るとメモリ増加と停止が起きる問題、許可プロンプトが表示される直前のキー入力を回答として扱ってしまう問題が修正された。後者は単なる表示不具合ではなく、承認UIの操作タイミングに関わる。

さらに`claude mcp add/remove`は設定ファイルのロックを待つか、取得できなければ終了コード1で失敗するようになった。従来はロックなしで書き込むことがあり、別プロセスの更新と競合する可能性があった。ただし公式ノートは、別ジョブの保存によって内容が上書きされる可能性がなお残ると明記する。共有ホームディレクトリで設定更新が失敗したのに成功と表示される事象にも修正が入った。

**開発者目線:** Agentを複数並行実行する環境では、設定ファイルのロック、ログイン更新、セッション再開、許可入力の境界が重要になる。更新後はMCP追加と削除を並行させるテストや、長時間Bash実行中のメモリ推移、セッション再開の回帰テストを実施したい。

## 5. Biome 2.6.5 — Promise.all内のawaitと連鎖比較を新ルールで検出

**11月4日公開｜公式一次情報**

11月4日に[Biome 2.6.5](https://github.com/biomejs/biome/releases/tag/%40biomejs/biome%402.6.5)が公開され、JavaScriptの誤解しやすい構文を検出するNurseryルールが増えた。特に`noAwaitInPromiseMethods`は、`Promise.all([await first(), second()])`のような記述を検出する。配列の最初の要素を評価する時点でawaitが実行されるため、Promise.allに渡す前に処理を待ってしまい、期待した並列性が失われることがある。並列実行が目的ならPromiseを生成してからまとめて待つ必要がある。

`noChainedComparison`は`a < b < c`のような連鎖比較を検出する。数学の記法と違い、JavaScriptでは左の比較が真偽値になり、その値と右辺が比較されるため、意図と異なる結果になり得る。`noArrayForEach`は配列の`forEach()`を`for...of`に置き換えられるケースを報告する一方、MapやSetなど配列ではないと分かる値を除外する。すべてのforEachを無差別に禁止するルールではない。

これらはNursery、つまり安定ルールとして固定される前の試験的なグループに属する。既存プロジェクトで突然すべてをエラー扱いするより、対象ルールを選び、検出件数と誤検知を観察する段階的な導入が適している。静的解析の価値は書式統一だけでなく、非同期処理の意味の取り違えをレビュー前に見つける点にある。

**開発者目線:** Promiseの実行順序に依存するAPI呼び出しをテストで確認し、lintの警告を機械的に消すだけで終わらせないようにしたい。並列化するとリクエスト負荷やレート制限も変わるため、正しい並列性と安全な同時実行数を別々に評価する必要がある。

## 6. ty 0.0.97 — 型推論の循環打ち切りとDjango主キーの解釈を改善

**11月4日公開｜公式一次情報**

11月4日公開の[ty 0.0.97](https://github.com/astral-sh/ty/releases/tag/0.0.97)は、Python向け型チェッカーの推論安定性を改善する更新だ。型推論が循環するケースに反復回数の打ち切りを適用し、bytesリテラルを連結した際に推論される値のサイズへ上限を設けた。複雑な型や生成コードを扱う際、解析器自身が膨大な計算やメモリを使って停止することを防ぐ方向の修正である。

DjangoについてはForeignKeyとOneToOneFieldを主キーとして使う定義への対応が追加された。通常の整数IDを前提としないモデル設計でも、属性の型をより適切に扱えるようになる。またfinalメソッドのOverrideを置き換えるDecoratorへの対応、Union推論で絞り込んだ型変数を保持する修正、空の`VIRTUAL_ENV`を無視する変更、LSPのOutgoing Calls展開時にPanicする問題の修正も含まれる。

型チェッカーは実行時の挙動を変えない一方、開発時のエラー数やエディタ応答速度を変える。循環推論の打ち切りは、解析が終わらないより安全だが、特定の複雑な型について推論結果が変わる可能性もある。リリースノートが説明するのは実装修正であり、あらゆるPythonプロジェクトで性能が改善するというベンチマークではない。

**開発者目線:** 既存の型エラーをBaselineとして保存しているチームなら、更新前後の診断差分を取るとよい。Djangoモデルの主キー、Decorator、ジェネリック型の複雑な箇所を小さな再現コードにしておけば、型チェッカーの改善とアプリ側の型定義ミスを切り分けやすい。

## 7. Wrangler 4.157.0 — Container削除時の課金残りを警告、zstd圧縮を選択可能に

**11月3日公開｜公式一次情報**

11月3日公開の[Wrangler 4.157.0](https://github.com/cloudflare/workers-sdk/releases/tag/wrangler%404.157.0)では、Workersと連動するContainerのライフサイクル管理が改善された。従来の`wrangler delete`はWorkerを削除しても、デプロイ時に作成されたContainer Applicationを残すことがあり、処理を止めたつもりでもリソースと課金が続く可能性があった。今回の更新では対話実行時に関連Containerの削除を提案する。

ただし`--force`やCIのような非対話環境では、Containerを自動削除するのではなく一覧を表示する。残ったリソースは`wrangler containers delete <id>`で明示的に削除する必要がある。自動化の安全性と意図しない破壊を防ぐための分岐だ。IaCやCIでWorkerを破棄するチームは、Worker削除がすべての関連リソース削除を意味しない点を確認したい。

もう一つの変更は、Wranglerが構築するContainerイメージのレイヤーにzstd圧縮を選べること。`WRANGLER_CONTAINER_IMAGE_COMPRESSION=zstd`という環境変数でOpt-inする。圧縮方式の変更は転送量やビルド時間に影響し得るが、公式の変更記録は一律の高速化数値を保証していない。さらに新規プロジェクト生成などで用いる既定のCompatibility Dateが、同梱workerdの2026-11-03へ更新された。

**開発者目線:** 削除操作を含むCIには、WorkerとContainer Applicationを別々に棚卸しする工程を設けたい。zstdはイメージサイズとビルド・配布時間を測り、実行基盤との互換性を確認したうえで採用を判断するとよい。

## 8. Next.js 16.5 Canary — 画像リダイレクトとTurbopack診断を改善

**11月4日公開｜公式一次情報**

11月4日公開の[Next.js 16.5.0-canary.41](https://github.com/vercel/next.js/releases/tag/v16.5.0-canary.41)では、`next/image`の内部画像リダイレクト対応、Turbopackの問題報告にSource Mapを反映したファイルを表示する改善、Request Insightsのフィルターと一時停止操作などが入った。Canaryは次期版に向けた検証用であり、安定版として本番へ一律に更新する対象ではない。

画像リダイレクトの変更は、外部URLだけでなくアプリ内部の画像取得経路でも、リダイレクトを考慮する必要があるという問題に関係する。画像最適化ではキャッシュやPlaceholder生成の責務も整理されている。これらは一見UIの小変更だが、画像の取得先、変換、キャッシュキーが絡むため、同じ画像が別の経路で取得されると配信結果や性能が変わり得る。

Turbopack側では、問題の見出しにSource Mapに基づく元ファイル情報を出す変更が含まれる。ビルド後の生成物ではなく、開発者が編集すべきファイルへ辿りやすくする狙いだ。また開発用Runtime間のローカルトレース共有や、Telemetry要求を計測対象から除外する調整も含まれ、診断データの意味を揃える作業が続いている。

**開発者目線:** Canaryを検証するなら、本番用ブランチとは分けて画像リダイレクト、キャッシュヒット、エラースタック、開発時のHot Reloadを比較したい。表示速度の改善を主張する前に、測定条件と画像最適化設定を固定することが必要だ。

## 9. Electron 45.2.2 — Waylandの非表示親ウィンドウCrashとCSS削除を修正

**11月3日公開｜公式一次情報**

11月3日公開の[Electron 45.2.2](https://github.com/electron/electron/releases/tag/v45.2.2)では、Wayland環境で非表示ウィンドウを親にした際にCrashする問題が修正された。Electronではアプリの画面に出さないウィンドウを内部処理に利用することがあり、表示しないからといってWindow間の親子関係が無関係になるわけではない。Linuxデスクトップでのウィンドウ管理方式の違いが、アプリの安定性に直結する例だ。

同じ更新では`removeInsertedCSS()`が`cssOrigin: 'user'`で挿入したStylesheetを削除できない問題を修正した。動的なテーマ変更、プラグインによる表示調整、アクセシビリティ用CSSなどを使うアプリでは、挿入と削除が対になっていることが重要になる。削除できないと、画面遷移後にも古いスタイルが残り、再挿入で優先順位が複雑になる可能性がある。

Chromiumは156.0.8078.80、Node.jsは24.22.2へ更新された。ElectronはWeb技術とOSネイティブ機能の橋渡しをするため、ChromiumとNodeの更新を単純に「ブラウザのバージョンが上がった」とだけ理解しない方がよい。OS固有のWindow処理やAPI互換性も一緒に検証する必要がある。翌11月4日の45.2.3では複数の上流コンポーネント修正のBackportも公開されている。

**開発者目線:** LinuxのWaylandとX11でウィンドウ生成・破棄の回帰テストを分け、CSS注入を使う画面では挿入・削除・再挿入を繰り返すテストを用意したい。アップデート時はアプリの配布対象OSを基準に優先度を決めるとよい。

## 10. VS Code 1.145 — Timeline拡張API正式化とLocal Agent旧ツールの整理

**11月4日公開｜公式一次情報**

11月4日公開のVS Code 1.145では、拡張機能がTimelineビューへ独自の履歴を追加するAPIが正式化された。`workspace.registerTimelineProvider`はファイルやフォルダー単位、`workspace.registerWorkspaceTimelineProvider`はワークスペース全体の履歴を提供する。拡張が追加した履歴はGit CommitやLocal Historyと並び、`TimelineItem.resourceUri`にその時点の内容を指定すると、Compare Selectedによる差分比較が可能になる。

この仕組みは単なる一覧表示ではない。例えば独自の生成処理や保存スナップショットを扱う拡張が、エディタ標準の履歴UIへ統合できる。利用者が別の専用パネルを覚える必要が減り、Git履歴とは別の作業履歴も比較しやすくなる。ただし履歴の保存方式や復元可能性は提供する拡張側の実装に依存する。APIが正式化されたことは、個別拡張のデータ永続化を保証するものではない。

同じ[公式リリースノート](https://code.visualstudio.com/updates/v1_145)ではLocal Harnessの`#installExtension`、`#runCommand`、`#newWorkspace`や`/new`などの旧Agentツールが削除された。新規ワークスペース生成では空フォルダーを開いてAgentへ指示し、通常のツールで必要なファイルや設定を作成する方式へ移る。拡張の推奨は`.vscode/extensions.json`に記載して、利用者が確認して導入する。

**開発者目線:** VS Code拡張を開発する場合はTimeline APIの採用余地を調べ、過去のスナップショットを安定したURIで取得できるかを検証したい。Agent向けのPromptやCustom Agentに旧ツール名が残っていないかも検索し、移行後の操作をテストする必要がある。

## 👀 今日ならこの3つ

### 🥇 VS CodeのNested Session

異なるAgent Harnessを同じ作業の中で比較できるため、設計レビューや実装検証の進め方が変わる可能性がある。

### 🥈 Claude Codeの設定競合修正

並列Agent運用で起こる保存競合や権限操作の問題に直接関係し、実運用の安定性に効く。

### 🥉 Biomeの非同期処理ルール

Promiseの並列実行を妨げる書き方を検出でき、日常的なレビューの見落としを減らせる。
