## 1. GitHub Actions — pull_request_targetの既定ブロックを12月2日に延期、11月に予行停止

**11月2日発表｜CI/CD・サプライチェーン防御**

[GitHub公式Changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/)は、公開リポジトリで`pull_request_target`イベントを原則ブロックする既定ルールの強制開始を、11月2日から**12月2日**へ延期した。GitHub Free、Team、Enterprise Cloudの公開リポジトリが対象で、Private・InternalリポジトリとEnterprise Serverは対象外。現在はEvaluate Modeで、どのWorkflowがブロックされるかを事前確認できる。

`pull_request_target`はForkの提出元ではなくBase RepositoryのContextで動くため、Secretや書き込み権限に触れられる。そこで信頼できないForkのコードをCheckoutして実行すると、攻撃者へ権限を渡す危険がある。一方、ラベル付けやコメントなどBase側の権限を必要とする正当な用途もあるため、イベント名だけで一律に危険と判断せず、実際に何を実行するかを確認する必要がある。

**11月9日・16日の各16:00〜18:00 UTC**にはBrownoutとして一時的に強制ブロックされ、対象WorkflowのRunは失敗Annotationを残して実行されない。恒久適用前に、不要なTriggerを外すか、必要なWorkflowだけをActions Event Policyで明示的に許可する。例外許可をRepository全体に広げず、Workflow File単位で対象を絞る設計が推奨される。

> [!WARNING]
> Brownoutによる失敗はアプリコードの回帰ではない。12月2日の恒久適用と区別して調査したい。

**開発者目線:** `.github/workflows`を検索し、Fork由来のCheckout、Shell実行、依存Install、外部Action、Token権限を棚卸ししたい。特権を必要とするJobと不信頼コードを扱うJobを分離できるか検討することが、単純にAllowを付けるより本質的な対策になる。

## 2. Cloudflare Workers — 11月17日から新Module RegistryをCompatibility Dateで既定化

**11月2日発表｜JavaScript Module・互換性移行**

[Cloudflare公式Changelog](https://developers.cloudflare.com/changelog/post/2026-11-02-module-registry-default/)によると、JavaScript Workersで`compatibility_date`を**2026-11-17以降**に設定すると新Module Registryが既定になる。従来は`new_module_registry`というFlagで試す機能だった。Python Workersは引き続き旧Registryを使う。単一APIの追加ではなく、Moduleの発見と読み込みというRuntimeの基盤を切り替える変更だ。

新RegistryはJavaScript標準とNode.js互換性の改善を目的としている。`nodejs_compat`を使うWorkerではCommonJSの`require()`からES Moduleを読み込めるが、対象Moduleまたは依存先にTop-level Awaitがあると失敗する。また`import.meta.url`、`import.meta.main`、`import.meta.resolve()`でEntry PointやBundle内ModuleのURLを扱える。ただしResolveはModuleの存在確認やNetwork Fetchを実行しない。

既存WorkerはCompatibility DateやFlagを変更しない限り挙動を維持する。先行検証には`new_module_registry`、新Dateでも旧挙動を維持するには`legacy_module_registry`を指定できる。新Registryは不正なImport Attributesを拒否するため、曖昧な構文を含む依存Packageは移行時に問題が表面化し得る。Bundlerが`import.meta`を書き換える場合も注意が必要だ。

| 構成 | 11月17日以降の扱い | 確認項目 |
| --- | --- | --- |
| JS・新しいDate | 新Registryが既定 | CJS/ESM・Import Attributes |
| JS・古いDate | 従来挙動 | 将来のDate更新 |
| Python Workers | 旧Registry継続 | JSとの差異 |

**開発者目線:** Compatibility Dateを依存更新と同じく変更管理し、CJS/ESM混在、Top-level Await、Dynamic Import、Unbundled DeploymentのSmoke TestをCIに用意したい。既定値の変化は目立たないが、BuildとRuntimeの再現性に直結する。

## 3. Astro 7.4.5 — SandboxからのDev Server誤停止と環境変数・URL処理を修正

**11月2日公開｜Web Framework・Buildの安全性**

[Astro 7.4.5公式Release](https://github.com/withastro/astro/releases/tag/astro%407.4.5)は、Server管理、環境変数、URL検証、Dynamic Tagを修正した。`astro dev status`などのBackground Server Commandが、Sandboxや別UserからProcessへSignalを送れない場合、稼働中ServerのLock Fileを消してしまう問題が修正された。Serverは生きているのに管理情報だけ失われると、誤った停止判定や重複起動につながる。

Build時には`import.meta.env`の値に`$$`や`$&`が含まれる場合、Server Codeが環境変数Objectを直接読む経路で値が壊れる問題を修正した。PasswordやTokenに特殊文字が入ることは珍しくなく、文字列の完全性は重要だ。ただし環境変数が正しく読めることと、秘密情報をClientへ公開してよいことは別問題である。

不正なPercent Encodingを含むRequest Path、例えば`/%C0%AF`や単独の`%`は**400 Bad Request**として扱われる。またDynamic Tag、JSX、MDXでString Tag Nameの検証を揃え、`/`や`=`で生成Markupが変化しないよう制約した。無効な先頭文字は例外になる。同日の[@astrojs/vercel 11.0.18](https://github.com/withastro/astro/releases/tag/%40astrojs%2Fvercel%4011.0.18)では、MonorepoのDynamic Path TraceがWorkspace全体をGlobし、無関係なFileをFunction Bundleへ含め得る問題も修正された。

**開発者目線:** Build成功だけでは環境変数の値が正しいと限らない。特殊文字を含むFixture、Invalid URLの400応答、SandboxからのServer状態確認、Dynamic Tagの境界を回帰テストへ入れたい。Serverless Bundleは容量だけでなく、意図しないFile混入も点検したい。

## 4. Cloudflare Workers — Request.signalの切断通知を11月17日から既定で有効化

**11月2日発表｜AbortSignal・非同期処理**

[Cloudflare公式Changelog](https://developers.cloudflare.com/changelog/post/2026-11-02-request-signal-default/)によると、`compatibility_date`が**2026-11-17以降**のWorkersでは、Client切断を`request.signal`のAbort Eventとして既定で通知する。これまでは`enable_request_signal`のFlagが必要だった。機能自体は2025年5月に導入されており、今回の新情報は既定化の時期と条件だ。

利用者が画面を閉じた後もWorkerが遅い外部APIを呼び続けると、結果を受け取る相手がいないのに通信・計算コストが残る。`request.signal.addEventListener('abort', ...)`で切断を観測し、`fetch(url, { signal: request.signal })`へSignalを渡すと不要なSubrequestを中止できる。ただしAbort Eventが届くことと、下流処理がすべて自動停止することは別だ。

今回の変更は`request_signal_passthrough`を有効化しないため、Signalの伝播は**明示的に指定**する必要がある。検索候補取得のようなReadは中止しやすいが、確定済み注文や監査Logの書き込みをClient切断と同時に止めると、整合性を壊す可能性がある。新Dateで旧挙動へ戻すには`disable_request_signal`を使い、先行検証には`enable_request_signal`を使える。

> [!NOTE]
> Client切断は処理の失敗と同義ではない。副作用の完了保証と通信の中断を分けて設計する。

**開発者目線:** 非同期処理を中断可能なReadと完了保証が必要なWriteに分類し、Signalの伝播先を明示したい。ブラウザでRequestを中断するE2E Testを作り、外部API呼び出し回数、Resource Cleanup、DBへの書き込み状態を測ると効果を検証できる。

## 5. Next.js 16.4.4 — Turbopack CSS更新とPPR再開時のCSP Nonceを修正

**11月2日公開｜Stable系列へのBug Fix Backport**

[Next.js 16.4.4公式Release](https://github.com/vercel/next.js/releases/tag/v16.4.4)は、Canaryの新機能をまとめて導入するのではなく、16.4系列へ修正をBackportするMaintenance Release。Turbopack起動時のCSS Update取りこぼし時にReloadする修正、Partial Prerendering（PPR）のResumeでShared Runtime BootstrapへCSP Nonceを反映する修正、Route AnalyzerのIndex参照修正などが含まれる。

CSSのHot Updateを取りこぼすと、Sourceは更新済みなのにBrowserの表示だけ古くなる。開発者はStyleの記述を疑いがちだが、Dev ServerとClientの同期が原因の場合もある。今回の修正はUpdateを受け取れない場合にReloadし、画面とSourceの整合性を優先する。Turbopack全体が何倍速くなるといった性能改善を示すReleaseではない。

CSPのNonceは、許可されたScriptだけを実行するためHTMLへ付与する一時的な値。PPRは静的な部分とRequest時に再開する部分を組み合わせるため、Resume経路のBootstrapにNonceが付かないと、正当なScriptまでPolicyでブロックされ得る。今回の修正はその接点を整えるものだ。ほかにStrict Module Factory Chunkの最適化をRevertし、`jsonwebtoken`から`fast-jwt`へ切り替える変更がある。

公式Noteは**11月向けのSecurity Releaseを翌日に公開予定**と記しているが、16.4.4自体を未発表のSecurity Advisory対応版と混同してはいけない。予定と実際の公開は別であり、正式なVersionとAdvisoryを確認する必要がある。

**開発者目線:** PPRと厳しいCSPを併用するサイトではResume後のConsole Errorを確認したい。Dev ServerのCSS更新は連続保存と初回起動直後を含めて検証する。Security Release予告だけで対応済みと判断せず、公開物を追うべきだ。

## 6. Cloudflare Flagship — Feature FlagをローカルStoreで評価、Offline開発に対応

**11月2日発表｜Feature Flag・テスト再現性**

[Cloudflare Flagship公式Changelog](https://developers.cloudflare.com/changelog/post/2026-11-02-local-flag-store/)で、Local Development中のFlagship BindingがRemote Appではなく**Local Flag Store**を参照して評価できるようになった。`wrangler dev`、Cloudflare Vite Plugin、Vitest Integration、`cf dev`が対象。OfflineでもFlag分岐をテストでき、開発中の変更がProductionのFlagに影響しない構成を作れる。

Local Storeは初期状態では空で、Flag評価はApplication Codeが渡したDefault Valueを返す。Local Flagを作成・更新・評価するには`wrangler flagship flags`の各Commandに`--local`を付ける。Remote AppのFlagを一括取得する`npx wrangler flagship flags pull <APP_ID>`も利用できる。Local Explorerや`cf flagship`からの管理にも対応した。

Remote Appを参照したい場合はBindingに`remote: true`を指定する。Local StoreにはWrangler **4.135.0**以上、または`@cloudflare/vite-plugin` **1.56.0**以上が必要。Local ExplorerのFlagship機能はWrangler **4.148.0**以上、またはVite Plugin **1.63.0**以上が必要だ。既存Toolchainが古い場合、Changelogを読むだけで機能が利用可能になるわけではない。

| 環境 | Flagの参照先 | 主な用途 |
| --- | --- | --- |
| ローカル開発 | Local Store | Offline・分岐確認 |
| 自動テスト | Local Store | 条件固定と再現 |
| Remote明示設定 | Remote App | 配信設定の確認 |

**開発者目線:** Feature FlagをRemote設定へ依存させると、CIが実行時刻によって異なる結果になる。Local Storeで有効・無効・未定義の状態をFixture化し、UIやAPIの分岐を固定して検証したい。Productionの段階Rolloutと開発時の決定的なテストを分離できる点が実用的だ。

## 7. Gemini API CLI 0.4.5 — Agentの継続トークンとSandbox操作を拡充

**10月30日公開・今週の見逃し｜API操作用CLI**

[Google公式Gemini API CLI 0.4.5](https://github.com/google-gemini/gemini-api-cli/releases/tag/v0.4.5)では、Interactionsの`continuation_token`や`requires_continuation`状態、`continuation_ids`、Sandbox Runtimeの操作基盤、Video Upscale Task Parameterなどが変更履歴に並んだ。対話型Coding AgentのGemini CLIとは**別のRepository・別のTool**であり、Gemini APIをCommand Lineから操作するためのCLIだ。

Agentの処理が一回の同期Requestで終わらない場合、Clientは進行状態を保持して続きを取得する必要がある。Continuation TokenやIDは、そのような分割処理を表すInterfaceの一部。ただしSchema Fieldが追加されたことと、全Model・全Planで同時に使えることは別で、実際のAPI応答やDocumentationを確認する必要がある。

`agent run --background`を指定した際にStreamingを無効化する`stream: false`を暗黙に適用する修正も入った。Background Jobの起動と同じTerminalへの逐次Token表示を同時に要求すると、Lifecycleが曖昧になる。今回の変更はCommand指定と実行形態を整えるものだ。また`transcribe`の既定Modelは`gemini-3.5-transcribe`へ変更され、Video UpscaleのTask Parameterも追加された。

ReleaseにはOpenAPI Generator更新やSchema再生成も含まれる。API生成CLIではEnumやStatusの差分が自動で取り込まれるため、未知のStatusを未処理にすると、進行中のAgentを失敗と誤判定したりPollingを止めたりする可能性がある。継続処理の状態を単純な成功・失敗の二択で扱わない設計が重要だ。

**開発者目線:** 非同期Agentを組み込むならRun ID、Continuation、Cancel、RetryをState Machineとして設計したい。CLI更新時にはBackground Runの戻り値、終了Code、Streamingの有無、再開条件を小さなContract Testで確認する。

## 8. Cloudflare Access — Service TokenにTagを付け、Policyで属性単位の認可が可能に

**11月2日発表｜Machine-to-Machine認証**

[Cloudflare Access公式Changelog](https://developers.cloudflare.com/changelog/post/2026-11-02-service-token-tags/)で、Service TokenへKey-Value形式のTagを付け、そのTagをService Auth Policyの条件に利用できるようになった。各Tokenに最大**5個**のTagを設定でき、例として`environment: production`や`team: payments`が挙げられる。DashboardとAPIで編集でき、Service Tokens画面で検索・Filterも可能だ。

複数Serviceが同じAccess Applicationを利用する場合、個々のToken IDをPolicyへ列挙すると、Tokenの追加やRotationのたびにPolicy更新が必要になる。Tag Selectorなら、例えば`environment=production`を持つ**有効なToken**だけを許可する条件を作れる。認可をTokenの識別子ではなく、運用上の属性へ結び付けられる点が新しい。

Policyは`service_token_tag`の`key`と`value`を完全一致で評価する。単なる表示用Labelではなくアクセス許可条件なので、Tagを誰が編集できるかが重要になる。Token自体の有効性検証を省略する機能ではないし、`team`の文字列が組織の人事情報と自動同期するわけでもない。命名規則と変更権限は運用側で管理する必要がある。

TagはResource Taggingからも検索でき、Credentialの棚卸しに役立つ。一方、Tagの誤設定がアクセス範囲の拡大に直結するため、ProductionとStagingを区別するTagをHuman Reviewなしで変更できる構成は避けたい。

**開発者目線:** Service Token発行WorkflowにTagのValidationを組み込み、許可するKeyとValueを制限したい。Rotationのテストでは新旧TokenのTagとPolicy判定が一致するかを確認する。IDの羅列から属性ベース認可へ移す際は例外的なTokenの見落としに注意する。

## 9. GitHub Security Assessment — Repositoryの保護状態をRisk評価へ表示

**11月2日発表｜Security Coverage・組織運用**

[GitHub公式Changelog](https://github.blog/changelog/2026-11-02-security-risk-assessments-include-repository-protection-status/)によると、Code Security Risk AssessmentとSecret Risk Assessmentで、検出結果が**保護されたRepositoryか、保護されていないRepositoryか**を表示するようになった。Organization AdminとSecurity ManagerはOrganizationのSecurity TabにあるAssessmentsから評価を開始できる。GitHub Enterprise CloudとGitHub Teamで利用可能で、Enterprise ServerではSecret Risk Assessmentへの対応が**3.24**で予定されている。

新しい脆弱性検出器の追加ではなく、既存の検出結果をSecurity Coverageと結び付ける改善だ。例えば同種のSecret Exposureが複数Repositoryに見つかったとき、既に保護済みのRepositoryでの運用改善と、保護未導入のRepositoryへの展開では、優先すべきActionが異なる。Coverageが分からなければ、単純な件数比較で対策の優先順位を誤りやすい。

Repository Protection StatusをBranch Protectionの有無と同義と決めつけない方がよい。公式説明はRisk Assessment上の保護・未保護の区分を示しており、各組織が使うSecurity機能やPolicyの詳細はDocumentationで確認する必要がある。表示が増えたこととRepository設定が自動修復されることも別だ。

未保護Repositoryに重大なFindingが集中していないかを見る際は、Repository数だけでなく変更頻度、公開範囲、Secretの影響範囲も合わせて判断したい。Archiveと活発なProduction Projectを同じ重みで扱うと、実際のRiskを表しにくい。

**開発者目線:** 組織のSecurity改善では検出件数の削減だけでなく、未保護Repositoryの削減も追跡可能な目標にできる。Assessmentを定期比較し、新規Repository作成時点で必要なSecurity機能を適用する仕組みを検討したい。

## 10. Cloudflare AI Search — 課金開始を12月1日に延期、既定Sync間隔を24時間へ

**11月2日発表｜検索Index・運用コスト**

[Cloudflare AI Search公式Changelog](https://developers.cloudflare.com/changelog/post/2026-11-02-billing-postponed-default-sync-interval/)は、AI Searchの課金開始を**11月1日から12月1日**へ1か月延期したと発表した。12月1日より前のAI Search利用は課金されず、料金表と含まれる利用枠は変更しない。これは価格改定ではなく、課金開始時期の変更だ。

同時にAI Search Instanceの**既定Sync間隔が6時間から24時間**へ変更される。検索対象Documentを更新しても、次回Syncまで新しい内容がIndexへ反映されない可能性がある。RAGのように検索結果をModelへ渡す仕組みでは、生成Modelが正確でも、参照した情報が古ければ回答の信頼性は下がる。既定値の変更がアプリケーションの鮮度要件に影響する点が重要だ。

Sync間隔は固定ではなく、Instance SettingsまたはAPIの`sync_interval`で**15分〜24時間**から選べる。更新の少ないKnowledge Baseでは長い間隔が合理的な一方、運用Runbookや障害対応情報では24時間の遅延を許容できないこともある。更新頻度を高めること自体が目的ではなく、Sourceの更新特性と利用者の期待に合わせて決めるべきだ。

| データの性質 | Sync設計 | 検証指標 |
| --- | --- | --- |
| 更新の少ない公開資料 | 長めの間隔 | 反映までの時間 |
| 頻繁に変わる運用文書 | 短めの間隔 | 古い回答の発生率 |
| テスト用Corpus | 手動更新も併用 | Fixtureの再現性 |

**開発者目線:** RAGを評価する際はModelの正答率だけでなく、Document更新から検索結果へ反映される時間を測りたい。課金開始延期の期間を使ってSync頻度と運用要件を検証し、Defaultに依存しない明示設定を残すとよい。
