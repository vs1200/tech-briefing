## 1. GitHub CLI 2.105.0、PRイベント待機をポーリングなしで実行

**発表日：2026年11月18日｜公式一次情報**

11月18日、GitHub CLI 2.105.0でGitHub Event Streamsに対応する新しいgh eventコマンドが案内された。従来、PRのレビュー提出やチェック完了を待つ自動化では、一定間隔でAPIを呼ぶポーリングを組み込むことが多かった。短い間隔なら反応は速いが無駄な通信が増え、長い間隔ではレビュー完了後も待たされる。今回の仕組みは、関心のあるイベントを購読してストリームから受け取る方式へ転換する。

gh event listenにPRのURLとイベント種別を渡すと、購読を作成し、イベントごとにJSONを一行ずつ出力する。既定では最初のイベントで終了し、--countで受信件数、--followで継続監視、--timeoutで待機上限を設定できる。--jqや--templateで必要なフィールドだけ取り出せるため、シェルスクリプトやコーディングエージェントの次の判断につなぎやすい。レビュー、PRの状態やheadの変化、マージ競合、チェック完了が対象だ。

購読自体を管理するcreate、list、view、deleteのサブコマンドも用意された。長時間動くエージェントが状態確認を繰り返す代わりに、イベントを受けてから次の作業を開始する設計が可能になる。ただしEvent Streamsとgh eventはプレビューで、GitHub.comの利用にはウェイトリスト経由のアクセスが必要だ。CLIを更新しただけですべてのアカウントで利用できるわけではない。

**開発者目線:** PRを作成したエージェントがレビューを待ち、指摘を修正して再度チェック完了を待つ流れに適する。イベントの重複受信、通信切断、購読の失効を想定し、受信したイベントをきっかけにPRの最新状態を再取得する設計が堅実だ。ポーリング削減と、イベントだけを真実とみなさない再確認を両立させたい。

[公式出典](https://github.blog/changelog/2026-11-18-wait-for-pull-request-events-with-github-cli/)

## 2. CopilotにMCPコネクター8サービス追加、DBとCIを同じ作業文脈へ

**発表日：2026年11月18日｜公式一次情報**

GitHubは11月18日、Copilotの検証済みMCPコネクターに8サービスを追加した。対象はBox、Buildkite、Calendly、ClickUp、Mixpanel、Supabase、Webflow、Wix。既存のSlack、Figma、Sentryなど25以上の接続先に加わる。MCPはAIエージェントが外部サービスの機能やデータへアクセスする共通の接続方式で、チャット画面に資料を貼り付けるだけの連携とは異なる。

今回の追加では、例えばBuildkiteの失敗したビルドを確認してコード修正へ進む、Supabaseのスキーマを見てからマイグレーションを書く、といった横断的な作業が想定されている。単に情報を検索できるだけでなく、開発作業の前提となる実際の環境状態を参照できることが利点だ。ただし外部の状態を読み取ることと、外部サービスに変更を書き込むことは権限やリスクが異なる。

接続はCopilot appのCustomize、Copilot CLIの/mcp、VS CodeのAgents画面、github.comのカスタマイズページから行う。全Copilotプラン向けのパブリックプレビューだが、BusinessとEnterpriseでは管理者がEditor preview featuresを有効にする必要がある。MCP許可リストを個別列挙している企業では、新しいコネクターの追加許可も必要だ。Boxなど接続先側の管理者承認が必要なケースもある。

**開発者目線:** 接続数の多さより、操作権限の最小化と結果の検証が重要になる。まず読み取り専用でビルド失敗の原因分析やスキーマ確認を試し、書き込みはレビュー付きにする。エージェントが参照したデータの時点と環境名をログに残すと、古いスキーマに基づく変更や本番環境への誤操作を避けやすい。

[公式出典](https://github.blog/changelog/2026-11-18-connect-supabase-box-calendly-and-more-to-copilot/)

## 3. Gemini 4 NeonがGitHub Copilotで一般提供、速度と変更範囲に注目

**発表日：2026年11月18日｜公式一次情報**

11月18日、GitHubはGemini 4 NeonをCopilotで一般提供すると発表した。GoogleのモデルをCopilotの複数の画面から選べるようにするもので、エージェント型コーディング、複数段階のツール利用、知識作業を主な用途としている。モデル選択は単に回答の文体を変える設定ではない。コード編集の範囲、ツールの使い方、回答開始までの待ち時間などが変わる可能性がある。

GitHubが引用するGoogleの説明では、Gemini 4 Carbonに近い品質を、タスク当たりのトークン費用を抑えて提供するという。また応答開始が速く、要求されていないコード変更や、コード・テスト結果に関する裏付けのない主張を減らすとされる。いずれも提供元の評価に基づく説明であり、独立した実測値やすべてのリポジトリでの再現を意味しない。価格も固定の定額モデルではなく、利用量課金における提供元の定価が適用される。

利用対象はCopilot Pro+、Max、Business、Enterprise。VS Code、Visual Studio、Copilot CLI、coding agent、Copilot app、github.com、モバイル、JetBrains、Xcode、Eclipseなどに段階的に展開する。企業向けにはモデルポリシーで利用可否を制御できる。一般提供という表現と、個々のアカウントでモデル選択欄に現れる時期が一致しない点に注意したい。

**開発者目線:** 同じ修正課題をCarbonとNeonに与え、テスト成功率だけでなく差分行数、無関係なファイルへの変更、ツール呼び出し数、実行時間を比較したい。特に小さなバグ修正で意図しないリファクタリングが減るなら、レビュー負荷の低下につながる。ベンチマークの公称値だけでなく実際の変更差分を評価軸に含めるとよい。

## 4. GitHub Copilotのチーム共通プラグイン設定が一般提供

**発表日：2026年11月18日｜公式一次情報**

11月18日、GitHubはCopilotのチーム単位カスタマイズを一般提供した。これまで各開発者が個別にプラグインを探して設定する運用では、同じチームでも使えるエージェント機能が揃わず、手順書に書かれた操作が他の人の環境では再現できないことがあった。新機能は個人の自由な設定と、組織全体の強制ポリシーの中間に、チーム共通の初期状態を設けるものだ。

チームのmaintainerまたは組織ownerが、github.comのチームページにあるCustomize Copilotからプラグインを選ぶ。Copilot内蔵マーケットプレイス、企業独自のマーケットプレイス、GitHubリポジトリに置かれたマーケットプレイスを参照できる。選択したプラグインはチームの直接所属メンバーに対し、VS Code、Copilot app、Copilot CLIで既定有効になる。子チームには自動継承されない。

重要なのは、チーム設定が企業や組織の許可・禁止ポリシーを上書きしない点だ。個々のメンバーは許される範囲で既定プラグインをオフにできる。したがって共通設定は強制インストールの代替というより、セットアップの再現性を高める仕組みである。提供対象はCopilot BusinessとEnterpriseで、すべての個人プランへ開放されたという発表ではない。

**開発者目線:** 新規参加者が最初の一日で同じエージェント機能を使えるように、推奨プラグインの最小セットを定義する運用に向く。権限の強いツールを初期状態で大量に有効化するのではなく、用途ごとに導入理由と責任者を記録したい。子チームへ継承されない仕様も、オンボーディング時の確認項目に含める必要がある。

[公式出典](https://github.blog/changelog/2026-11-18-customize-github-copilot-for-your-team/)

## 5. GitHub Teamでセキュリティリスク評価が自動実行へ

**発表日：2026年11月18日｜公式一次情報**

GitHubは11月18日、GitHub Teamプランの組織に対してセキュリティリスク評価を自動実行するようにしたと発表した。評価結果は組織管理者とセキュリティマネージャーが確認でき、公開されてしまった認証情報やコードの脆弱性など、現在のリスクを把握する材料となる。従来のように個々の開発者が問題を見つけてから報告する流れだけに頼らず、組織レベルで棚卸しするきっかけを作る。

この発表で強調されているのは、無料の評価を自動で実施して発見事項を可視化する点だ。評価を実行したことと、すべての脆弱性が検出されたこと、あるいは修正が自動適用されたことは別である。スキャンは対象範囲や検出手法に限界があり、リポジトリに保存されていないシークレット、実行時設定、依存サービスまで網羅するとは限らない。

発見された認証情報については、単にリポジトリから文字列を削除するだけでは不十分な場合がある。既に取得された可能性を考え、トークンの失効、ローテーション、アクセスログ確認まで進める必要がある。コード上の脆弱性は、到達可能性、外部入力、実行権限、公開範囲などによって優先順位が変わる。自動評価は修正順序を決める出発点として使うのが妥当だ。

**開発者目線:** まず管理者が検出結果を分類し、漏洩した資格情報と実際に攻撃可能なコード経路を優先して扱いたい。発見数をゼロにすることだけを目標にせず、検知から失効までの時間、再発した原因、修正のテストを記録する。自動評価の導入で生まれた時間を、認証情報をコードへ置かない設計へ振り向けることが重要だ。

[公式出典](https://github.blog/changelog/2026-11-18-security-risk-assessments-run-automatically-on-github-team/)

## 6. GitHub ActionsのRHEL 9・10ランナーイメージが正式提供

**発表日：2026年11月19日｜公式一次情報**

11月19日、GitHub ActionsのGitHub-hosted larger runners向けにRed Hat Enterprise Linux 9と10のイメージが一般提供となった。2026年6月からのパブリックプレビューを経た変更で、本番ワークフローに使えるサポート対象となる。開発時はUbuntuなどでビルドし、配布先はRHELという構成では、標準ライブラリやシステムパッケージの差がデプロイ後の不具合につながることがある。

今回の提供によって、実際の配布先と同じOS系列上でビルドやテストを実行できる。RHELイメージを土台にして、必要なツールや依存関係を組み込んだカスタムイメージを用意することも可能だ。GitHubの説明では、新しいLinux x64のlarger runnerを作成し、partner imagesから対象のRHELイメージを選ぶ。既にプレビュー版を使っていたランナーは移行操作なしで継続利用できる。

利用対象はGitHub TeamとGitHub Enterprise Cloudのlarger runnersであり、一般的なubuntu-latestの無償枠と同じ条件だと解釈してはいけない。ランナーのサイズや課金、必要な組織設定を確認する必要がある。OSの一致は互換性確認に役立つが、実際の本番サーバーとカーネル設定、アーキテクチャ、セキュリティポリシー、外部サービスまで完全に一致するわけではない。

**開発者目線:** RHEL向けに配布するCLIやネイティブモジュールは、Ubuntuでのユニットテストに加えRHEL上の結合テストを組みたい。共有ライブラリの依存関係、ファイル権限、暗号ライブラリ、パッケージマネージャーの違いをCIで早期に検出できる。実行コストを抑えるなら、全PRでは軽量テスト、リリース候補でRHEL検証といった分担が現実的だ。

[公式出典](https://github.blog/changelog/2026-11-19-red-hat-enterprise-linux-runner-images-now-generally-available/)

## 7. GitHub EnterpriseのS3監査ログ転送、GHE.comでもOIDC認証に対応

**発表日：2026年11月19日｜公式一次情報**

11月19日、GitHubはデータ所在地を指定できるGitHub Enterprise Cloud、いわゆるGHE.comで、Amazon S3への監査ログストリーミングにOpenID Connect認証を利用できるようにした。従来github.comで使えた仕組みの対象拡大だ。監査ログには組織の管理操作や権限変更などの記録が含まれ、継続的な保存と検索がインシデント対応に重要になる。

長期間有効なAWSアクセスキーをGitHub側に登録して連携する構成では、そのキー自体の保管、定期更新、漏洩時の影響範囲が運用課題になる。OIDCを使う方式では、信頼関係に基づいて必要な認証を行えるため、GitHubに長期有効なAWS資格情報を保存せずに済む。認証方式の変更は監査ログの内容を増やす機能ではなく、転送経路の資格情報管理を改善するものだ。

ただしOIDCなら設定ミスが起こらないわけではない。AWS側の信頼ポリシーで想定外の主体を許可したり、S3の書き込み権限を広く付与したりすれば、ログの保護は弱くなる。ログ保存先の暗号化、削除防止、保持期間、アクセス権限、転送停止時の監視も別途設計が必要だ。GHE.comのデータ所在地要件とS3の保存リージョンの整合も確認したい。

**開発者目線:** 監査ログ基盤をIaCで管理する場合、OIDCの信頼条件とS3権限をレビュー可能なコードとして固定したい。設定変更後はテストイベントがS3へ届くか、転送が止まったとき検知できるかを確認する。認証情報のローテーション作業を減らすだけでなく、障害時にログが欠落しない監視までセットで考えると実用性が高い。

[公式出典](https://github.blog/changelog/2026-11-19-s3-audit-log-streaming-with-openid-connect-expands-to-ghe-com/)

## 8. Azure DevOpsからGitHubへのライブ移行が正式提供、作業継続しながら同期

**発表日：2026年11月19日｜公式一次情報**

11月19日、GitHubはAzure DevOps Servicesからデータ所在地指定のGitHub Enterprise Cloudへ移すEnterprise Live Migrationsを一般提供した。大規模なリポジトリ移行では、作業を止めて全履歴を一括コピーし、検証後に再開する方式だと停止時間が長くなりやすい。今回の方式は移行先へ継続同期しながら、開発チームが元の環境で作業を続けられる点が特徴だ。

管理はAzure DevOpsのポータルまたはCLIから行い、事前検証と移行ライフサイクルの追跡を備える。Gitの履歴、ブランチ、タグだけでなく、PRのタイトル、説明、コメント、ユーザー履歴も同期対象となる。Azure DevOpsのブランチポリシーはGitHubのrulesetsへ移されるため、単なるソースコードのコピーにとどまらず、レビューや保護ルールも移行対象として扱う。

切り替えのタイミングはチーム側で決められ、短いカットオーバー期間で最終移行を行う。Azure BoardsとAzure Pipelinesを使い続ける構成もサポートされ、Boardsの接続作成やPipelinesの移行先リポジトリへの再接続を支援する。一方、作業項目やパイプライン定義そのものはAzure DevOps側に残る。すべてがGitHubへ統合されるという意味ではない。

**開発者目線:** 移行前後でコミットSHA、ブランチ保護、PRコメント、CIトリガー、サービス接続の差を一覧化して検証したい。特に移行後のCIが元のAzure DevOpsに残る場合、リポジトリURLや認証トークンの変更が失敗要因になる。試験移行で差分を洗い出し、カットオーバー時に書き込み先が二重化しない手順を作ることが大切だ。

[公式出典](https://github.blog/changelog/2026-11-19-enterprise-live-migrations-from-azure-devops-generally-available/)

## 9. CopilotコードレビューにAdaptive深度とシークレット検出を追加

**発表日：2026年11月17日｜公式一次情報**

11月17日、GitHubはCopilot code reviewのAdaptiveレビュー深度、リポジトリ横断の文脈参照、シークレット検出などを発表した。変更が小さく単純なPRと、認証処理を変更する危険度の高いPRに同じ計算量を使うのは効率的ではない。AdaptiveはPRの複雑さとリスクに応じてLite、Balanced、Maxのいずれかを選び、どの深度を選んだかをレビュー画面に示す。

Adaptiveはパブリックプレビューで、PR単位または個人、リポジトリ、組織、企業の既定値として選択できる。既定のレビュー深度は引き続きBalancedであり、Adaptiveが自動的に全利用者へ適用されるわけではない。さらに企業や組織、リポジトリで設定した最大深度を超えて選ぶことはない。運用コストを管理する上限設定と、PRごとの柔軟な深度選択を両立させる仕組みだ。

横断文脈では関連する公開リポジトリや別リポジトリのドキュメント、指示、スキルを参照して影響を探せる。シークレット検出はメインブランチへ到達する前に危険な値を指摘することを狙う。いずれもレビューの補助であり、すべての依存関係や漏洩情報を確実に見つける保証ではない。公開リポジトリ以外の文脈を無条件に取得できるとも限らない。

**開発者目線:** レビュー深度の自動選択を評価する際は、実際のバグ指摘率、誤検知、レビュー待ち時間、修正採用率を追跡したい。特に認証やデータ移行のPRで浅いレビューが選ばれた場合は手動で深度を上げる余地を残す。シークレット検出もpush保護や専用スキャナーの代替ではなく、多層防御の一段として利用するのが適切だ。

[公式出典](https://github.blog/changelog/2026-11-17-copilot-code-review-adaptive-effort-secret-detection-and-more/)

## 10. GPT-6.2 AstraとSolがCopilotで一般提供、コードレビュー性能を訴求

**発表日：2026年11月17日｜公式一次情報**

GitHubは11月17日、OpenAIのGPT-6.2 AstraとGPT-6.2 SolをCopilotで一般提供した。どちらもエージェント型コーディングやコードレビューを想定したモデルで、Astraはターミナル作業を含む開発タスク、Solは複雑な開発作業と詳細なレビューに重点が置かれる。これはCopilot内での提供開始の発表であり、他の製品やAPIでのモデル提供状況を示すものではない。

GitHubの初期評価では、Astraは以前のGPT-6 Astraよりコードレビューで実際の問題を多く検出し、エージェントタスクを少ないトークンで完了したとされる。SolはGPT-6.1 Solに比べて実際の問題の検出数がほぼ2倍になり、指摘の正確さも維持したという。ただし評価対象のPRや計測条件の詳細を伴う独立検証ではないため、あらゆるコードベースで同じ改善率になるとは言えない。

提供対象はCopilot Pro+、Max、Business、Enterpriseで、VS Code、Visual Studio、Copilot CLI、coding agent、Copilot app、github.com、モバイル、JetBrains、Xcode、Eclipseなどに段階展開する。利用量課金では提供元の定価が適用される。企業管理者はモデルポリシーで利用可否を制御でき、選択肢に表示されない場合は段階展開や管理者設定も確認する必要がある。

**開発者目線:** モデル比較では、レビューコメントの数より、再現可能な不具合をどれだけ発見したかを重視したい。同じPR群を複数モデルにレビューさせ、真陽性率、誤検知、修正に必要な時間、トークン消費を比較すると選択基準が明確になる。高性能なモデルを常時使うのではなく、通常の修正と重大な変更で使い分ける運用も検討に値する。

## 👀 今日ならこの3つ

### 🥇 GitHub CLIのイベント待機

ポーリングからイベント駆動へ移行する具体的なコマンドが登場した。エージェントによるPRレビュー待ちやCI連携の設計に直接役立つ。

### 🥈 CopilotコードレビューのAdaptive深度

PRのリスクに応じてレビューの深さを変える仕組みは、AIレビューの費用と品質を両立する運用を考える材料になる。

### 🥉 CopilotのMCPコネクター拡充

DBやCIの実状態を参照しながら修正する作業が現実的になる一方、最小権限と操作確認の設計が重要になる。
