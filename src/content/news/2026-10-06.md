## 1. Beam — 501B、でも実際に動くのは23Bの巨大Open-weight Model

[Reflection公式：Introducing Beam](https://reflection.ai/blog/introducing-beam)

Reflection AI が10月5日、初のOpen-weight Model **Beam** を発表しました。

総Parameter数は**501B**ですが、Sparse Mixture-of-ExpertsなのでInference時にActiveになるのは**23B**。Coding・Reasoning・Agent用途を主眼にしています。Pretrainingは23.8T tokens、さらに10,500基のNVIDIA GB300を4週間使った大規模RLで**1億回以上のRollout**を生成したとしています。([Reflection](https://reflection.ai/blog/introducing-beam))

現在は最終Red Teaming / Evaluation中で、Weight公開はその後になります。

**開発者目線:** 面白いのは「501B」という数字より**23B active**です。

```text
501B total knowledge capacity
          ↓ routing
       23B active
          ↓
       inference
```

巨大Dense Modelを毎Token全部動かすのではなく、知識容量を大きくしながらInference Computeを抑える方向です。

Open-weight側でも、単に「小さいモデルを量子化してローカル実行」から、**大規模Sparse MoE + Agentic RL**へ競争軸が移っています。第三者Benchmarkが出たら改めて見たいモデルです。([Reflection](https://reflection.ai/blog/introducing-beam))

## 2. GitHub ReviewBench — 「AI Code Reviewは本当に使える？」を同じ物差しで測る

[GitHub公式：ReviewBench](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)

[GitHub](https://github.com/) が10月5日、AI Code Review Agent向けのOpen Benchmark **ReviewBench** をResearch Previewとして公開しました。

従来のCoding Benchmarkは「Issueを修正できるか」が中心ですが、ReviewBenchは、

**問題を見逃さないか**
**存在しない問題を大量に指摘しないか**
**Criticalな問題を優先できるか**

を測ります。

実際のGitHub PRを母集団にし、複数SourceからGround Truthを作り、Precision / RecallのTrade-offを評価できる設計です。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/))

**開発者目線:** かなり重要なBenchmarkです。

Code Review Agentで最悪なのは、

```text
100 comments generated!
↓
95個どうでもいい
↓
人間が全部読む
↓
むしろ遅くなる
```

こと。

つまりReviewでは**RecallだけでなくSignal-to-noise ratio**が重要です。

Copilot / Claude / Codexなどを「実装能力」だけでなく**Reviewerとして独立評価する**ための共通Datasetが出てきたのは良い流れです。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/))

## 3. Google PageBreak — AI Agentが500件超のXSSを発見、しかも「実際にExploitして確認」

[Google Security Blog：PageBreak](https://blog.google/security/agentic-hacks-real-proofs-inside-googles-pagebreak-project/)

Google のProduct Security Teamが開発したSecurity Agent **PageBreak** が、Google自身のWeb Applicationから**500件を超えるXSS**を発見しています。Sensitive Domainも含まれます。([blog.google](https://blog.google/security/agentic-hacks-real-proofs-inside-googles-pagebreak-project/))

ただし今日注目したいのは件数ではありません。

PageBreakはLLMが、

> 「このコード、XSSっぽい」

と言っただけでは報告しません。

Candidateを**AIではない専用Validator**へ渡し、実際にJavaScript Payloadを投入してBrowserで発火することを確認してからFindingにします。その結果、GoogleはFalse Positiveがほぼゼロになったとしています。([blog.google](https://blog.google/security/agentic-hacks-real-proofs-inside-googles-pagebreak-project/))

**開発者目線:** Agent設計として非常に良いです。

```text
LLM
 ↓
hypothesis
 ↓
deterministic validator
 ↓
real execution
 ↓
✓ confirmed
```

**「LLMに正解を判定させない」**のがポイント。

Coding Agentでも、

`Agent: 実装できました`

ではなく、

`compiler / tests / screenshot / benchmark / actual server`

のようなDeterministic Oracleで終了条件を判定する方が信頼できます。

先日紹介したNVIDIA SWE-Serveとも完全に同じ思想です。([blog.google](https://blog.google/security/agentic-hacks-real-proofs-inside-googles-pagebreak-project/))

## 4. Unity公式Plugin、Claude / Codexに続きGrok Buildへ

[Unity公式：Unity Plugin for Grok Build](https://web-prd.hexagon.unity.com/blog/unity-plugin-grok)

Unity が公式Agent Pluginを **Grok Build** にも提供しました。

これで公式対応は、

**Claude Code**
**Codex**
**Grok Build**

の3系統。

重要なのは単なるDocumentation Bundleではなく、Unityの各Feature Team自身が書いた**30以上のSkills**が入っていることです。UI Toolkit / uGUI、2D / Tilemap、URP / Shader Graph、Audio、Navigation、Physics、IAP、LevelPlay、Multiplayer、Web、Localizationなどをカバーします。([Unity](https://web-prd.hexagon.unity.com/blog/unity-plugin-grok))

さらに3 Agent分を**一つのRepositoryから維持**しているため、基本的に同じUnity Guidanceが配布されます。

**Unity開発者目線:** Unityの方針がかなり明確になりました。

> 「Unity独自AIを使わせる」のではなく、**Developerが選んだAgentへUnity自身がKnowledgeを届ける**。

Unity CLIにはMCP Modeもあるので、

```text
Agent
 ├ Skills → Unityの正しい使い方
 └ MCP    → Editorを実際に操作
```

という構成になります。([Unity](https://unity.com/features/ai))

個人的にはこの方向はかなり良いと思います。

## 5. Namespaceが€37M調達 — 「Coding Agent用Computer」がInfrastructure市場に

[Namespace公式](https://namespace.so/)

Developer Infrastructureの Namespace が10月5日、**€37M（約$42M）のSeries B**を発表しました。前Roundからわずか7か月で、過去12か月のRevenueは8倍になったとしています。([EU-Startups](https://www.eu-startups.com/2026/10/namespace-secures-e37-million-to-scale-coding-build-and-test-infrastructure-across-mac-windows-and-linux/))

Namespaceが提供するのはProduction Serverではなく、

**coding / build / test**

専用の高速Cloud Machine。Linuxだけでなく**MacとWindows**も扱います。

特にCoding Agent需要でMac Fleetを拡大しています。理由は単純で、AgentがiOS/macOS ApplicationをBuild/Testしたければ**本物のmacOS Environmentが必要**だからです。([EU-Startups](https://www.eu-startups.com/2026/10/namespace-secures-e37-million-to-scale-coding-build-and-test-infrastructure-across-mac-windows-and-linux/))

**開発者目線:** Coding AgentがCloudへ移ると、

> Model Compute

だけでなく、

> **Agentが仕事をするComputer**

が必要になります。

Web開発ならLinux VMで済みますが、

`Unity iOS build → macOS + Xcode`
`Windows native → Windows`
`Android → Linux/macOS`

とTargetごとにEnvironmentが必要。

**Agent Compute / Development Compute**がCloudの独立Categoryになり始めています。

## 6. Swiftに公式Google Cloud SDK — Backend言語として一段前へ

Google が、**Google Cloud API Client Libraries for Swift**を公開しました。

Swift 6.2+対応で、Cloud Storage、AI Service、IAMなど**100以上のGoogle Cloud Service**をSwiftから直接利用できます。Linux ContainerとしてCloud Run / GKE / Compute EngineへDeploy可能です。([Techzine Global](https://www.techzine.eu/news/devops/144739/google-brings-swift-to-the-backend-with-its-own-cloud-sdk/))

AuthenticationもApplication Default Credentials / Workload Identity Federationに対応。

なおGoogleは**iOS ApplicationへこのSDKを直接入れないよう明示的に警告**しています。管理CredentialをClientへ置くことになるためで、iOSから直接使う場合はFirebase等を推奨しています。([Techzine Global](https://www.techzine.eu/news/devops/144739/google-brings-swift-to-the-backend-with-its-own-cloud-sdk/))

**開発者目線:** Swiftが、

`Apple client language`

から、

**`client + CLI + backend + systems`**

へじわじわ広がっています。

Swift 6のStrict Concurrency、SwiftNIO、Linux対応が揃ったところへCloud SDKまで来たので、Apple中心のTeamがBackendまでSwiftで統一する選択肢がかなり現実的になっています。

## 8. Rook — Ghostty Engineを使った「AI Agentを群れで動かすTerminal」

もう一つ面白いOSS。

**Rook** はmacOS NativeのTerminalですが、普通のTerminal Emulatorではなく**複数Coding Agentの管理**を最初から設計に入れています。

Rendering / VT ParsingにはGhostty の`libghostty`を使用。Claude CodeやCodexが動いているSessionを自動認識し、

**active / blocked / completed**

をSidebarから確認できます。([GitHub](https://github.com/jokius/rook))

さらに`rookctl`というControl APIがあり、Agent自身がTerminal Sessionを作ったりSplitしたり、Overlayを開いたりNotificationを送れます。

**開発者目線:** 面白いのは、

> 人間がAgent用Terminalを操作する

だけでなく、

> **Agent自身がTerminal Workspaceを構成する**

こと。

tmux + Coding AgentをさらにAgent-nativeにした発想です。

普段Ghostty + tmuxを使う人には、かなり分かりやすい方向性だと思います。

## 9. 「Agent Fleet」は本当にInternet上を動き始めている

研究者が、中国のInfrastructureから大量に動いている**AI Agent Fleet**を追跡しています。

現在確認されているAgent群はTencent Infrastructure上で動作しているように見え、Alibabaの地図Service Amapへ多数のQueryを送っています。公園・動物園・病院などの複数Entranceへの経路探索などが確認されています。([TechCrunch](https://techcrunch.com/2026/10/05/researchers-are-tracking-a-chinese-ai-agent-fleet/))

研究者は「Swarm」という言葉は避けています。Agent同士が通信・協調しているEvidenceはなく、**同種Taskを大量のAgentが並列実行しているFleet**だからです。([TechCrunch](https://techcrunch.com/2026/10/05/researchers-are-tracking-a-chinese-ai-agent-fleet/))

今のところ悪意ある活動というよりAPI Ruleを迂回している程度とされています。

**開発者目線:** Bot TrafficとAgent Trafficの境界が曖昧になります。

従来：

`crawler → deterministic requests`

今後：

```text
goal
 ↓
thousands of agents
 ↓
each discovers URLs/APIs
 ↓
adaptive traffic
```

Server側でもRate LimitをIPだけで考えるのではなく、**Agent Identity / Intent / Credential / Behavior**を含めたTraffic Controlが必要になりそうです。
