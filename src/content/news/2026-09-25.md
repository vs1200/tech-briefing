## 1. Google Cloud — 既存REST APIを「ほぼそのままMCP Server」に

[Google公式：Turn your REST APIs into MCP tools](https://developers.googleblog.com/turn-your-rest-apis-into-mcp-tools-with-google-cloud-api-gateway/)

[Google Cloud](https://cloud.google.com/) API Gatewayが、9月24日に**Native MCP Server機能**をPublic Preview公開しました。

既存のOpenAPI 3.x定義へAnnotationを足すだけで、

```text
Agent
   ↓ MCP JSON-RPC
API Gateway
   ↓
Existing REST API
```

という変換をGateway自身が行います。別途MCP Serverを書く必要がありません。しかも既存のJWT / API Key認証、Quota、Loggingをそのまま共有します。([Google Developers Blog](https://developers.googleblog.com/turn-your-rest-apis-into-mcp-tools-with-google-cloud-api-gateway/))

**開発者目線:** かなり重要です。

これまでMCP対応というと、

`REST API → MCP wrapperを自作`

でしたが、今後は**API GatewayがProtocol Adapterになる**方が自然です。

特に既存Backendを大量に持つ会社では、「Agent対応」のコストを大きく下げられそうです。

## 2. Meta Horizon Create — Promptだけで2D/3Dゲームを丸ごと生成

[Meta公式：Horizon Create / Horizon Studio](https://developers.meta.com/resources/videos/a-new-way-to-create-on-meta-horizon/)

[Meta](https://www.meta.com/) がMeta Connectで **Horizon Create** と **Horizon Studio** を発表しました。

Createはスマホ、StudioはBrowser上で動き、自然言語から2D / 3D Gameを生成。StudioではArt、Difficulty、Progression、Multiplayerなどをさらに細かく編集できます。([Meta for Developers](https://developers.meta.com/resources/videos/a-new-way-to-create-on-meta-horizon/))

そして技術以上に面白いのがDistribution。

生成したゲームは**Facebook / Instagram Feed内で直接Play可能**になる予定です。([AI Chat Daily](https://www.aichatdaily.com/ai-tools/meta-launches-horizon-create-studio-build-ai-games))

**ゲーム開発目線:** Roblox的UGCとAI生成を一気につないだ形です。

重要なのは「AIでGameを作れる」より、

> **Prompt → Game → Publish → Recommendation → Play**

までをMetaが一つのPlatformに閉じたこと。

本当に面白いゲームを作れるかは別問題ですが、Game Creationの裾野にはかなり影響しそうです。

## 4. Anthropic、950個のClaude Agentで未知の酵素システムを発見

[Anthropic公式：Claude discovers a novel enzyme system](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system)

Anthropic が新設したLife Sciences Labの最初の成果を公開しました。

約**950のClaude Agent**が21時間動作し、20万以上のReverse Transcriptase候補を探索。最終的に、CRISPRのArrayに似たDNA Repeatを伴う未知の酵素System **ART（array-associated reverse transcriptases）** を発見しました。([Anthropic](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system))

消費したTokenは約**2.1億**。ただし重要な注意点として、ARTの機能はまだ不明で、物理的なWet Lab実験は人間が行っています。([Anthropic](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system))

**開発者目線:** 発見そのもの以上にWorkflowが興味深いです。

```text
Human
  ↓ broad goal
950 agents
  ↓ huge search space
3,500 candidates
  ↓
20 candidates
  ↓
Human wet-lab validation
```

Agent Fleetを**巨大な探索空間を絞り込む並列Search Engine**として使っています。

「1 Agentをもっと賢くする」とは全く違うScaling方法です。

## 5. GitHub Security Lab — Fuzzingをほぼ丸ごとAgent化

[GitHub公式：AI-powered fuzzing with Taskflow Agent](https://github.blog/security/application-security/ai-powered-fuzzing-with-the-github-security-lab-taskflow-agent/)

[GitHub](https://github.com/) Security Labが9月24日、**Fuzzing Taskflow**を公開しました。

C/C++ Repositoryを一つ渡すとAgentが、

**Entry Point探索 → Build System解析 → Harness生成 → AFL++実行 → Coverage解析 → Harness改善 → Crash Triage → Vulnerability Report**

まで自律実行します。([The GitHub Blog](https://github.blog/security/application-security/ai-powered-fuzzing-with-the-github-security-lab-taskflow-agent/))

起動も、

`./scripts/fuzzing/run_fuzzing.sh owner/repo`

程度です。

**開発者目線:** Agentと非常に相性の良いTaskです。

Fuzzingは従来、

> Harnessを書いたら終わり

ではなく、Coverageを見てHarnessを改善し続ける人間が必要でした。

そこを**Feedback LoopごとAgent化**したのがポイントです。

Coding Agentの用途として、Feature実装よりこういう反復的Engineering Taskの方が本質的に面白いと思います。

## 6. GitHub Copilot Canvas — 「そもそもChat UIが間違っているのでは？」

[GitHub公式：When chat is the wrong UI](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/)

GitHubが9月24日に紹介した **Canvas** がかなり面白いです。

Copilot App内でAgentに、

> SQLite Browserを作って
> Winget Package Managerを作って
> このWorkflow専用Dashboardを作って

と頼むと、**小さなFull-stack Applicationをその場で生成**します。

CanvasはAgentと双方向通信でき、Local Code Executionも可能です。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/))

GitHubの主張も面白く、

> 毎回LLMへ「SQLiteを検索して」と頼むより、一度UIを作らせて以後は普通に操作した方がTokenも安い。

という考えです。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/))

**開発者目線:** これはかなり同意できる方向です。

2023〜2025：

`Everything → Chat`

2026：

**`Agentに目的専用UIを生成させる`**

UI Generationが十分安くなれば、Softwareを「汎用品」として作る必要すら一部なくなる可能性があります。

## 9. Agent向けAPI設計で「Tool Description」が急に重要になる

Google CloudのMCP Gateway記事には、小さいけれどかなり重要な指摘があります。

MCP Toolへ変換するOpenAPI OperationにはDescriptionが必要で、Googleは、

> **何を返すかだけではなく「いつ・なぜこのToolを使うべきか」を書け**

と推奨しています。([Google Developers Blog](https://developers.googleblog.com/turn-your-rest-apis-into-mcp-tools-with-google-cloud-api-gateway/))

理由は単純で、LLMがどのToolを選ぶかの主要Signalになるからです。

例えば、

`Returns order status`

より、

`Use when the user asks where an order is or when it will arrive`

の方がAgentには有用。

**開発者目線:** API DocumentationのAudienceが変わり始めています。

従来：

**人間が読むAPI Docs**

これから：

**人間 + LLM Routerが読むAPI Metadata**

OpenAPIの`description`が単なるDocumentationではなく、**Agent Routing Logicの一部**になっています。

## 10. 今日の小ネタ：Agentに全部やらせるほどTokenを無駄遣いする

最後はGitHub Canvasの記事から、地味ですが面白いDeveloper UXの話。

GitHubは、

> Agentに毎回`stage and commit`させる必要ある？

とかなり直接的に問題提起しています。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/))

例えば同じDatabaseを何度も操作するなら、

```text
毎回：
Human → LLM → tool → DB
```

ではなく、

```text
最初だけ：
Human → LLM → UI生成

以降：
Human → deterministic UI → DB
```

の方が安く、速く、結果も予測可能です。

**開発者目線:** 2026年のAI Toolは「何でもAgent化」へ進んでいますが、その次には逆に、

> **LLMを使わなくてよい部分からLLMを抜く**

Optimizationが来そうです。

これはAgent Architectureでも同じで、Routing / Validation / UI / Data Transformationを全部Frontier Modelへ投げる必要はありません。
