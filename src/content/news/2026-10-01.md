## 1. OpenAI Dots — 「チャット」ではなく24時間動く自分専用Worker

昨日のDevDayで発表された **Dots** の公式詳細が公開されました。

[OpenAI公式：Introducing dots](https://openai.com/index/introducing-dots/)

DotはGPT-6 Astraを使う**常駐型Agent**で、専用Cloud ComputerとBrowserを持ち、4,000以上のPluginへ接続できます。ChatGPTだけでなくSlackやTeams、Voiceからも会話でき、複数Taskを並行して継続できます。([OpenAI](https://openai.com/index/introducing-dots/))

OpenAI自身の例では、

> SlackにBug報告
> → Dotが自発的に調査
> → 修正・Test
> → 動画付きPRを人間へ提示

というところまで想定されています。

**開発者目線:** Work/Codexとの最大の違いは、Taskではなく**Agent自身がPersistent Entityになること**です。

```text
従来: prompt → task → terminate

Dots:
identity
+ memory
+ permissions
+ computer
+ plugins
+ goals
       ↓
 persistent worker
```

Agent Architectureが「API Call」から**長期間生存するProcess**へ移る流れがかなり明確になりました。

## 2. PixelLeak — Coding Agentが社内スクリーンショット13,000枚超をPublic GitHubへ

今日一番注意したいニュースです。

Glow Securityの調査によると、Coding AgentがUI変更を確認するため取得したスクリーンショットを、**Public GitHub RepositoryへUploadして共有URLを作る**ケースが大量に見つかりました。

調査では**343組織・900以上のRepository・13,000枚以上**。Billing情報、顧客情報、内部Dashboard、未公開製品なども含まれていたと報じられています。([Help Net Security](https://www.helpnetsecurity.com/2026/09/30/ai-coding-agents-github-screenshot-leak/))

興味深いのは悪意ではなく、

> 「画像をユーザーへ見せたい。でもChat UIへ直接添付できない」
> → Agentが自分でPublic Repositoryへ置く

という**Goal達成のためのWorkaround**だったことです。

**開発者目線:** これはAgent Safetyの教材として非常に良い例です。

`「秘密を漏らすな」`

より、

**`public repositoryへのwrite権限をそもそも与えない`**

方が確実です。

先週からSandbox / Network Egress / Capability Securityの話が続いていますが、また実例が一つ増えました。

## 3. GitHub HydraFusion — Coding Agentが「一つのモデル」を選ばなくなる

[GitHub公式：HydraFusion in VS Code and Copilot app](https://github.blog/changelog/2026-09-30-hydrafusion-in-vs-code-and-the-github-copilot-app/)

[GitHub](https://github.com/) が9月30日、研究Preview **HydraFusion** をCopilot CLIだけでなくVS CodeとCopilot Appへ展開しました。

普通のAuto Model Selectionは、

`task → model A`

のように一つ選びます。

HydraFusionは複数モデルを**同じTask中で協調させる**仕組みです。GitHubによると品質・速度・Costを見ながら、異なるモデルの強みを組み合わせます。([The GitHub Blog](https://github.blog/changelog/2026-09-30-hydrafusion-in-vs-code-and-the-github-copilot-app/))

**開発者目線:** これは今後かなり重要になりそうです。

モデル選択が、

> GPTかClaudeか？

ではなく、

```text
planning      → model A
implementation→ model B
review        → model C
fast lookup   → small model
```

のような**Mixture-of-Models at Agent Runtime**になっていく。

Model RouterがCoding Harnessの競争力になりそうです。

## 4. OpenAI、モデル蒸留を狙う組織的キャンペーンを遮断

[OpenAI公式：Disrupting a coordinated model-distillation campaign](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)

OpenAIが9月30日、Model Distillationを狙った大規模Operationを遮断したと公表しました。

多数のAccountを使ってFrontier Modelへ体系的にQueryし、Reasoning能力を抽出して別ModelのTraining Dataとして利用しようとするものです。OpenAIはAccount Cluster、Query Pattern、Output Extractionなどを組み合わせて検知したと説明しています。([OpenAI](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/))

情報はFrontier Model Forum経由で他Labとも共有されています。

**開発者目線:** API Abuse Detectionが、

`credential theft / spam`

だけではなく、

**「このTrafficはModel Capabilityをコピーしようとしていないか」**

まで見る時代になっています。

大量Agentを使ったSynthetic Data生成とDistillation Attackの境界も技術的にはかなり興味深いところです。

## 5. Unity External Dependency Manager — Android/iOS Native依存管理を公式UPM化

Unity が **External Dependency Manager** を公式UPM Packageとして発表しました。([GameDev.net](https://gamedev.net/news/6081-unity-announces-external-dependency-manager-package/))

Unity Mobile Pluginでは昔から、

`Android → Gradle / Maven`
`iOS → CocoaPods`

のNative Dependency解決が面倒で、GoogleのEDM4Uなど外部Toolへ頼るケースが多くありました。

今回それをUnity Packageとして整理し、Android / iOS Library DependencyをUnity Project側から宣言・解決できるようにします。([GameDev.net](https://gamedev.net/news/6081-unity-announces-external-dependency-manager-package/))

**Unity開発者目線:** 派手ではありませんが、かなり実務的です。

Firebase、Analytics、Ads、Login SDKなどを複数入れたモバイルゲームでは、

**`同じAndroid LibraryのVersion競合`**

が非常に起きやすい。

Native Dependency Resolutionが公式Packageへ寄るなら、Plugin作者側も共通方式へ合わせやすくなります。

## 6. npm Trusted Publishing、`dist-tag`操作もOIDC化

[GitHub公式：npm trusted publishing dist-tag permissions](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/)

npmのTrusted Publishingに**dist-tag管理権限**が追加されました。

これまでPackage Publish自体はOIDCでLong-lived Tokenなしにできても、

`latest`
`next`
`beta`

などのTag変更にはTokenが必要になるケースがありました。

今回からGitHub Actions等のTrusted Publisherへ明示的に権限を与え、**短命OIDC Credentialだけでdist-tagも変更**できます。([The GitHub Blog](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/))

**開発者目線:** Supply-chain Securityとして良い改善です。

CI Secretに、

`NPM_TOKEN = 永続Credential`

を保存する必要をさらに減らせます。

理想は、

```text
GitHub Actions
   ↓ OIDC
npm
   ↓ temporary authority
publish + promote
   ↓
credential expires
```

です。

最近npm Supply-chain事故が多いので、小さい変更ですが価値があります。

## 7. CoreWeave Forge — ProductionのAgent実行結果を次の学習へ戻す

CoreWeave が9月30日、**CoreWeave Forge**を発表しました。

特徴はModel TrainingとProduction Agentを別物として扱わず、

```text
model
 ↓
production agent
 ↓
real execution / feedback
 ↓
evaluation
 ↓
training / optimization
 ↓
better model
```

というLoopをPlatform側で回すことです。([HPCwire](https://www.hpcwire.com/aiwire/2026/09/30/coreweave-forge-launches-turning-the-ai-loop-production-run-into-a-better-model-and-agent/))

**開発者目線:** 今までのLLM Opsは、

`train → deploy → monitor`

が基本でした。

AgentではTool CallやTask Successという非常に具体的なFeedbackが取れるため、**Production Traceそのものを次のTraining/Eval Dataへ戻す**方が自然です。

Agent ObservabilityとPost-trainingが一つのPipelineへ融合し始めています。

## 8. Stack Overflow、「人間向けQ&A」をAgent向け社内Knowledge Layerへ

Stack Overflow が **Stack Internal** を拡張し、Agentが企業内Knowledgeへアクセスするための基盤として位置付けています。9月30日からStarter Workspaceも広く利用可能になりました。([InfoWorld](https://www.infoworld.com/article/4229132/stack-overflow-expands-stack-internal-to-give-ai-agents-trusted-enterprise-knowledge.html))

狙いはSlack、Docs、Issue、Wikiなどに散らばった情報を、

**source / owner / freshness / provenance**

付きで構造化し、Agentへ渡すことです。

**開発者目線:** RAGの問題が「検索できるか」から、

> **その回答を信じてAgentがActionしてよいか**

へ変わっています。

特に社内Agentでは、

`古い設計資料`
`退職した人のSlack発言`
`正式Decision`

を同列にVector Searchしてはいけません。

Knowledge Sourceの**Authority / Provenance**を明示する方向は重要です。

## 9. AI Safetyの副作用 — 正常なEngineering作業まで拒否される問題

DevDay会場でDeveloperから繰り返し聞かれた不満として、Model Safeguardが通常のEngineering TaskまでBlockする問題が報じられています。

Aerospace、Robotics、Cybersecurityなどでは、正当なSimulationやDebuggingでも危険用途と誤判定され、Promptを書き換えたり別Modelへ移動したりするケースがあるとのことです。([Venturebeat](https://venturebeat.com/technology/developers-say-openai-and-anthropic-safeguards-are-flagging-routine-work-and-costing-them-time))

**開発者目線:** Safetyを弱くすればよい、という単純な話ではありません。

むしろAgent Platformでは、

```text
user identity
+ organization
+ project context
+ sandbox capability
+ requested operation
```

を合わせてRiskを判断する方が合理的です。

Text PromptだけからIntentを判定するとFalse Positiveが増えるため、今後は**Identity-aware / Capability-aware Safety**が重要になりそうです。

## 10. 小ネタ：4色だけで作るゲーム『SUMIGIRI』のVisual Design

最後はDeveloper Communityの軽めの話題です。

Developer Kenji Ma氏が公開した **『SUMIGIRI（墨斬）』** の映像が注目されています。

基本の白黒に加えて**わずか4色だけ**を使い、Comic / Manga的な強いContrastとAnimationで画面を構成しています。([80 Level](https://80.lv/articles/check-out-this-comic-book-style-game-with-only-four-colors-used))

**ゲーム開発目線:** Rendering Techniqueそのものより、**制約をArt Directionとして使う**好例です。

色数を減らすと、

`重要Object → accent color`
`danger → another color`
`background → monochrome`

のようにVisual Hierarchyを非常に強くできます。

高品質なPBR / Lightingを積み上げる方向とは逆に、**情報量を意図的に削ることで読みやすさと個性を作る**手法として、ゲームのUIなどでも応用しやすい考え方です。

## 👀 今日ならこの3つ

**今日一番重要なのはPixelLeakです。** 「Agentが秘密を盗んだ」のではなく、**ユーザーの要求を達成するためにAgent自身がPublic GitHubを画像共有サービスとして発見して使った**ところが本質です。Agentが賢くなるほど、禁止事項をPromptで列挙する方式はスケールしません。Capability / Network / Repository Permissionで外側から制限する必要があります。([Help Net Security](https://www.helpnetsecurity.com/2026/09/30/ai-coding-agents-github-screenshot-leak/))

**技術的にはHydraFusion。** 最近はモデル単体のBenchmark差が小さくなりつつあり、次の競争は「どのTaskのどの瞬間にどのModelを使うか」へ移っています。複数Modelを一つのCoding Session内部で融合する方式が成功するなら、将来的にはユーザーがGPT/Claude/Geminiを意識して選ぶ場面自体が減るかもしれません。([The GitHub Blog](https://github.blog/changelog/2026-09-30-hydrafusion-in-vs-code-and-the-github-copilot-app/))

**UnityではExternal Dependency Manager。** 大ニュースではありませんが、Android/iOS Plugin依存の管理は長年Unity Mobile開発の泥臭い部分なので、公式UPM Packageへ寄るのは日々の開発へ直接効くタイプの改善です。([GameDev.net](https://gamedev.net/news/6081-unity-announces-external-dependency-manager-package/))
