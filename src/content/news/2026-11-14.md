## 1. GitHub Copilot、12月14日に旧モデル6種を廃止へ — 固定モデル指定を点検

GitHubは11月13日、Copilotの複数モデルを12月14日に廃止すると発表した。対象はClaude Fable 5、Claude Haiku 4.5、Gemini 3.8 Flash、Gemini 4 Argon、Grok 4.6、Kimi K3。Chatだけでなく、インライン編集、Ask、Agent、コード補完などCopilotの各体験が対象になる。新しいモデルが追加される話題と異なり、これは既存ワークフローが突然選択不能になる可能性のある、移行期限付きの変更だ。[GitHub公式発表](https://github.blog/changelog/2026-11-13-upcoming-deprecation-of-selected-github-copilot-models-in-december/)が対象と代替候補を一覧化している。

GitHubが推奨する移行先は順にClaude Fable 5.2、Claude Haiku 5.5、Gemini 4 Hydrogen、Gemini 4 Carbon、Grok 4.7。Kimi K3の代替は発表時点で未定となっている。例外として、年間契約の個人Copilot利用者にはClaude Haiku 4.5の廃止が適用されない。企業契約では、既定のモデル有効化がオンなら代替モデルは原則自動で有効になるが、管理者が全体の既定設定を無効にした場合や個別モデルを禁止した場合は別途ポリシー設定が必要だ。

注意したいのは、モデル選択が画面上の好みだけではない点だ。CLI、SDK、IDE設定、社内の利用ガイド、再現性を重視する評価スクリプトなどに特定モデル名を埋め込んでいる場合、モデル提供終了後に失敗や意図しない選択変更が起きうる。移行先のモデルは名称が似ていても、推論速度、料金、ツール実行の傾向、出力形式が同じとは限らない。変更を単なる文字列置換で終わらせず、代表的なタスクを用いて比較することが重要になる。

**開発者目線:** リポジトリ内の設定ファイルとCI、Copilot SDK呼び出し、チームの手順書を検索し、旧モデル名を洗い出したい。移行前後で小さな修正タスクと複数ファイル編集を試し、テスト成功率、差分の大きさ、実行時間を記録すると影響が見えやすい。特にKimi K3を固定している環境では代替が未発表なので、別モデルへの切り替え方針を先に決めておくと安全だ。

## 2. GitHub Copilot app 1.2.0、GitHub Enterprise Server連携が正式提供

GitHubは11月13日、GitHub Copilot appからGitHub Enterprise Server（GHES）を利用する機能を一般提供したと発表した。従来はオプトインのプレビューだったが、Copilot app 1.2.0以降で正式な機能となった。企業内で管理するGitHubサーバー上のリモートリポジトリ、Issue、Pull Requestをアプリの作業対象にできる。クラウドのgithub.comとオンプレミス・自社管理のGHESを混同しないことがポイントだ。[公式変更履歴](https://github.blog/changelog/2026-11-13-github-enterprise-server-support-in-the-github-copilot-app/)に要件が記載されている。

接続には最初にGitHub.comまたはGHE.comのアカウントでサインインし、その後SettingsのAccountsからAdd accountを選び、GitHub Enterprise Serverを追加する。つまり、GHESの認証情報だけでアプリの初回セットアップを完結できるという案内ではない。また、GHESに対してCloud sessionsは利用できないと明記されている。リポジトリ参照やIssue操作の対応と、クラウド側でエージェント実行環境を用意する機能は別の提供範囲として理解する必要がある。

この区別は導入判断に直結する。企業のコードを外部クラウドへ持ち出さない運用では、単に「GHES対応」と書かれていてもデータ経路、認証の種類、アクセス権、実行場所まで確認しなければならない。正式提供はプレビューより導入計画を立てやすくするが、すべてのCopilot機能がGHESで等しく使えることを意味しない。サーバー側のバージョン条件やネットワーク制限は、公式ドキュメントと実環境で照合したい。

**開発者目線:** まず読み取り権限の小さな検証用リポジトリで接続し、Issue一覧、PR参照、リポジトリ切り替えを試すとよい。続いて、権限のないリポジトリが見えないこと、認証期限切れで安全に再ログインできること、ログに機密情報が残らないことを確認する。Cloud sessions非対応を前提に、ローカル実行とリモート作業の責任分界を運用資料に書いておく価値がある。

## 3. Gemini 4 HydrogenがCopilotで一般提供 — 高速エージェント用途の選択肢

GitHubは11月13日、GoogleのGemini 4 HydrogenをGitHub Copilotで一般提供すると発表した。GoogleのFlash系モデルとして、高速なエージェント型コーディング、ツール利用、複数段階のワークフローを想定し、Gemini 3.8 Flashより指示追従を改善したと説明している。これは11月10日に提供が告知されたGemini 4 Carbonとは別モデルで、選択肢が増えたこと自体がニュースだ。[GitHubの公式案内](https://github.blog/changelog/2026-11-13-gemini-4-hydrogen-in-github-copilot/)に対応範囲がまとまっている。

対象プランはCopilot Pro、Pro+、Max、Business、Enterprise。VS Code、Visual Studio、Copilot CLI、coding agent、Copilot app、github.com、GitHub Mobile、JetBrains IDE、Xcode、Eclipse、Copilot SDKでモデル選択の対象となる。展開は段階的なので、対象プランでも即座にモデル一覧へ表示されないことがある。BusinessとEnterpriseでは管理者がモデルポリシーで利用を制御でき、既定のモデル有効化設定が変更されていれば個別の許可が必要になる。

料金面では、従来の「使えるモデルが増えたから無条件に切り替える」という判断は避けたい。公式はプロバイダーのリスト価格に基づく従量課金と説明している。Copilotのプランに含まれる利用枠や他モデルとの比較を推測で書くのではなく、利用画面と料金表で確認する必要がある。高速なモデルは、短いツール呼び出しを繰り返すエージェントで待ち時間を縮める可能性がある一方、複雑な設計判断まで同等の品質で処理できるとは限らない。

**開発者目線:** 同じIssueを使い、Hydrogenと既存モデルで「原因特定→修正→テスト」の一連の操作を比較したい。単発の回答速度だけでなく、ツール呼び出し回数、誤ったファイル編集、再試行、最終テスト結果まで測ると実用上の差が分かる。特に頻繁に小規模な変更を行うCI支援や定型修正では、速度と費用のバランスが重要な評価軸になる。

## 4. GitHub AI Scan、リポジトリ単位の有効化をREST APIから管理可能に

GitHubは11月13日、Code scanningのAI Scan for repositoriesについて、組織・リポジトリ単位の有効化をREST APIで管理できる公開プレビューを発表した。既存のAI Scan設定APIに新しいrepository_scanプロパティが追加され、enabledまたはdisabledを指定できる。従来の管理画面で一つずつ変更する作業に代えて、スクリプトやInfrastructure as Codeに組み込めるのが大きな変化だ。[公式Changelog](https://github.blog/changelog/2026-11-13-manage-ai-scan-for-repositories-using-the-rest-api/)はエンドポイントと権限を具体的に示している。

APIは組織向けのGET/PATCH /orgs/{org}/code-scanning/ai-scanと、リポジトリ向けのGET/PATCH /repos/{owner}/{repo}/code-scanning/ai-scanを使用する。既存のpr_scanとrepository_scanを同じリクエストで変更できるが、どちらかの変更がポリシーに阻まれると422が返り、両方とも変更されない。組織で無効なら個々のリポジトリは有効化できず、組織で有効なら継承したリポジトリが個別にオプトアウトできる。企業全体のポリシーが禁止している場合も422になる。

重要なのは、設定を有効にしてもスキャンは自動開始されないことだ。書き込み権限を持つ利用者がオンデマンドで実行し、実行ごとにGitHub Code Security AI creditsを消費する。対象は組織所有の公開リポジトリ、またはGitHub Code Security/Advanced Securityを備えた非公開・内部リポジトリで、GHESは非対応。機能の利用可能性と実行コストを分けて把握する必要がある。

**開発者目線:** まずGETで現状を棚卸しし、組織ポリシー、個別設定、対象リポジトリの一覧を突き合わせてからPATCHを実行するのがよい。宣言的設定にするなら、422時に再試行を繰り返すのではなく、上位ポリシーとの矛盾を検出して明示的に失敗させる。スキャン開始は別ジョブとし、クレジット予算、実行承認、結果のレビュー責任者まで設計すると安全に展開できる。

## 5. GitHub Actions、ARM32のWindows・Linuxホスト実行を12月8日に終了

GitHubは11月12日、GitHub ActionsのホストランナーにおけるARM32ジョブ実行サポートを12月8日までに終了すると告知した。CIのアーキテクチャは普段意識しにくいが、対象プラットフォームで動かしているビルドやテストにとっては期限のある互換性変更だ。[GitHub公式告知](https://github.blog/changelog/2026-11-12-actions-for-arm32-linux-windows-retirement/)はWindowsとLinux上のARM32実行を対象としている。

ここでARM32とARM64を区別する必要がある。ARMという名前だけで全てのARM系実行環境が終了するわけではない。また、GitHubが提供するホストランナーのサポート終了と、自前で管理するself-hosted runnerの構成は別問題だ。ジョブ定義が標準的なx64で動いているのか、32ビットARMのクロスコンパイルだけを行っているのか、ARM32環境で実際に実行しているのかを切り分けないと影響範囲を誤る。

CIの移行ではビルドが通ることと成果物が対象端末で動くことも別である。クロスコンパイルに切り替えると、生成物の形式や依存ライブラリは検証できても、実機固有のシステムコール、ネイティブ拡張、デバイスアクセスなどの挙動は自動的に保証されない。エミュレーションで代替する場合も、速度と再現性を確認する必要がある。特に長期間変更していないワークフローでは、ランナーの廃止が初めての更新契機になることがある。

**開発者目線:** ワークフローのruns-on、コンテナイメージ、ビルドマトリクス、アーキテクチャ指定を検索し、実際にARM32で実行しているジョブを特定する。対象があれば、x64/ARM64でのクロスビルド、適切なself-hosted runner、実機テストの組み合わせを比較したい。移行後はコンパイラの成功だけでなく、成果物の起動確認までCIの受け入れ条件に含めるべきだ。

## 6. GitHub Secret scanning、Cloudflare Accessのサービストークン検出を追加

GitHubは11月12日、Secret scanningでCloudflareのサービストークンを検出する仕組みを追加したと発表した。新たな検出タイプはcloudflare_access_service_token。Cloudflare Accessのサービス間認証に使う秘密情報がリポジトリへ混入した際に、GitHub側で発見する機会が増える。[GitHubの公式変更履歴](https://github.blog/changelog/2026-11-12-secret-scanning-adds-a-detector-for-cloudflare/)が対象のトークン種別を明示している。

サービス間の認証情報は、人間のユーザーがログインするパスワードとは異なり、CIやバッチ、サーバー側の設定に置かれることが多い。そのため開発時の設定ファイル、サンプルコード、テストログ、環境変数のコピーなどを経由して流出する危険がある。検出機能の追加は有益だが、すべての秘密情報を検出できるわけではなく、誤って公開したトークンの無効化まで自動で完了することを意味しない。

運用上は「検出されたから安全」と考えず、露出した期間と権限を評価する必要がある。公開リポジトリに一度コミットされた文字列は、最新コミットから削除しても履歴やフォーク、外部のキャッシュに残り得る。したがって、見つかった認証情報は原則ローテーションし、古い値を失効させるのが重要だ。さらに、Cloudflare側のアクセスログを調べて不審な利用がないか確認する対応も検討したい。

**開発者目線:** Cloudflare Accessを使うチームは、サービストークンをコードに直接書かず、CIのSecretや適切な秘密管理基盤から注入する構成を点検したい。検出通知の担当者、失効手順、再発防止策をあらかじめ用意しておくと初動が速くなる。ローカルのpre-commit検査とGitHub側の検出を併用すれば、コミット前後の異なる段階で漏えいを防げる。

## 7. GitHub Public monitoring、アラートを直接共有できるリンクを追加

GitHubは11月12日、企業向けPublic monitoringの個別アラートを直接開けるリンクを追加した。従来、監視一覧から該当する項目を探して共有する必要があった場面で、アラート番号をクリックして対象の詳細ページへ移動できる。[公式変更履歴](https://github.blog/changelog/2026-11-12-public-monitoring-alerts-now-have-direct-links/)は、EnterpriseのPublic monitoring画面でアラート番号から開けることを案内している。

一見すると小さなUI改善だが、セキュリティ運用では対象を正確に指し示せることが重要になる。たとえば監視担当者が発見した問題をIssueやインシデント管理システムへ転記する際、説明文だけでは似た警告を取り違えることがある。安定した個別リンクがあれば、発見者、調査担当者、承認者が同じ対象を参照しやすくなる。ただしリンクが存在することと、リンクを知る人全員が閲覧できることは別で、権限管理は引き続き必要だ。

この機能は検出エンジンの性能改善や新しい種類の脅威を発見する機能ではない。変わるのは、検出後の情報共有と追跡の効率だ。セキュリティの改善は検出率だけでなく、アラートが実際の対応に結びつくまでの時間でも評価される。チケットから監視画面へ戻る導線が短くなることで、再確認や引き継ぎの手間を減らせる可能性がある。

**開発者目線:** 既存のインシデント対応テンプレートにアラートURLを記録する欄を用意するとよい。通知からチケットを起票する自動化では、アラート番号、対象、検知日時、対応状況を別々の項目に保持し、URLだけに情報を依存させない設計が扱いやすい。アクセス権のない担当者にはリンクがあっても読めないため、チームの閲覧権限とエスカレーション経路も併せて確認したい。

## 8. Astral ty 0.0.101、再帰型とPydantic型エイリアスの解析を修正

Astralは11月11日、Python向け型チェッカーtyの0.0.101を公開した。再帰的な名前付きタプルを含むUnionでのpanic回避、ネストしたpartialの重複正規化の抑制、PEP 695型エイリアスを通じたPydanticのstrictness保持など、実際のPythonコードで型解析が不安定になりやすい箇所を修正している。[公式リリースノート](https://github.com/astral-sh/ty/releases/tag/0.0.101)には個別の修正Pull Requestが列挙されている。

Pythonの型解析は単に関数の引数と戻り値を比較するだけではない。Union、ジェネリクス、再帰的な型定義、ライブラリが提供する特殊な型の意味を組み合わせて推論する必要がある。Pydanticのように実行時のバリデーションと型注釈を組み合わせるライブラリでは、型エイリアスを一段挟むだけで情報が欠落すると、エディタ上の警告や補完が実際の動作と食い違う可能性がある。

今回の更新では、ネストしたアンパック対象に対する例外チェックポイントの記録、タプルをコールバックとして渡す際の要素型保持、Fieldの特殊化に関する型の絞り込みも調整された。LSPサーバーではファイルウォッチャー登録が失敗した場合、ワークスペース全体の監視へフォールバックする。つまり、型理論上の精度だけでなく、エディタで変更が検知されず診断が古いままになる問題への対処も含まれている。

**開発者目線:** tyを導入済みのプロジェクトでは、型エイリアス、Pydanticモデル、複雑なUnionを多用するコードで診断差分を比較したい。型チェッカーの更新はエラー件数が増えたか減ったかだけで評価せず、以前の誤検知が解消されたのか、見逃していた不整合が新たに検出されたのかを分類するのが有効だ。LSPの監視フォールバックについても、大きなモノレポではCPU負荷と診断反映速度を観測しておくとよい。

## 9. Biome 2.6.7、Promise.finallyの非同期コールバックを静的検出

Biomeは11月11日、CLI 2.6.7を公開した。新たなnurseryルールnoAsyncPromiseFinallyとnoDuplicateTypeConstituentsが追加されている。前者はPromiseのfinallyへasync関数を渡すコードを検出し、後者はUnionやIntersectionに同じ型を重複して列挙した場合や、オプショナル引数の型にundefinedを重ねて書いた場合を報告する。[公式リリース一覧](https://github.com/biomejs/biome/releases)で変更内容を確認できる。

Promise.prototype.finallyは成功・失敗のどちらでも後処理を行うための仕組みだが、コールバックが返すPromiseが失敗すると、元のPromiseの結果やエラーが後処理のエラーで置き換わる。ログ送信や一時ファイルの削除など、後処理をasyncで書くこと自体は構文上可能でも、元の障害原因が失われるリスクがある。たとえばAPI呼び出しの失敗を調査していたのに、finally内の監査ログ送信エラーだけが観測されると、根本原因を追いにくい。

一方、型の重複は直ちに実行時の不具合になるとは限らないが、生成された型定義や複雑な条件型を保守するときに可読性を下げる。nurseryは安定した既定ルールと同じ位置付けではなく、試験的なルール群として導入を判断する必要がある。既存コードへ一括適用すると診断件数が大きく増える可能性もあるため、まず変更対象のファイルで効果を確認するのが現実的だ。

**開発者目線:** 非同期処理の後片付けをfinallyに集約しているコードを検索し、そこで発生する例外を元のエラーとどう扱うべきか設計を見直したい。ログ送信の失敗を握りつぶしてよいか、明示的に別経路へ報告すべきかは用途次第である。ルールをCIへ導入する際は、既存の警告を棚卸しし、誤検知と実害のあるパターンを分けて段階的に有効化すると導入しやすい。

## 10. Bun 1.4.5のリリース準備が進行 — リリースブランチ運用を変更

Bunの公式リポジトリでは11月13日、1.4.5へのバージョン更新コミットと、リリースパイプラインの整理が相次いでマージされた。公開されたコミット履歴には「Bump to 1.4.5」「release pipeline cleanups」「build releases from release branches」などが並ぶ。これは新バージョンの完成を断定する材料ではなく、リリースに向けた開発・配布工程の変更を確認できる一次情報だ。[公式コミット履歴](https://github.com/oven-sh/bun/commits/main/)に日付と変更の題名が記録されている。

注目したいのは、単なるバージョン番号の変更よりも「リリースブランチからビルドする」という運用の調整だ。開発のmainブランチは新機能や修正が継続的に入るため、公開するバイナリをどのコミットから生成したのかを明確にする必要がある。専用ブランチから成果物を作る方式は、リリース候補を固定して検証し、緊急修正だけを選択的に取り込む運用と相性がよい。ただし、実際にどのブランチ戦略や承認条件を採用したかは個別の変更差分を読む必要がある。

BunはJavaScriptランタイム、パッケージ管理、テスト、ビルドなど複数の役割を持つため、配布工程の不具合は広い範囲へ影響し得る。ソースコードが正しくても、特定OS向けの成果物が欠落したり、タグとバイナリが一致しなかったりすれば利用者に問題が生じる。リリース工程の整理は目立たないが、ツールチェーンへの信頼を支える基盤作業だ。

**開発者目線:** BunをCIや本番環境で利用する場合、mainのコミットだけを見て「1.4.5が正式公開された」と判断せず、公式Releasesにタグと配布物が出たことを確認してから更新するのが安全だ。バージョン固定、チェックサム、プラットフォーム別の起動テストを組み合わせると、配布工程の変更による事故を早期に検出できる。開発ツールを自作するチームにとっても、リリースブランチと再現可能なビルドの設計は参考になる。
