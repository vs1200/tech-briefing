今朝は **Claude Code Projectsの全面刷新**が頭ひとつ抜けています。ほかにも、GitHub ActionsのUbuntu 26移行、AgentをEdgeで動かすためのNVIDIAの実測、そして東京で昨日完走した「100時間AIゲーム開発」など、実装寄りの話が多めです。昨日まで扱ったUnity × Codex、GitSpawn、Google Home × MCPなどは繰り返していません。

## 1. Claude Code Projects刷新 — 1つの会話が複数Coding Agentを勝手に指揮

[Anthropic公式：Projects redesigned](https://claude.com/blog/projects-redesigned)

Anthropic が9月17日、Claude Codeの **Projects** を大きく作り直しました。

従来の「ファイルをまとめて置くProject」ではなく、Claude自身がCoordinatorになります。たとえば「checkoutのp75 latencyを下げて」とだけ頼むと、Claudeが作業を分解し、**複数のClaude Code Cloud Sessionを別Branchで並列起動 → 進捗監視 → 結果Review → 統合**まで行います。Shared MemoryとProject LibraryもThread間で共有されます。([Claude](https://claude.com/blog/projects-redesigned))

さらにLaptopを閉じてもCloud Threadは動き続け、スマホから途中で指示変更できます。現在は一部Pro / MaxユーザーからBeta展開中で、Local Tool対応も予定されています。([Claude](https://claude.com/blog/projects-redesigned))

**開発者目線:** これはかなり大きいです。ここ数週間紹介してきた、

`人間 → 複数Agentをtmux/worktreeで管理`

から、

`人間 → Coordinator Agent → 複数Coding Agent`

へ一段抽象化されました。

特に長時間作業では、Developer自身がAgent Session Managerになる必要がなくなっていく方向です。

## 2. NVIDIA、27B AgentをJetson 1台で実行 — Agent Benchmarkを6.4倍高速化

[NVIDIA技術解説](https://developer.nvidia.com/blog/tensorrt-edge-llm-completes-the-mlperf-edge-agentic-benchmark-6-4x-faster-on-jetson-agx-thor/)

NVIDIA が9月16日、TensorRT Edge-LLMを使った **MLPerf Edge Agentic** の結果を公開しました。

Qwen3.6-27BをJetson AGX Thor 1台で動かし、1,007 Agent Turnを**24分36秒**で完走。公開されているllama.cpp Referenceの2時間37分に対して6.4倍高速でした。52.33 tokens/sです。([NVIDIA Developer](https://developer.nvidia.com/blog/tensorrt-edge-llm-completes-the-mlperf-edge-agentic-benchmark-6-4x-faster-on-jetson-agx-thor/))

面白いのは高速化の中身で、NVFP4量子化、FP8 KV Cache、Multi-token Predictionに加え、**過去のAgent会話のKV CacheをTurn間で再利用**。Prompt Tokenのおよそ96%をHot Cacheから供給しています。([NVIDIA Developer](https://developer.nvidia.com/blog/tensorrt-edge-llm-completes-the-mlperf-edge-agentic-benchmark-6-4x-faster-on-jetson-agx-thor/))

**開発者目線:** ChatbotよりAgentでKV Cacheが重要になる理由がよく分かる実例です。

Agentは、

`prompt → tool → result → prompt → tool → result…`

と同じ長いHistoryを何度も読むので、**Modelそのものより「過去Contextを再計算しないRuntime」**がPerformanceへ大きく効きます。

## 3. GitHub Actions、Ubuntu 26.04がGA — `ubuntu-latest`も来月移行開始

[GitHub公式：Ubuntu 26 generally available](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration/)

[GitHub](https://github.com/) Actionsで **Ubuntu 26.04 Runner** が正式GAしました。x64だけでなくarm64にも対応しています。([The GitHub Blog](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration/))

そして重要なのが`ubuntu-latest`。

現在の24.04から26.04への切り替えが**10月19日〜11月19日**に段階的に行われます。([The GitHub Blog](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration/))

**開発者目線:** CIを使っているなら今のうちに、

`runs-on: ubuntu-26.04`

で一度Build / Testしておくのがおすすめです。

Preinstalled ToolやVersionが変わっているため、`ubuntu-latest`任せのWorkflowが突然壊れる可能性があります。移行したくなければ`ubuntu-24.04`へPinできます。

## 4. GitHub Actions、「誰が・何を契機にWorkflowを実行できるか」を強制

[GitHub公式：Workflow execution protections GA](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/)

同じく9月17日、GitHub Actionsの **Workflow Execution Protections** がGAしました。

ActorとEventをAllowlist化でき、さらに今回から**Workflow File単位**でPolicyを変えられます。([The GitHub Blog](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/))

例えば、

`ci.yml → contributorも実行OK`
`deploy.yml → release-teamのみ`

という設定が可能。

実際にRuleが何をBlockしたか確認するInsightsも追加されています。([The GitHub Blog](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/))

**開発者目線:** Coding AgentがPRやWorkflowまで作る現在、これはかなり良い境界です。

「AgentにdeployしないでとPromptする」より、**CI/CD側でdeploy Workflowを起動できるIdentityを制限する**方が圧倒的に堅牢です。

## 5. Claude Code 2.1.274 — MCPと長時間Session周辺を大量修正

Claude Code **2.1.274** が9月17日に公開されています。

今回は派手なFeatureより運用品質改善。Memoryが危険域に達すると警告を出すようになり、`CLAUDE_CODE_MCP_STARTUP_WAIT_MS`で非対話実行時のMCP接続待ち時間も制御可能になりました。OpenTelemetryにはModelの`effort`も記録されます。([Gradually AI](https://www.gradually.ai/en/changelogs/claude-code/))

さらに、壊れたTranscriptで`unexpected tool_use_id`を延々Retryする問題、5分以上のStreamable HTTP MCP CallがTimeoutする問題、Bash Permission判定などが修正されています。([Gradually AI](https://www.gradually.ai/en/changelogs/claude-code/))

**開発者目線:** 長時間Agentでは「モデルが賢い」より、**1回の異常でSession全体が死なないこと**の価値が大きいです。

Claude Codeを長時間走らせる用途なら、今回は更新価値が高いReleaseです。

## 9. LlamaIndexの面白い指摘：「抽出AIが嘘をつく原因はPromptではなくSchemaかも」

LlamaIndex 周辺で今週注目したい小さなEngineering Topicが、Document Extractionにおける**Schema設計**です。

例えば請求書抽出で、

```text
discount: required number
```

と定義しているのに、実際にはDiscountが存在しないDocumentもあるとします。

Modelから見ると「required」は**必ず値を出せというInstruction**でもあるため、存在しない値を推測して埋める圧力になります。([Gttome](https://gttome.github.io/Daily-AI-Brief/stories/2026-09-17/llamaindex-treats-extraction-schemas-as-semantic-contracts/))

**開発者目線:** Structured Outputを使うと型安全になった気がしますが、

**型が正しい ≠ 内容がGroundedしている**

という良い注意点です。

LLM向けSchemaではTypeだけでなく、Optional / Nullable / Cardinality自体がPromptの一部だと考えた方がよさそうです。

## 👀 今日ならこの3つ

今日は **Claude Code Projects** が圧倒的におすすめです。これまで複数Agentをworktreeやtmuxで管理するToolを何度も紹介してきましたが、Anthropic自身が「Goalを一つ渡せばCoordinatorがThreadを作る」という抽象化を製品へ入れました。特に**長時間Coding AgentをSupervisorとして管理する**使い方では大きな変化です。([Claude](https://claude.com/blog/projects-redesigned))

すぐ実務へ影響するのは **GitHub Actions Ubuntu 26.04**。`ubuntu-latest`の移行は10月19日からなので、CIがあるRepositoryは今のうちに26.04で一度通しておくと安全です。([The GitHub Blog](https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration/))

技術的に一番面白いのは **TensorRT Edge-LLM**。Agentでは同じ巨大Contextを何百回も読み直すため、96%近くをKV Cacheから再利用できたことが6.4倍という差につながっています。これはCloudでもLocal LLMでも、今後のAgent Runtime最適化を考えるうえでかなり重要な数字です。([NVIDIA Developer](https://developer.nvidia.com/blog/tensorrt-edge-llm-completes-the-mlperf-edge-agentic-benchmark-6-4x-faster-on-jetson-agx-thor/))
