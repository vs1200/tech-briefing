## 1. Codex CLI 0.171.0、GPT-6.2をモデル一覧に追加しSolを既定選択へ

**公開日：2026年11月20日｜公式一次情報**

OpenAIはCodex CLI 0.171.0を公開し、モデルカタログにGPT-6.2 SolとGPT-6.2 Astraを追加した。カタログで最初に選ばれるモデルはSolとなる。モデルが存在することと、契約・組織設定・ロールアウト状況に応じて実際に利用できることは別なので、更新した全利用者が無条件に両方へアクセスできると解釈すべきではない。直前の0.170.0では音声接続やMCP認証の修正が中心だったが、今回はモデル選択という普段の作業に直結する変更だ。

CLIのモデルカタログは単なる表示一覧ではない。ターミナルで新規セッションを開始したときの既定選択、保存済み設定、明示指定したモデル名、利用できないモデルの扱いが組み合わさって、実際の推論経路を決める。エージェントが自動でコードを編集する運用では、既定値が変わるだけで生成される差分、必要な承認、処理時間などが変化し得る。公式リリースはモデル追加を説明するが、すべての開発タスクで一方が優れるという測定結果を示してはいない。

更新時にはCLI本体のバージョン、モデル一覧、設定ファイル、実際のセッションで表示されるモデルを別々に確認したい。長期運用するスクリプトは暗黙の既定値に依存せず、再現性が必要ならモデル名を明示する方が追跡しやすい。性能評価は同じリポジトリの同じコミットを使い、テスト結果と差分の品質を比較するのが妥当だ。

**開発者目線:** バグ修正、単体テスト生成、既存コードの調査といった性質の違うタスクを用意し、SolとAstraをそれぞれ複数回試したい。回答の印象だけでなく、正しく完了した割合、変更ファイル数、レビューでの手戻りを記録する。モデル更新を機に既定設定がどこで決まるかを可視化することも、チーム内の再現性向上につながる。

## 2. Codex CLI 0.171.0、TUIワークスペースを既定有効化

**公開日：2026年11月20日｜公式一次情報**

Codex CLI 0.171.0では、これまでオプトインだったターミナルUIのワークスペースが既定で有効になった。メインの会話と並べて、検索可能なドキュメントのプレビュー、画像プレビュー、サブエージェントの実行履歴を表示できる。単一の会話ログを上下に移動して状況を追う操作から、関連情報を横断的に参照する操作へ比重を移す更新だ。

コーディングエージェントの出力には、最終回答だけでなくファイル検索結果、画像、別エージェントへの委譲結果が含まれる。長い履歴にこれらが混ざると、どの根拠で変更を判断したのかを再確認しにくい。プレビューを分離すると、作業中のコードと根拠資料を行き来しやすい。一方で、画面上に並んだ情報が同じ時点のファイルを指すとは限らないため、古いプレビューを根拠に判断しない注意は残る。

同じリリースには非Vim入力欄のundo・redoショートカット設定も含まれる。大きな貼り付けや添付情報の復元に対応する点は、プロンプト作成のやり直しコストを減らす。画面表示や入力体験の変更は、モデルの性能改善とは独立した生産性要因として評価できる。

**開発者目線:** 複数ファイルを調べるリファクタリングで、サブエージェントの調査内容とメインの編集方針を同時に照合できるか試したい。狭いターミナル、リモート接続、長い日本語パスでも表示が崩れないか確認する。入力欄のundoは、誤って消した長文指示や添付を復元できるか実際に検証してから常用すると安心だ。

## 3. Codex CLI 0.171.0、既存App Serverへの非対話リモート接続を追加

**公開日：2026年11月20日｜公式一次情報**

Codex CLI 0.171.0は`codex exec --remote <ADDR>`を追加し、既存のApp Server上で非対話セッションを開始または再開できるようにした。これまでの`codex exec`をローカルの単発実行として使う運用に対し、接続先サーバーが保持するセッションへCLIからアクセスする経路が増える。公式ノートでは機能追加が確認できるが、あらゆるネットワーク構成で利用できることや認証設定の不要性までは意味しない。

リモート実行で重要なのは、どのマシンでコマンドが走り、どのファイルシステムが編集されるかを明確にすることだ。ローカルの端末で指示していても、実行先の環境変数、依存パッケージ、認証情報、作業ディレクトリは接続先に依存する。接続を再開できる便利さと、誤ったセッションを操作するリスクは表裏一体である。

同版にはTUIからリモート制御と端末ペアリングコードを管理する`/rc`、`/remote`も追加された。対話画面からの制御とスクリプトからの非対話実行を別々に扱える設計だが、権限やログの管理は運用側の責務として残る。特に長時間の作業では、接続断がタスク中断と同義かどうかを確認したい。

**開発者目線:** まず破壊的操作を含まないテスト用リポジトリで、開始・切断・再接続・中断の各ケースを試す。作業ディレクトリ、Gitのブランチ、実行主体、成果物の保存先をログに残し、ローカルとリモートを取り違えない表示を整える。CI連携に使う場合は、資格情報の有効範囲と接続先の固定も必須だ。

[公式出典](https://github.com/openai/codex/releases/tag/rust-v0.171.0)

## 4. Claude Code 2.1.330、Enterprise Admin Console管理組織へのログインに対応

**公開日：2026年11月21日（日本時間）｜公式一次情報**

AnthropicはUTC11月20日にClaude Code 2.1.330を公開した。新たにEnterprise Admin Consoleで管理される組織へのサインインに対応し、`claude auth login`の後に組織の設定を適用して、指定されたクラウドプロバイダーまたはゲートウェイを使用する。個人の認証と企業の実行ポリシーを別々に手作業で整える場面を減らすための変更と考えられる。

企業でコーディングエージェントを導入すると、モデルの選択だけでなく、どの経路でAPIへ接続するか、ログや監査の設定をどう配るかが問題になる。ログイン後に管理対象組織の設定が反映される仕組みは、端末ごとの設定差を抑える助けになる。ただし、管理コンソールの設定が適用されたからといって、すべてのネットワーク制約や機密情報の取り扱いが自動的に解決するわけではない。

この版では自前で運用するランナーに`--start-dir`と`SELF_HOSTED_RUNNER_START_DIR`も追加された。リポジトリの一部フォルダーを作業開始位置にでき、設定とフックは従来どおり読み込む。大きなモノレポで作業対象を限定したい場合に役立つが、開始位置の指定をアクセス制御と混同してはいけない。

**開発者目線:** 組織ログイン前後で実際の接続先、モデル選択、管理設定の優先順位を確認し、意図したゲートウェイを経由しているかテストしたい。ランナーの開始ディレクトリは対象プロジェクトを絞る手段として活用しつつ、読み込まれる設定とフックを別途監査する。認証の成功だけで運用準備完了としないことが重要だ。

[公式出典](https://github.com/anthropics/claude-code/releases/tag/v2.1.330)

## 5. Claude Code 2.1.330、Easelによるチャート表示とランナー計測を追加

**公開日：2026年11月21日（日本時間）｜公式一次情報**

Claude Code 2.1.330には、チャートを描く組み込みmodであるEaselが追加された。依頼された場合やMCPのメトリクス結果を扱う場合にグラフを描画する。対象はmacOSとLinuxのPro、Max、および提供されるTeam・Enterprise環境で、Windowsを含む全環境への一般提供と読み替えてはいけない。自動グラフは`/config`から無効にできる。

開発作業ではログやメトリクスの数値を文章で読むだけだと、急激な変化や複数系列の差に気づきにくい。グラフを会話の流れに組み込めれば、テスト実行時間、失敗件数、処理量などの変化を短時間で確認できる。ただし、可視化の品質は元データの粒度や単位に依存する。軸の切り取りや欠損値の扱いによって印象が変わるため、重要な判断には生データとの照合が欠かせない。

自前ランナーには、作業指示からランナー登録までの秒数、作業指示から最初のセッション引き渡しまでの秒数を測るメトリクスも追加された。処理時間全体だけでは分からなかった起動待ちと実作業の区別がしやすくなる。エージェントの体感速度はモデルの生成速度だけでなく、ランナーを確保するまでの時間にも左右される。

**開発者目線:** チャートを利用する際は、元データの単位と集計期間を併記し、同じ入力から同じグラフが再現できるか確認したい。ランナー計測では待ち時間、準備時間、実行時間を分けて記録すると、モデル変更よりインフラ調整が効く箇所を発見できる。自動可視化は意思決定の補助として扱うのが適切だ。

[公式出典](https://github.com/anthropics/claude-code/releases/tag/v2.1.330)

## 6. Claude Code 2.1.330、worktree誤削除と設定競合などを修正

**公開日：2026年11月21日（日本時間）｜公式一次情報**

Claude Code 2.1.330は多数の安定性修正を含む。特に重要なのが、別のClaude Codeセッションで使用中のworktreeを`ExitWorktree`や終了ダイアログが削除してしまう問題の修正だ。Git worktreeは一つのリポジトリから複数の作業ディレクトリを持てる機能で、並列エージェントが別ブランチを扱うときに使われる。作業中の領域が誤って消えると、未コミット変更を失う危険がある。

同版では複数プロセスが同時にユーザー設定を保存した際の更新消失、長い会話を圧縮した直後の停止、WebFetchの長時間停止や空結果も修正された。これらは新しいモデル能力ではなく、複数セッションを継続利用したときの状態整合性に関わる。エージェントの運用が長時間・並列になるほど、正常終了だけを試すテストでは見つからない種類の問題だ。

さらに多数のMCPツールがAPIで受け付けられない入力スキーマを持つ場合のエラーや、セッションファイルが肥大化する問題にも対処している。ツールの定義はモデルが呼び出し方法を理解するために必要だが、定義の数や複雑さが増えるほど検証と復旧の重要性が高まる。修正が入ったからといって既存の不正なスキーマを放置してよいわけではない。

**開発者目線:** 複数worktreeを並行運用するなら、終了操作の前後でディレクトリと未コミット差分が保たれるか確認する。設定の同時更新や長時間セッションの復元も回帰テストに加えたい。重要な変更は小さくコミットし、エージェント側の状態保存だけを唯一の復旧手段にしない運用が堅実だ。

[公式出典](https://github.com/anthropics/claude-code/releases/tag/v2.1.330)

## 7. GitHubのSecurity Advisory権限が正式提供、管理者権限なしで脆弱性対応

**公開日：2026年11月20日｜公式一次情報**

GitHubは11月20日、リポジトリのSecurity Advisoryを操作する権限を一般提供した。組織のオーナーはカスタムリポジトリロールを通じて、非公開の脆弱性報告を含むセキュリティアドバイザリの作業を担当者へ委譲できる。従来は必要以上に広い管理者権限を与えなければ作業を進めにくい場面があったが、専用の権限によって役割を分けやすくなる。

脆弱性の報告を受けた直後は、再現確認、影響バージョンの調査、修正案の作成、公開時期の調整など、複数の担当者が関わる。ここで全員にリポジトリ管理権限を与えると、セキュリティ対応に不要な設定変更まで可能になってしまう。権限を細分化することは最小権限の原則に沿うが、アドバイザリの閲覧・編集権限がどこまで及ぶかは実際のロール設定で確認する必要がある。

正式提供はプレビュー段階から運用上の位置づけが変わったことを意味する。ただし、組織のロール管理や既存の管理者権限を自動的に見直す機能ではない。すでに広い権限を持つ担当者がいる場合、新しい権限を追加するだけでは最小権限化にならない。権限の棚卸しと組み合わせて初めて効果が出る。

**開発者目線:** セキュリティ担当と通常の開発担当の操作範囲を表にし、非公開報告の閲覧、修正PRの作成、公開操作を分離できるか試したい。テスト用リポジトリで実際の操作可否を検証し、権限不足時の連絡先と承認フローも定める。事故時に急いで管理者権限を配布する運用から脱却する機会になる。

[公式出典](https://github.blog/changelog/month/11-2026/)

## 8. GitHub Enterprise Server 3.23、リリース候補を公開

**公開日：2026年11月20日｜公式一次情報**

GitHubは11月20日、GitHub Enterprise Server 3.23のリリース候補版を案内した。GHESは企業が自社管理環境でGitHubの機能を運用する製品で、クラウド版のGitHub.comとは更新時期や利用できる機能が異なる。今回の発表は3.23の正式提供ではなく、リリース候補の段階である点を押さえたい。

企業内でGHESを更新する際には、開発者の画面上の新機能だけでなく、認証、バックアップ、外部連携、Actionsランナー、API利用ツールへの影響が重要になる。特にCIや社内Botは、画面から見えないAPIや権限の差分に依存していることがある。リリース候補を検証できる期間は、正式更新後の障害を減らすための準備時間と考えられる。

GitHubの告知ではGitHub Projectsなどプラットフォーム各所の機能追加が紹介されている。具体的な機能の利用条件や移行手順は、告知の概要だけで決めず3.23の公式リリースノートと管理者向け文書で確認したい。候補版の挙動がそのまま最終版と一致する保証もない。新機能の採用判断と本番環境のアップグレード判断は分けるべきだ。

**開発者目線:** 検証環境で主要なリポジトリ操作、PR作成、Webhook、Actions、社内認証を一通り試し、現在のバージョンとの差分を記録する。移行時にはロールバック手順、バックアップの復元時間、停止可能な時間帯も確認する。新機能の魅力よりも、既存の開発フローが継続できることを最初の合格条件にしたい。

## 9. setup-uv 10.4.0、チェックサム必須化でCIの供給網検証を強化

**公開日：2026年11月20日｜公式一次情報**

AstralはGitHub Actionsでuvをセットアップする`astral-sh/setup-uv`のv10.4.0を11月20日に公開した。新しい入力`require-checksums`を有効にすると、取得対象のuvリリースについて既知のチェックサムがない場合にActionを失敗させる。既定値はfalseであり、更新しただけで全ワークフローが厳格化されるわけではない。

たとえば`version: latest`を使うと、Action側がチェックサム情報を同梱するより先に新しいuvが公開されることがある。この場合、`require-checksums`を有効にしたジョブは安全側に倒れて失敗する。利用者は`checksum`入力で期待値を指定することもできる。`latest-known`を使う場合にも追加の防御層となる。新しいバージョンへすぐ追従する便利さと、取得物の整合性を強く検証する運用にはトレードオフがある。

同版は`version`入力でPEP 440の部分的なバージョン指定を解決する処理や、WindowsランナーでキャッシュされたPythonディレクトリのジャンクション修復も改善した。Pythonの実行環境がCIで再現できない問題は、アプリのテスト失敗と混同されやすい。セットアップAction自身の更新履歴も、依存ライブラリと同じように管理する必要がある。

**開発者目線:** 重要なリリースパイプラインではuvのバージョンを固定し、`require-checksums: true`を検討したい。更新直後にチェックサム未登録で停止した場合は、検証を無効化して通すのではなく、信頼できる出典から値を確認する。Windowsを含むマトリクスCIではキャッシュ有無の両方で動作を試すと問題を早期に発見できる。

[公式出典](https://github.com/astral-sh/setup-uv/releases/tag/v10.4.0)

## 10. Cloudflare Spectrum、管理画面を刷新し専用IPアプリの設定に対応

**公開日：2026年11月19日｜公式一次情報**

Cloudflareは11月19日、TCPやUDPアプリケーションを保護するSpectrumのダッシュボードを刷新した。アプリケーション一覧には種類、エッジポート、オリジン、エッジIPの種類に加え、直近1分の接続数や流入・流出トラフィックが表示される。検索と列ごとの並べ替えにも対応し、運用対象が多い環境で状態を比較しやすくなった。

作成・編集操作はモーダル画面から独立したページへ移り、アプリケーション設定、オリジン設定、高度なオプションに分かれた。さらに専用の静的IPやBYOIPを使うアプリケーションを画面から作成・編集できるようになった。サブドメイン欄を空にするとゾーンのルートに配置できる。従来API操作が必要だった構成の一部をGUIで扱えるようにした点が実務的だ。

注意したいのは、新規TCP・UDPアプリケーションではIP Access Rulesが既定で無効になることだ。これはAPIの既定値と一致させた変更で、既存のアプリケーション設定は変更されない。画面の刷新だけだと思って新規作成すると、アクセス制御の前提を取り違える可能性がある。作成時の既定値と、既存環境の実際の設定は区別して確認する必要がある。

**開発者目線:** 新規アプリケーションの作成手順を更新し、IP制限が必要なサービスでは作成後の設定をチェックリストに加えたい。既存アプリについては刷新前後でエッジIP、オリジン、アクセス制御が変わっていないか確認する。管理画面で見える直近の通信量は障害の手がかりになるが、長期的な傾向分析には別途ログと監視指標を残す。
