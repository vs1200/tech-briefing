今朝はかなり強い日です。特に **Claude Sonnet 5.5、NVIDIAのAgent Safety Platform、OpenCodeの「Webページを見るだけでRCE」脆弱性**が重要です。ゲーム開発ではUnityの実践的なマルチプラットフォーム事例を拾いました。昨日まで扱ったOpenAIのAgent事故、AG-UI、Julia 1、Google AXなどはなるべく重複させていません。

## 1. Claude Sonnet 5.5 — Opus 5.5を一部Coding Benchmarkで上回る

Anthropic が9月28日、**Claude Sonnet 5.5**をリリースしました。価格はSonnet 5と同じ **$2/M input、$10/M output**ですが、出力は30%以上高速化し、同じ仕事をより少ないToken / Tool Callで完了するため、AnthropicはTask単位では最大約30%安くなるとしています。([TechCrunch](https://techcrunch.com/2026/09/28/anthropic-releases-sonnet-5-5-which-it-calls-a-significantly-cheaper-faster-work-partner/))

面白いのはCoding性能。Anthropic公称のTerminal-Bench 4.0では**Sonnet 5.5が70.6%、先週出た上位Opus 5.5が66.4%**。もちろん単一Benchmarkなので「Sonnetの方が賢い」とまでは言えませんが、Coding Agentではかなり競争力があります。([Decrypt](https://decrypt.co/379482/anthropic-claude-sonnet-5-5-release))

[Anthropic](https://www.anthropic.com/)

**開発者目線:** 今回は「性能/価格」のバランスがかなり良さそうです。日常的なClaude Codeなら、Opusを常用するより **Sonnet 5.5をDefault → 本当に難しいTaskだけOpus** という使い分けがさらに合理的になりました。

## 2. Claude Sonnet 5.5、GitHub Copilotでも即日GA

[GitHub公式：Claude Sonnet 5.5 in Copilot](https://github.blog/changelog/2026-09-28-claude-sonnet-5-5-in-github-copilot/)

[GitHub](https://github.com/) も9月28日、Sonnet 5.5をCopilotへ**General Availability**で追加しました。

Copilot Free / Pro / Pro+ / Business / Enterpriseで利用でき、GitHubは「well-scoped everyday coding tasks」向けモデルとして位置付けています。([The GitHub Blog](https://github.blog/changelog/2026-09-28-claude-sonnet-5-5-in-github-copilot/))

**開発者目線:** 1番と合わせて重要なのは、モデルが出てからIDEへ届くまでの時間がほぼゼロになったことです。

`model release → Claude Code / API / Copilot`

がほぼ同時。

## 3. NVIDIA Open Agent Safety Platform — Agentを「モデルの外側」で止める

[NVIDIA公式発表](https://nvidianews.nvidia.com/news/open-agent-safety-platform)

NVIDIA が9月28日、**Open Agent Safety Platform**を発表しました。

中心はOpen Sourceの **OpenShell**。AgentがアクセスできるData / Tool / API / Networkなどを、Agent自身では変更できないRuntime Boundaryで制限します。CPU上で動作し、NVIDIA以外にArm / Intelへの拡張も想定されています。([NVIDIA Newsroom](https://nvidianews.nvidia.com/news/open-agent-safety-platform))

さらに **Sentry** という別系統のWatchdogをBlueField-4 DPU上へ置きます。

```text
        Agent
          ↓
      OpenShell
          ↓
 OS / tools / network
          ↑
   Sentry on DPU
   （別Trust Domain）
```

AgentがBoundaryを突破しようとした場合、Sentryが**数msで隔離・停止**します。([NVIDIA Newsroom](https://nvidianews.nvidia.com/news/open-agent-safety-platform))

**開発者目線:** 昨日まで紹介してきたAgent Sandbox事故への非常にタイムリーな回答です。

重要なのは「安全Modelを作る」ではなく、**Modelが間違える前提でOS / Hardware側からAuthorityを制限する**こと。Agent SecurityがContainer Securityにかなり近づいてきました。

## 4. AnthropicもNVIDIAと「Agent Loopと実行Sandboxを分離」

NVIDIAの発表には、Anthropicとの共同設計も含まれています。

**Claude Managed Agents**ではAgent Loopを動かすServerと、Agentが実際に作業するSandboxを分離。そのSandboxへOpenShell / BlueFieldによる追加Policy Enforcementを組み合わせます。([NVIDIA Newsroom](https://nvidianews.nvidia.com/news/open-agent-safety-platform))

つまり、

```text
Claude / Agent loop
        │
        │ request
        ▼
   policy boundary
        │
        ▼
   execution sandbox
        │
 filesystem / shell / network
```

という構成です。

**開発者目線:** Coding Agentを自作するときにも参考になります。

`LLM process == shellを持つprocess`

にせず、**Reasoning PlaneとExecution Planeを別Trust Domainへ分離する**。KubernetesのControl Plane / Workerに少し似ています。

今後Agent Runtimeの標準Architectureになっても不思議ではありません。

## 5. OpenCode — 悪意あるWebページを開くだけでローカルAgent経由RCE

今日一番「自分の環境を確認したい」Securityニュースです。

Open-source Coding Agent OpenCode の**1.14.30〜1.18.21**に、Web Interface起動中なら悪意あるWebページを訪問するだけで、Developer PC上で任意Commandを実行され得る脆弱性が見つかりました。修正版は**1.18.22以降**です。([Cyber Security News](https://cybersecuritynews.com/opencode-ai-coding-agent-flaw/))

仕組みが面白く、

`malicious webpage`
→ `browserからlocalhost:4096へPOST`
→ `/global/upgrade`
→ `attacker-controlled npm tarball`
→ `preinstall script`
→ **RCE**

となります。

通常CORSが防ぎそうですが、攻撃側はHTML Form + `text/plain`を使いPreflightを回避。OpenCode側がContent-Typeを確認せずBodyをJSON Parseしていたことも組み合わさっています。([Cyber Security News](https://cybersecuritynews.com/opencode-ai-coding-agent-flaw/))

**開発者目線:** `localhostだから安全`は成立しません。

Coding AgentはShell Authorityを持つため、Local Web UIがそのまま**Remote Code Execution Gateway**になり得ます。OpenCodeを使っているならVersion確認価値があります。

## 6. Carbonato — Botnetが「AI Agentそのもの」を侵入後の道具に

新しい**Carbonato Botnet**は、認証なしでInternetへ露出しているDocker Daemonを侵害し、その中へ**Hermes AI Agent**をInstallしてTelegram経由で操作します。([The Hacker News](https://thehackernews.com/2026/09/carbonato-botnet-compromises-docker.html))

従来のBotnetなら固定Shell ScriptやCommand Setを配布しますが、今回はAgentへ目的を与えて、状況に応じたCommandを生成・実行させます。

**開発者目線:** Malware側にもAgent Harnessが入り始めています。

攻撃者が、

`100種類のenvironment用scriptを書く`

代わりに、

`Agentにenvironmentを観察させ、その場でcommandを生成`

できる。

防御側でも「既知Command PatternだけBlockする」手法が効きにくくなる可能性があります。

なお入口自体は古典的なので、**Docker APIを無認証で外部公開しない**という基本対策は変わりません。([The Hacker News](https://thehackernews.com/2026/09/carbonato-botnet-compromises-docker.html))

## 7. Unity：PC / Mobile / Switch 2を「1 Project・1 Branch」で維持

Unity が、Lunch Money Games / Funday Gamesの『Scritchy Scratchy』をPCからMobile / Nintendo Switch 2へ展開した事例を公開しました。([GameDev.net](https://gamedev.net/news/6052-scaling-scritchy-scratchy-across-platforms/))

特徴はPlatformごとにProject / Branchを分けず、**一つのUnity Projectから全Targetを維持した**こと。

特に難しかったのはPerformanceよりInput / UIで、Mouseでの「削る感触」をTouchやControllerへどう移すか、Aspect Ratio差でUIをどう自然に保つかだったとしています。([GameDev.net](https://gamedev.net/news/6052-scaling-scritchy-scratchy-across-platforms/))

**Unity開発者目線:** マルチPlatform案件ではかなり現実的な話です。

Platform別Forkは最初は楽でも、

`bug fix × platforms`

になって長期Costが増えます。

できるだけ**共通Core + Platform Adapter / Conditional部分だけ分離**する設計の良い事例です。

## 8. GitHub Actions、Self-hosted Runnerの強制更新を延期

[GitHub公式：Self-hosted runner enforcement変更](https://github.blog/changelog/2026-09-28-self-hosted-runner-version-enforcement-date-has-moved/)

GitHubは9月28日、GitHub Enterprise CloudにおけるSelf-hosted Actions Runnerの**Minimum Version Enforcement開始日を変更**しました。([The GitHub Blog](https://github.blog/changelog/2026-09-28-self-hosted-runner-version-enforcement-date-has-moved/))

最近Node 20廃止などRunner周辺の更新が続いているため、古い固定Imageや社内Runner Fleetを運用しているTeamへの移行猶予になります。

**開発者目線:** Hosted Runnerしか使っていない場合はほぼ無関係ですが、Game Build Machineのような**特殊EnvironmentをSelf-hosted RunnerにしているTeam**では重要です。

Unity Build環境はUnity Version / Android SDK / Xcodeなどを固定しがちなので、Runner自体だけ古く残るケースに注意です。

## 9. 「Vibe CodingはLoopが高い」— Spec-firstが再評価

Amazon KiroのDarko Mesaros氏が、Agent CodingのCostについて面白い説明をしています。

問題は1回の生成Costではなく、

`generate → test → error → inspect → regenerate → test ...`

という**Autonomous Loopが積み重なること**。曖昧な要求ほどAgentが探索を繰り返すためToken / Tool Callが膨らみます。([The Times of India](https://timesofindia.indiatimes.com/technology/tech-news/vibe-coding-got-expensive-because-the-loops-add-up-and-amazons-darko-mesaros-says-kiros-spec-first-approach-cuts-them-short/articleshow/134546240.cms))

KiroがSpec-firstを強く推す理由もここにあります。

**開発者目線:** 最近のSonnet 5.5の「少ないTool Callで同じ仕事を終える」と同じ話です。

Agent性能を、

`完成したか？`

だけでなく、

**`completion / tool calls / tokens / wall-clock time`**

で見る方が実用的。

最初にAcceptance Criteriaと変更範囲を明確化するだけで、Agent Costをかなり抑えられる可能性があります。

**まずClaude Sonnet 5.5。** Opus 5.5の半額で、一部Coding Benchmarkでは上回るところまで来ました。「一番高いModelをCoding Agentへ使う」が必ずしも最適ではなく、**TaskあたりCost / Tool Call数 / Latency**で選ぶ時代がかなり明確になっています。([Reuters](https://www.reuters.com/technology/anthropic-rolls-out-second-claude-55-model-it-builds-toward-ipo-2026-09-28/))

**Architectureとして最も面白いのはNVIDIA Open Agent Safety Platform。** OpenShellだけならSoftware Sandboxですが、さらにAgentから見えないBlueField DPU上へWatchdogを置く発想はかなり徹底しています。Modelに安全性を期待するのではなく、**Modelより権限の強いSecurity Layerを外側へ置く**という設計です。([NVIDIA Newsroom](https://nvidianews.nvidia.com/news/open-agent-safety-platform))

**実際に該当者が確認すべきなのはOpenCode。** `opencode serve` / `opencode web`を使っている場合、**1.18.22以降**か確認する価値があります。「localhostのHTTP Server + Browser + Package Manager + AgentのShell権限」が組み合わさると、個々には普通の機能でも危険なAttack Chainになるという好例です。([Cyber Security News](https://cybersecuritynews.com/opencode-ai-coding-agent-flaw/))
