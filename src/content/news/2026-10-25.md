## 1. Bun 1.4.4のBrotli脆弱性修正 — fetch経由の不正圧縮データに注意

**10月23日のSecurity Advisory｜JavaScript Runtime・圧縮処理**

[Bunの公式Security Advisory](https://github.com/oven-sh/bun/security/advisories/GHSA-663w-cv8g-jj2p)が、同梱するBrotli DecoderのOut-of-bounds Write（CVE-2026-111497）を公表しました。影響するBunは**1.0.21以上、1.4.4未満**で、修正済みVersionは**1.4.4**です。Bun 1.4.4自体は10月22日に公開され、Advisoryは翌23日付です。脆弱性はBun独自の圧縮Logicではなく、組み込まれているBrotli Library側に存在します。

BrotliはHTTP Responseの`Content-Encoding: br`などに使われる圧縮方式です。Bunの`fetch`は既定でBrotliを含む圧縮方式を受け付け、Responseを自動展開します。そのためアプリが悪意あるServerから取得したResponseを処理するだけで、問題のDecoderに細工されたDataが渡る可能性があります。`node:zlib`の`brotliDecompress`系API、`DecompressionStream`のBrotli Formatも影響経路です。単に「圧縮Fileを明示的に開かないから安全」とは判断できません。

Advisoryによると、Brotli本体はRemote Code Executionの可能性を示していますが、**Bunに対する攻撃成立や影響の程度をBun側が実証したわけではありません**。ここは「RCEが実際に再現した」と混同してはいけない点です。`bun build --compile`で生成したExecutableにはRuntimeが埋め込まれるため、Bun本体を更新しただけでは古いBinaryは直りません。**Bun 1.4.4で再Buildして再配布**する必要があります。

> [!WARNING]
> 古いBunを使い続ける場合、`fetch`ごとに`decompress: false`を設定する回避策はありますが、全APIをまとめて安全にするProcess-wideな回避策はありません。基本対応はVersion更新です。

**開発者目線:** Dependency Scannerで直接依存だけを見ていても、Runtimeへ静的に同梱されたLibraryの欠陥を見逃すことがあります。Buildに使ったRuntime Versionと**配布済みBinaryの生成履歴**を追えるようにし、ServerとClient双方のUpdate範囲を洗い出すのが実践的です。

## 2. GitHub Public Monitoringが漏洩Tokenの有効性確認とWebhook通知に対応

**10月23日｜Secret Scanning・Incident Response**

[GitHubの公式Changelog](https://github.blog/changelog/2026-10-23-public-monitoring-adds-triage-validity-api-and-webhooks/)で、Public MonitoringにAlert管理、継続的なToken有効性Check、REST APIとWebhookが追加されました。Public Monitoringは自社Repositoryの外にある**公開Repositoryで見つかったCredential**についても、所属Domainや組織との関連を判断して発見する仕組みです。開発者が自社のCodeを守っていても、外部のSampleやForkからCredentialが露出する問題に対応します。

今回の変更でAlertを`Dismissed`または`Fixed`として閉じ、必要に応じて再Openできます。AlertごとのActivity Timelineは判断履歴を残し、Repository、Committer、Secret Type、帰属の方法、状態で絞り込めます。また対応ProviderのTokenには**Active・Inactive・Unknown**というValidity情報が表示されます。単に「秘密らしい文字列がある」だけでなく、今も使えるTokenなのかを優先順位付けに使えます。ただし`Unknown`を無効と見なしてよいわけではありません。

Automation用には`GET /enterprises/{enterprise}/secret-scanning/public-monitoring-alerts`と、`secret_scanning_public_monitoring_alert`のEnterprise Webhookが用意されました。発見後にTicketを起票し、担当Teamを決め、Tokenを無効化し、影響範囲を調べるWorkflowを組み立てられます。ここで重要なのは、**AlertをCloseしてもTokenの失効や公開場所からの削除は実行されない**という明示的な仕様です。Alert状態の変更と実際の修復を別工程として管理する必要があります。

> [!WARNING]
> 2026年10月23日時点ではGitHub Enterprise Cloud向けの**Public Preview**です。Data Residency構成にも対応し、GitHub Advanced SecurityまたはGitHub Secret ProtectionのLicenseに含まれます。一般公開の無料機能とは区別してください。

**開発者目線:** Webhookを受けたらすぐにCredentialをRotationし、必要な証跡を残した上でAlertを閉じる運用が考えられます。Security Automationでは「検知」「危険度の判定」「Credential失効」「再発防止」を分け、失効の成功をAlertのDismissだけで代用しない設計が大切です。

## 3. Copilot Usage MetricsがOpenCode・Claude Code・Codex別の利用量を集計

**10月23日｜Coding Agent・利用分析**

[GitHubの公式発表](https://github.blog/changelog/2026-10-23-usage-metrics-api-adds-usage-from-tools-like-opencode/)で、Copilot Usage Metrics APIのResponseに`totals_by_client`が追加されました。従来はIDEのTelemetryに依存する集計では、IDE外からCopilotのModelを呼び出すToolの利用量を十分に捕捉できませんでした。今回の変更では、**ModelへのRequestをServer側で集計**することで、OpenCodeなどのClientも同じ指標で見られるようになります。

`client`には`opencode`、`claude_code`、`codex`、`zed`、`copilot_cli`、`vscode`、`jetbrains`などが入り、`request_count`、`session_count`、`token_usage`を返します。`totals_by_model`ではModel別にさらに分解され、Model選択がUser指定・自動選択・製品側選択のどれだったかも示されます。Enterprise、Organization、User単位の**1日版・28日版Report**で利用でき、28日版では日ごとの集計の中に同Fieldが含まれます。

注意したいのは**Request数とPrompt数が同じではない**ことです。ひとつのUser Promptが複数回のModel Callを生むAgentでは、Request Countが会話回数より大きくなります。また`client`は送信側Integration IDに基づくBest-effort分類であり、本人確認済みのClient Identityではありません。`totals_by_client`はAgent AppのJob実行数を数える別指標とも異なります。導入前後の比較では、分母を揃えないと誤った解釈になります。

この追加は既存Fieldを壊さないAdditive Changeで、該当利用がなければ空Arrayを返します。閲覧にはCopilot Usage Metrics Policyの有効化と、Enterprise Owner、Billing Manager、Organization Owner、または適切なCustom Roleが必要です。Reportを外部分析に取り込む場合は、未知のClient名や`other`を扱えるSchemaにするのが安全です。

**開発者目線:** IDE内の補完とTerminal上のAgentを同じ「Copilot利用者数」で評価するのは難しいものです。Client別・Model別・Token別に切ることで、**どのToolが実際にModel Trafficを発生させているか**を確認できます。ただし費用対効果はRequest数だけでなく、完了したTaskや品質と組み合わせて測るべきです。

## 4. Cloudflare Workers BuildsがpackageManagerによるnpm Version固定に対応

**10月23日｜Build再現性・Package Manager**

[Cloudflareの公式Changelog](https://developers.cloudflare.com/changelog/post/2026-10-23-workers-builds-pin-npm-version/)によると、Workers Buildsで`package.json`の`packageManager`を使って**npm Versionを明示的に選べる**ようになりました。Build環境が勝手に異なるPackage Manager Versionを選ぶと、Lockfileの形式が合わなかったり、Dependency解決結果が変わったりします。特に新しいnpmでLockfileを書き直した直後は、CI側が古いnpmを使うことが問題になりやすい場面です。

設定は`"packageManager": "npm@11.19.1"`のように、名前と**正確なVersion**を記載する方式です。Workers BuildsはDependencyをInstallする前に指定されたnpmをInstallします。同じFieldはYarn・pnpm・BunのVersion指定にも使われます。Cloudflareは`engines.npm`を見てnpmのVersionを選ぶわけではないと明示しています。`engines`は互換性の宣言に使われますが、今回のVersion選択とは役割が違います。

この仕組みはRuntimeを含めたBuildのすべてを完全固定するものではありません。Node.js Version、OS、Native Dependency、Environment Variableなどが異なれば結果は変わり得ます。またVersionをRangeで指定せず、`npm@11.19.1`のようなExact Versionにすることが公式の推奨です。`packageManager`を追加したら、Local・CI・Cloudflare Buildsの3環境でLockfileが書き換わらないかを確認すると安心です。

| 設定 | 主な役割 | Workers Buildsでの扱い |
| --- | --- | --- |
| `packageManager` | 利用するManagerとVersionを指定 | Build前に指定VersionをInstall |
| `engines.npm` | npmとの互換性を宣言 | npm Versionの選択には使わない |
| Lockfile | Dependency解決結果を固定 | Manager Versionとの互換性が重要 |

**開発者目線:** Cloud Buildが不安定なとき、DependencyのVersionだけでなく**Dependencyを解決するToolのVersion**も疑うべきです。RepositoryにToolchainを宣言できれば、開発者とCIの設定差を減らし、更新時に「何を変えたか」をReviewしやすくなります。

## 5. Ruff 0.17.2 — 自動修正のComment消失を防ぐ安全性改善

**10月22日Release｜Python Linter・Formatter**

[公式Release Notes](https://github.com/astral-sh/ruff/releases/tag/0.17.2)によると、Ruff **0.17.2**が公開されました。大規模な新機能よりも、**Lint Ruleの誤判定とAuto-fixの安全性**を改善するMaintenance Releaseです。Python Codeを自動整形するToolでは、Lint結果の精度だけでなく、Fixを適用した際に元のCodeの意味やCommentが保持されるかが重要になります。

今回の修正では、`PLR5501`、`PLW0120`、`UP035`などで**Commentを削除してしまう可能性があるFixをUnsafe扱い**へ変更しました。RuffのUnsafe Fixは、明示的に許可しない限り通常のSafe Fixと同じようには適用されません。Commentには処理意図、Lint抑制、外部仕様への参照などが書かれている場合があり、実行結果が変わらなくても消すことが望ましくない場面があります。

型変数のStar付きConstraintを扱う際にSyntax Errorを生成しないようにする修正、`*args`や`**kwargs`をDocstringに記載したときの`D417`誤判定修正、Starred Elementの`PLE0643`誤検出修正も含まれます。Preview機能では不要なRegular Expression Compileを検出するRuleが追加され、`PLR2004`にはMagic Value ComparisonのAllowlist設定が加わりました。Ruleの有効化状況によっては、Update後に警告数が変わる可能性があります。

Performance面では名前解決の中間Data削減、双方向Unicode Checkの事前Filter、Parsing時のExpression Copy削減が記載されています。ただしRelease Notesには**具体的なBenchmarkの倍率は示されていません**。高速化の幅を断定せず、実ProjectでLint時間を比較するのが適切です。

> [!NOTE]
> Preview Ruleは標準Ruleと同じ成熟度ではありません。CIで導入する際はRuleの有効化と自動FixのPolicyを分け、Update時の差分を確認してください。

**開発者目線:** AI Agentが自動Fixを大量に適用するWorkflowでは、**安全に書き換えられる範囲の線引き**が重要です。LinterのFix分類を信頼しつつ、Commentの消失や型注釈の変更はDiff Reviewで検出する、という二重の確認が役立ちます。

## 6. GitHubのEnterprise Managed User誤削除問題 — 監査履歴を復元

**10月23日公表｜Identity管理・障害分析**

[GitHub公式の障害説明](https://github.blog/changelog/2026-10-23-emu-deletions-fix/)で、2026年6月1〜13日に発生した**Enterprise Managed User（EMU）の誤削除**について、原因と復元対応が公開されました。SCIM経由でDeprovisionされた一部のAccountが、本来のSuspendとObfuscationではなく削除されていました。影響したのは複数Enterpriseにまたがる**約12,285 Account**で、うち76 Accountは削除時点でActiveだったと説明されています。

この障害は単にLoginできなくなる問題ではありません。Accountが削除されると、Issue・Pull Request・Audit Logに表示されるUserが**Ghost User**となり、過去の操作を追跡する際の参照関係が壊れます。監査を重視する組織では、Accountの無効化とHistoryの保存は別々の要件です。退職者や移籍者のAccountを利用不能にしても、過去のReviewや承認を誰が行ったかは保持する必要があります。

原因は6月1日に有効化した新しいDeprovision経路で、対象がEMUかどうかの判定が正しく行われなかったことでした。GitHubは6月13日に問題の経路を無効化し、10月には対象Recordを本来のSuspended・Obfuscated状態へ復元したと報告しています。Enterprise Audit Logで対象期間の`user.delete` Eventを確認すれば影響の有無を判断できますが、公式案内では**管理者側の追加操作は不要**です。

この事例はIdentity Lifecycleの設計に示唆があります。DeleteとSuspendは同じ「Accessを止める」操作に見えても、History、監査、再Provision可否が違います。APIで操作を自動化するときは、対象AccountのTypeによって期待される状態遷移が異なる可能性をTestする必要があります。

**開発者目線:** Account削除を伴うMigrationやSCIM連携では、**アクセス制御の成功だけでなく、過去Recordの参照整合性**も回帰テスト対象にすべきです。利用停止後にIssue・PR・Audit Trailが正しく残るかを検証する観点は、独自のUser管理基盤にも応用できます。

## 7. Cloudflare Radarのホーム画面刷新 — 通信障害を地図から探索

**10月23日｜Internet観測・Data Visualization**

[Cloudflare公式Changelog](https://developers.cloudflare.com/changelog/post/2026-10-23-radar-homepage-redesign/)で、世界のInternet TrafficやOutageを可視化する**Cloudflare RadarのHome画面刷新**が発表されました。Cloudflare Radarは通信量、Protocol、Security Threatなどの統計を扱う公開サービスです。今回の更新は観測Dataそのものの新規収集手法ではなく、**利用者がDataを発見し、地域や話題を掘り下げる入口の改善**が中心です。

新しいHomeにはInteractive Mapが設けられ、世界各地のTrafficとOutageを地図から探索できます。Curated InsightsはTab形式で主要な統計をまとめ、より詳細なPageへ誘導します。専門家以外の記者やPolicy担当者にも理解しやすくする一方で、技術者が必要とする詳細な分析は引き続き利用できる方針です。UIの実装にはCloudflare製品群でも使われる**Kumo Component**が採用されています。

Outageを調べる際、地図上の色の変化だけで「特定ServiceがDownした」と即断するのは危険です。通信量の減少には障害だけでなく、時刻・休日・地域的な利用習慣・計測経路の違いが影響します。RadarのDataは全Internetの完全な観測結果ではなく、Cloudflareの観測範囲と集計方法に依存します。UIが理解しやすくなるほど、**何を測った指標なのか**を確認する姿勢も重要になります。

| 入口 | 得られること | 読み解く際の注意 |
| --- | --- | --- |
| Interactive Map | 地域別Traffic・Outageの概観 | 色の変化だけで原因を断定しない |
| Curated Insights | 主要統計の素早い比較 | 集計期間と指標の定義を確認 |
| 詳細Page | Protocolや地域の深掘り | 他の観測情報と照合する |

**開発者目線:** Service障害を調査するとき、Application LogだけではISPや地域の問題を見落とします。Radarのような外部観測を**自社のMonitoringと突き合わせる**と、Client側Networkの問題なのかServer側の問題なのかを切り分ける助けになります。

## 8. Cloudflare One Client macOS Beta — MTU自動追従と接続診断を改善

**10月22日｜macOS・VPN・Zero Trust**

[Cloudflare公式Changelog](https://developers.cloudflare.com/changelog/post/2026-10-22-warp-macos-beta/)で、macOS向けCloudflare One Client **2026.9.1555.1 Beta**が公開されました。このBuildから**macOS 15.0以上が必須**となり、macOS 14では動作しません。利用中のDeviceを更新する場合、OSのSupport範囲を先に確認する必要があります。Betaなので安定運用端末へ無条件に適用するのではなく、検証用Deviceで試すのが適切です。

主な改善は、Global Acceleration利用時の**Endpoint自動選択**と、低いMTUを持つNetworkへの対応です。MTUは一度に送信できるPacketの最大Sizeで、Network経路の途中に小さいMTUがあると、大きなPacketが届かず通信が途切れる場合があります。今回のClientはPath MTU Discoveryで測定された**1147〜1199 Byte**の値を採用するようになり、以前は無視していた小さいMTUにも追従します。Mobile Hotspotなどで「接続済みなのに一部の通信が失敗する」問題の緩和につながります。

接続が劣化したときはUIにBannerを表示し、Zero Trust構成ではTunnel外のNetwork経路をTracerouteで記録する機能も追加されました。`warp-diag`には機密値を伏せたMDM File情報や測定済みQUIC Path MTUが含まれます。またMDM Fileが一時的に消えても即座にRegistrationを削除せず、一定時間以前のPolicyを保持する仕組みが入りました。これはDevice管理ToolがFileを一瞬置き換える場面での不要な切断を防ぐためです。

> [!WARNING]
> このReleaseは**Beta**です。MTU調整によってすべてのNetwork障害が解決するわけではなく、Tunnel外のDNS・Proxy・Certificateなど別の要因もあります。

**開発者目線:** Remote開発やCI接続で「VPNはConnectedなのにGit Cloneが失敗する」といった事象は、ApplicationのTimeout設定だけを変えても直らないことがあります。**MTU・DNS・Tunnel経路・接続診断Log**を切り分けて観測できることが重要です。

## 9. Copilot Impact Dashboardに業界比較 — Agent活用度を同規模企業と比較

**10月22日｜AI導入分析・Engineering Management**

[GitHub公式Changelog](https://github.blog/changelog/2026-10-22-industry-comparisons-in-the-copilot-impact-dashboard)で、Copilot Impact Dashboardに**Industry Comparison**が追加されました。企業が自社のAI Agent利用状況を、同じ規模・業種の参加企業による集計指標と比較できる機能です。**参加はOpt-inで既定では無効**。単に「Copilotを何人使ったか」ではなく、Agent-firstやMulti-agentの利用割合、Agentを使う人と使わない人のPull Request Merge Rateの差を確認できます。

比較Groupは従業員規模の区分と10業種から選べます。参加企業が十分に集まれば、過去28日のPeer Medianや上位10%と比較できます。ただし人数が足りない場合は業種を広げたGroupへ切り替わったり、順位が表示されなかったりします。自社で比較対象となるNon-agentic Userが存在しない場合も、Merge Rateの差を算出できません。つまり**Dashboardの空欄は必ずしも利用率が低いことを意味しません**。

データは日次更新で、Opt-outすると比較表示がすぐ停止し、次回更新から自社Dataは集計に含まれなくなります。集計済みBenchmarkに企業識別情報は含まれず、30日後に削除されると説明されています。Data Residency構成では同一Region内だけで比較されます。またこのIndustry Comparisonは**Dashboard専用**で、Usage Metrics APIやNDJSON Exportには含まれません。

ここで気をつけたいのは、PR Merge Rateが高いことと開発品質が高いことは同義ではない点です。TeamのTask構成、Repository規模、Review方針、Release頻度で数字は変わります。業界比較は「導入状況の相場を知る」参考にはなっても、因果関係の証明にはなりません。

**開発者目線:** Agent導入の判断では利用回数より、**Lead Time・Review品質・障害率・開発者の負担**を合わせて測ることが大切です。外部Benchmarkを目標値として機械的に採用せず、自社内の時系列変化を読む補助線として使うのがよさそうです。

## 10. GitHub PRレビュー改善 — 空白差分の表示設定を保存可能に

**10月22日｜Code Review・Developer Experience**

[GitHub公式Changelog](https://github.blog/changelog/2026-10-22-pull-requests-saved-whitespace-preferences-and-improved-split-view/)で、Pull Requestの`Files changed`画面に二つの改善が入りました。一つは**Whitespace変更の表示設定を保存**できること、もう一つは**追加・削除FileをSplit Viewの横幅いっぱいに表示**できることです。派手な機能ではありませんが、毎日大量のDiffを読む開発者にとっては作業の摩擦を減らす変更です。

Whitespace設定は`Settings → Whitespace changes`から、`Always show`、`Always hide`、`Hide for this diff only`を選べます。保存した設定は自分のPreferenceとして別のPull Requestにも適用されます。Whitespaceを隠しているときは`Hide whitespace` Filterが表示され、必要なときだけ一時的に解除できます。File CountやDiff Statisticsも表示中のDiffを反映するため、数字が変わったときはFilterの状態を確認する必要があります。

Split Viewは通常、左に旧Code、右に新Codeを並べます。しかし新規Fileには旧Codeがなく、削除Fileには新Codeがありません。今回の更新では、そのようなFileが両Column分の幅を使うようになり、長いLineの折り返しが減ります。既存Fileの差分比較というSplit Viewの利点を維持しつつ、**新規Fileの読みやすさをUnified Viewに近づける**改善です。

Whitespaceの非表示は便利ですが、Indentationに意味があるPythonやYAML、Formatting Toolの設定変更などでは注意が必要です。大量のFormatting差分を隠してLogic変更だけを追う場面と、WhitespaceそのものがBug原因になる場面を使い分ける必要があります。Reviewの視認性を上げる機能であり、Whitespace変更がRepositoryから消えるわけではありません。

**開発者目線:** Code ReviewではDiffの見せ方が判断の質に影響します。**通常はWhitespaceを隠してNoiseを減らし、Formatter更新やPythonのIndentation変更では表示する**といった運用を明確にすると、見落としを減らしながらReview速度を上げられます。

## 👀 今日ならこの3つ

### 🥇 BunのBrotli脆弱性

Runtimeに同梱されたLibraryの欠陥が、HTTPの自動展開を通じて問題になる事例です。特に`bun build --compile`で生成したBinaryの**再Build・再配布**が必要な点は見落としやすく、早めに確認したい話題です。

### 🥈 GitHub Public MonitoringのValidity Check

漏洩Credentialの発見からWebhookによる通知、失効作業までをWorkflowとしてつなげられます。**Alertを閉じるだけではTokenは失効しない**という責務の分離が重要です。

### 🥉 CopilotのClient別Usage Metrics

OpenCodeやClaude Code、CodexなどのTool別にModel Trafficを分析できます。Request数とPrompt数の違いを意識すれば、Agent運用の実態を数字で捉える入口になります。
