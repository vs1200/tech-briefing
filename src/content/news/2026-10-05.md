## 1. Uber MCP Gateway — MCP Serverが増えすぎた後に必要になるもの

[Uber Engineering：Designing MCP Gateway](https://www.uber.com/us/en/blog/designing-mcp-gateway/)

Uberが10月3日、社内の **MCP Management Platform** の設計を詳しく公開しました。

最初は各Teamが個別にMCP Serverを作っていましたが、数が増えるにつれ、

**どのServerを使えばいいか分からない**
**Authentication方式がバラバラ**
**同じToolが重複する**
**Permission / Security Reviewが難しい**
**Clientごとに設定が必要**

という問題が発生。

そこで中央に **MCP Gateway** を置き、AgentからはGatewayだけを見せます。Gateway側がTool Discovery、Routing、Authentication、Authorization、Observabilityなどを担当します。([Uber](https://www.uber.com/us/en/blog/designing-mcp-gateway/))

概念的には、

```text
Claude / Codex / internal agents
             ↓
        MCP Gateway
       /     |      \
 Payments  Search  Internal API
```

です。

**開発者目線:** MCPが普及するとほぼ必ず発生する「次の問題」です。

小規模なら、

`agent → 5 MCP servers`

で十分ですが、企業内で100、500、1000 Serverになれば、Kubernetes以前のMicroservicesと同じ問題になります。

今後 **MCP Gateway / Registry / Policy / Observability** はかなり普通のInfrastructure Categoryになりそうです。([Uber](https://www.uber.com/us/en/blog/designing-mcp-gateway/))

## 2. MLCommons、「AgentのPrivacy Risk」を25種類に体系化

MLCommons が、AI Agent特有のPrivacy Riskを体系化したDraftを公開し、Developer向けに**25種類のRisk**を整理しています。

大きくは5 Domainに分類し、AgentのLifecycleを、

`input → reasoning → memory → tool/action → output → retention`

のように追いながら、「どこでPrivacy Failureが起きたか」を分類できるようにします。([PPC Land](https://ppc.land/mlcommons-catalogues-25-privacy-risks-posed-by-ai-agents/))

例えば普通のChatbotよりAgentで問題になるのは、

**Memoryへの過剰保存**
**Tool経由の意図しないData Transfer**
**SubagentへのContext伝播**
**異なるIdentity間でのData混入**

など。

**開発者目線:** 先週から実例としてPixelLeakやOpenAIのAgent事故を紹介してきましたが、ようやくRiskを**分類可能なEngineering Vocabulary**へ落とし込む動きが出てきました。

SecurityのSTRIDEのように、Agent設計Reviewで、

> このAgentのPrivacy Threat Modelは？

をChecklist化するための土台になりそうです。([PPC Land](https://ppc.land/mlcommons-catalogues-25-privacy-risks-posed-by-ai-agents/))

## 3. Zig 0.17 — Build Systemを大改修、Incremental Compilationが現実的に

Zig **0.17** が10月3日にリリースされました。

5か月、206 Contributors、925 Commitsのかなり大きなReleaseです。([LWN.net](https://prodcs.lwn.net/Articles/1098412/))

特に大きいのがBuild Systemの再設計。

新しい **Build Server Protocol** が導入され、ELF Linkerも大幅改善。x86_64 Linuxでは、Incremental Compilationを広く実用できる状態を目指した変更が入っています。([LWN.net](https://prodcs.lwn.net/Articles/1098412/))

**開発者目線:** Zigの面白さはLanguage Syntax以上に、

**compiler + build system + linker + C interop**

を一つのDeveloper Experienceとして作り直しているところです。

RustがCargoを非常に強い武器にしたように、Zigも「Build ToolまでLanguage Platformの一部」という思想がかなり明確です。

C/C++ Native LibraryやGame Tooling用途でRustとZigを比較するなら、0.17のBuild Systemはチェックしておきたい変更です。

## 4. RuneScape 4 — 25年続くMMOがUnreal Engineで次世代版へ

Jagex がRuneFest 2026で、Working Title **RS4（RuneScape 4）** を正式発表しました。

新しいMMORPGで、**Unreal Engine**を採用。まだDevelopment初期で発売は数年先です。([AOL.com](https://www.aol.com/articles/fourth-runescape-game-under-development-180553000.html))

興味深いのは既存RuneScapeを置き換えないこと。

RuneScape、Old School RuneScape、Dragonwildsはそれぞれ独立して開発を継続し、RS4も別Team / 別Gameとして並存します。([TechSpot](https://www.techspot.com/news/114088-runescape-4-officially-works-started-dragonwilds-expansion.html))

さらにRS4は元々、Dragonwilds向けの2027年Expansionとして作り始めたものが、Playtestを経てStandalone MMOへ膨らんだProjectです。([TechSpot](https://www.techspot.com/news/114088-runescape-4-officially-works-started-dragonwilds-expansion.html))

**ゲーム開発目線:** かなり面白いArchitecture / Product判断です。

25年分のLegacyを、

> 既存Gameを全面RewriteしてMigration

するのではなく、

> **Legacy Serviceを維持したまま、新Architectureを別Productとして並走**

させています。

Software ModernizationでもよくあるStrangler Patternに少し似ています。

## 5. Cloudflare Web Search API — Agent向け「検索」をInfrastructure化

[Cloudflare公式：Web Search API](https://blog.cloudflare.com/introducing-web-search-api/)

[Cloudflare](https://www.cloudflare.com/) がAI Gatewayへ **Web Search API** を追加しました。

Ceramic.ai、Exa、LinkupのSearch Providerを共通Interfaceから利用し、検索結果をStructured ContextとしてAgentへ渡せます。([Cloudflare Blog](https://blog.cloudflare.com/introducing-web-search-api/))

Cloudflareが挙げている理由は単純で、

> AgentにURLを推測させて`curl`させると404が多い。

そのため、

```text
Agent
  ↓ search(query)
Web Search API
  ↓
structured results
  ↓
Agent
  ↓ fetch selected page
```

にします。

**開発者目線:** 地味ですがAgent Tool設計では重要です。

`fetch(url)`と`search(query)`は別Primitiveにした方が良い。

さらにProviderをGateway側へ隠すことで、Agent側はExaなのかLinkupなのか意識する必要がありません。([Cloudflare Blog](https://blog.cloudflare.com/introducing-web-search-api/))

## 6. Cloudflare AI Search、11月から本格課金 — RAGのCostがかなり見えやすく

先日紹介したCloudflare AI SearchにPricingの続報です。

11月1日から課金が始まり、Workers Planには引き続き**10GB Storage + 各種Query 1,000回**の無料枠があります。Token Processingは**100万Tokenあたり$0.75**から。([PPC Land](https://ppc.land/cloudflare-ai-search-starts-billing-november-1-at-0-75-per-million-tokens/))

AI Searchは、

**crawl → parse → OCR → chunk → embedding → Vectorize → retrieval**

をまとめてManaged化するServiceです。画像検索とScan PDF OCRもGA版で追加されています。([Cloudflare Blog](https://blog.cloudflare.com/ai-search-ga/))

**開発者目線:** RAGで意外と困るのは「LLM料金」ではなく、Indexing Pipeline全体のCostを予測しづらいことです。

Managed RAGが、

> Storage + indexed tokens + queries

という普通のInfrastructure Pricingへ落ちてきたのは良い傾向です。

小〜中規模Documentation Searchなら、Vector DB + OCR Pipelineを自前で持つか比較しやすくなりました。

## 7. GitHub：「AI時代に強いDeveloperはPromptが上手い人」ではない

[GitHub公式：AI is rewriting the developer career ladder](https://github.blog/ai-and-ml/ai-is-rewriting-the-developer-career-ladder-heres-how-to-stand-out/)

[GitHub](https://github.com/) が10月2日に公開した記事で、AI Coding時代にDeveloperが伸ばすべき能力を3つに整理しています。

大きくは、

**Agentへ仕事を正しく委譲する能力**
**生成結果を批判的にReviewする能力**
**Architecture / Product / Technical Judgment**

です。([The GitHub Blog](https://github.blog/ai-and-ml/ai-is-rewriting-the-developer-career-ladder-heres-how-to-stand-out/))

つまり「コードを書く速さ」の比重が下がっても、

> 何を作るべきか
> どこが危険か
> どのTrade-offを選ぶか

の価値はむしろ上がる、という主張です。

**開発者目線:** 最近のCoding Agentを実際に使っているとかなり納得感があります。

Agentへ、

`このIssueを実装して`

だけ渡すより、

```text
goal
constraints
architecture boundary
acceptance criteria
validation
```

まで明示した方が結果が安定します。

今後Senior Engineerの仕事は「大量にCodeを書く」から、**Agent FleetにTechnical Directionを与える**方向へ少しずつ移りそうです。

**Release notes → 人間向け**

**開発者目線:** 昨日NVIDIA DOCAがAgent Skillsを提供した話と同じ流れです。

Documentationが、

```text
human docs
agent docs
machine schema
```

へ分化し始めています。

今後LibraryのDocumentation Siteが「LLM-friendly Markdown endpoint」を公式提供するのは普通になるかもしれません。

## 10. 今週のOSS小ネタ：Consumer Hardware向けLocal AI Engine「Strata」が急上昇

GitHub上で週末に伸びている小さめのProjectとして **Strata** が注目されています。

10月2日の集計では1日で約**+1.9K Stars**。Consumer Hardware上で8-Flash-Next系Modelを動かし、localhostからOpenAI / Anthropic互換APIとして利用できるInference Engineです。([GitHub.Locker](https://github.locker/topics/ai))

Windows / Linux向けOne-click Installを重視し、Image Inputにも対応します。

**開発者目線:** Local LLM Toolは、

`Ollama / llama.cpp / LM Studio`

あたりで成熟したようにも見えますが、新規実装がまだ大量に出ています。

最近の差別化ポイントは単に「Modelを動かせる」ではなく、

**OpenAI-compatible API**
**Agent Harnessとの互換性**
**Consumer GPU Memory最適化**
**Installの簡単さ**

へ移っています。

Local Coding Agentを組むならInference EngineをApplicationに直接依存させず、**OpenAI-compatible Endpointを境界にして差し替え可能にする**設計がますます有効です。

## 👀 今日ならこの3つ

**一番実務的なのはUber MCP Gateway。** MCP Serverを数個使う段階では不要ですが、組織全体へ広げると必ずDiscovery・Auth・Policy・Observabilityの問題が出ます。Uberが既に「MCPのKubernetes/API Gateway相当」を作り始めているのは、MCPが実験段階からEnterprise Infrastructureへ進んだSignalとして面白いです。([Uber](https://www.uber.com/us/en/blog/designing-mcp-gateway/))

**ゲーム開発ならRuneScape 4。** 25年分のLegacy MMOを無理にUnreal EngineへMigrationせず、既存Serviceを維持したまま次世代Architectureを別Gameとして並走させる判断が興味深いです。Game Engine移行の技術詳細が今後公開されるなら追いたいProjectです。([AOL.com](https://www.aol.com/articles/fourth-runescape-game-under-development-180553000.html))

**Toolchain好きならZig 0.17。** Language FeatureよりBuild Server Protocol / Linker / Incremental Compilationの改善が主役なのがZigらしいReleaseです。Rustとの比較でも「言語そのもの」だけでなく、**Build / Cross Compile / C interop / Linkerまで含めた開発体験**を見る価値があります。([LWN.net](https://prodcs.lwn.net/Articles/1098412/))
