## 1. Git 2.56.1 — 再帰cloneやmergeを含む6件の脆弱性を修正

**11月9〜10日公開｜公式一次情報**

11月10日、Gitプロジェクトは6件の脆弱性を修正したGit 2.56.1を公開した。旧系列向けにも2.55.1、2.54.1、2.53.1、2.52.1、2.51.3、2.50.2が提供されている。Gitは単なるバージョン管理コマンドではなく、CI、IDE、コードホスティング、エージェントが外部コードを取得する際の共通基盤だ。したがって、悪意あるリポジトリを処理した際の不具合は、開発者が明示的に危険なプログラムを実行しなくても問題になる。

最も注意したいCVE-2026-111760は、極端に長いパスを扱う際の整数切り詰めを利用し、再帰clone時にサブモジュールの.gitファイルを不正なシンボリックリンクへ置き換え、設定やhookの実行につながり得る問題だ。CVE-2026-113408は空リポジトリをcloneする際のHEAD参照名検証不足、CVE-2026-114467は複数署名を持つタグをmergeした際のスタック破壊、CVE-2026-114469は圧縮されたバイナリパッチの展開サイズ検証不足に関係する。

さらにCVE-2026-105437は大きなmerge結果のサイズ計算でヒープを破壊し得る問題、CVE-2026-114466はfast-importの一部機能が想定外のファイルを読み書きできる問題だ。影響条件はそれぞれ異なるが、共通するのは「Gitへ渡す入力も信頼境界の外側にある」という点。GitHubはホスティング側の修正を展開済みと説明し、同梱Gitを持つアプリやActionsなども更新対象としている。

**開発者目線:** 開発用PCのgit --versionだけでは不十分だ。CIランナー、Dockerイメージ、IDE同梱バイナリ、独自ビルドエージェントのGitも棚卸ししたい。特に外部PRをcloneする自動化、再帰サブモジュール、パッチ適用、fast-importを扱うサーバーでは優先順位が高い。更新がすぐできない環境では未信頼の再帰cloneやmergeを避ける暫定策を採るが、根本対策は修正版への更新である。

[公式解説](https://github.blog/open-source/git/git-security-vulnerabilities-announced-7/)

## 2. Dependabot — 1年以上動きのないリポジトリのアラートを12月8日から休止

**11月9〜10日公開｜公式一次情報**

GitHubは11月10日、2026年12月8日から、過去1年間に活動がない大半のリポジトリでDependabot alertsを自動的にオフにすると告知した。既存アラートは削除ではなくアーカイブされ、再有効化すれば復元される。脆弱性データベースが拡大するなか、使われていないリポジトリにも新しい検出を継続する負荷を抑え、活動中のプロジェクトへ処理を集中させる変更だ。

GitHubが活動と数えるのは、ブランチやタグへのpush、リポジトリ作成、Dependabot alertsの有効化である。Issueの閲覧や単なるcloneが活動として数えられるとは発表されていない。休止後もpushするとアラートは自動復帰し、設定画面から手動で有効化してもよい。再有効化した時点から1年間の時計が再スタートするため、長期保管しているプロジェクトでも復帰手段は残される。

例外もある。Dependabot alertsを強制的に有効にするセキュリティ構成を適用したリポジトリと、管理者がアラートを切り替えられない企業ポリシー下のリポジトリは対象外。github.comの全プランとデータ所在地指定のGitHub Enterprise Cloudが対象で、GitHub Enterprise Serverには適用されない。つまり「GitHubを使っていれば全部同じ」ではなく、ホスティング形態と統制ポリシーで動作が分かれる。

**開発者目線:** 保守停止したライブラリでも、将来の再利用や監査で脆弱性情報が必要になる場合がある。休止を無理に回避するための無意味な定期pushより、アーカイブ方針と保守責任を明確にする方がよい。資産台帳に「最終push」「Dependabot有効状態」「再稼働時の依存監査」を持たせ、復帰時に既存アラートを一括確認する手順を整えたい。

[公式告知](https://github.blog/changelog/2026-11-10-dependabot-alerts-will-pause-on-inactive-repositories/)

## 3. Copilot CLIのC++ Language Server — MSBuildのコンパイル情報を自動生成

**11月9〜10日公開｜公式一次情報**

11月10日、GitHubはCopilot CLI向けMicrosoft C++ Language ServerがMSBuildプロジェクトのコンパイルコマンド抽出器を同梱し、起動時に自動実行するようになったと発表した。C++のコード補完や定義ジャンプは、ソースを読むだけでは正確にならない。インクルードパス、プリプロセッサの定義、言語モード、ビルド構成を把握する必要があるため、Language Serverにはコンパイルデータベースが重要になる。

従来、MSBuildのプロジェクトでは利用者がcompile_commands.jsonを用意するか、エージェントが別の設定Skillを発見して実行する必要があった。新方式では抽出器がLanguage Serverに組み込まれ、プロジェクトを開くと自動的にデータベースを生成する。GitHubは、準備工程の発見に使っていたトークンと時間を減らし、定義ジャンプや参照検索をより早く正確に開始できると説明している。これはモデルの賢さを増す変更ではなく、モデルへ渡す構造化情報の質を改善する変更だ。

CMakeの場合は既存のcompile commands生成Skillを使い、独自ビルドシステムには抽出器Skillを作る方針が示されている。すべてのC++プロジェクトで自動生成が成立するわけではない。またプラグインの導入とEULAへの同意、Copilotの有効な契約が必要だ。MSBuild固有の自動化を、一般的なビルドシステム対応と混同しないようにしたい。

**開発者目線:** エージェントがコードを変更する前に正しいシンボル情報を取得できるかは、編集精度に直結する。大規模C++コードベースでは、設定前後で「同名関数の定義を正しく選べるか」「条件付きコンパイルの分岐を誤認しないか」を試すとよい。生成されたコンパイル情報がDebug/Releaseや対象プラットフォームに合っているかも検証対象にする。

[公式更新](https://github.blog/changelog/2026-11-10-c-language-server-now-auto-configures-msbuild-builds/)

## 4. pnpm 12.19 — loaded linkerがビルド済み依存パッケージを再利用

**11月9〜10日公開｜公式一次情報**

11月10日公開のpnpm 12.19.0では、nodeLinker.typeをloadedにした環境で、インストール時にビルドを必要とする依存パッケージの扱いが改善された。従来はビルドを必要とするパッケージをnodeLinker.excludedへ列挙する必要があったが、今回の実装は条件に応じて自動的に実体化する。依存をストアから読み出す高速な仕組みと、ネイティブ拡張や生成処理を伴うパッケージの互換性を両立する方向だ。

side-effects cacheに一致する成果物があればストアからロードする。キャッシュの読み書きが有効なら、承認されたビルドを一度実行して結果を保存し、同じストアを使う別プロジェクトでも再利用する。変更ファイルがないビルドであっても繰り返し実行を避ける設計になった。ただしGit hookをインストールするような「各プロジェクトで必ず走るべき処理」はsideEffectsCache.excludeで除外する必要がある。

JavaScriptソースのファイルシステム関連importや__dirname、import.metaの利用も調べ、必要なパッケージを実体化する。ただし計算された動的importは検出できないため、そのようなパッケージは手動でexcludedへ登録する。つまり自動化は万能な静的解析ではなく、よくあるパターンを補うヒューリスティックだ。パッケージ固有のインストールスクリプトが期待する副作用を理解して使う必要がある。

**開発者目線:** monorepoの依存インストール時間を測る場合、初回とウォームキャッシュを分け、ストアを共有するCIと共有しないCIを比較したい。ネイティブモジュールのABI、OS、Nodeバージョンが異なる環境でキャッシュを流用しないことも重要。高速化の数値を一般化せず、インストール後のテストが同じ結果を返すかまで確認したい。

[公式リリース](https://github.com/pnpm/pnpm/releases/tag/v12.19.0)

## 5. pnpm 12.19 — 実験的ロックファイル形式とoptional peer解決の境界

**11月9〜10日公開｜公式一次情報**

pnpm 12.19.0には、依存関係を再現可能にするロックファイルとpeer dependencyの解決を扱う新設定も追加された。lockfile.format: v13は実験機能で、pnpm-lock.yamlをJSON風の構文で書き出す。タブ字下げや末尾カンマを含むが、YAMLとしても有効な形式だ。従来のpackagesとsnapshotsの二重構造を、パッケージバージョンごとの単一エントリへまとめ、peer依存のバージョン情報をその属性として記録する。

狙いはpeer dependencyが変わったときに大量の無関係な行が差分へ現れる問題を減らすことだ。ロックファイルは人間が頻繁に手で編集するものではないが、PRレビューで差分を追うことは多い。不要な変更が少なければ、意図しない依存更新を見つけやすくなる。pnpmは設定にかかわらず両形式を読めると説明する一方、書き出し形式の採用は実験扱いなので、周辺ツールとの互換性確認が必要だ。

projectScopedOptionalPeersをtrueにすると、あるworkspaceプロジェクトが欠けているoptional peerを、別プロジェクトの依存から勝手に補わない。従来は開発ツールの依存が別アプリの本番依存へ影響するような、見えにくい解決が起き得た。workspace全体で共有する依存と各パッケージの境界を明確にする変更であり、monorepoの分離性を重視する場合に意味がある。

**開発者目線:** ロックファイル形式を変える際は、単に差分が小さいことより、CIのfrozen-lockfile、Dependabotなどの更新Bot、古いpnpmを使う開発者が問題なく扱えるかを検証したい。optional peerの境界変更では、単体テストだけでなく各workspaceを個別にインストールした場合の依存解決も比較すると、隠れていた結合を発見できる。

[公式リリース](https://github.com/pnpm/pnpm/releases/tag/v12.19.0)

## 6. pnpm 12.19 — オフライン時の認証情報露出を防ぎCPU制限も尊重

**11月9〜10日公開｜公式一次情報**

pnpm 12.19.0のパッチ修正には、エラーメッセージに秘密情報が混入する問題への対策が含まれる。オフラインモードで必要なtarballがストアに存在しない場合、従来はエラーにレジストリURL内の認証情報やトークンが出力される可能性があった。今回の修正ではそれらを表示しない。依存インストールの失敗ログはCIに残されやすく、閲覧者が多い環境ほど影響が広がるため、正常系では見えない問題でも優先度が高い。

また、コンテナ内でpnpm installを実行する際の並列度がCPU quotaを尊重するようになった。ホストに多数のCPUが見えていても、KubernetesのCPU limitなどで実際に使える計算資源が少ない場合がある。従来はホスト側のCPU数を基準に大量のworkerを起動し、メモリ不足を招く場合があった。今回の変更では制限されたCPU quotaに合わせてworker poolとworkspaceConcurrencyの既定値を調整する。

さらに、並行するダウンロードがキャンセルされた際にinstallが待ち続ける問題や、取得失敗したtarballを二重にリトライして待ち時間が伸びる問題も修正された。依存インストールは毎日のCIで大量に実行されるため、まれなハングでも累積すると開発効率へ影響する。性能改善とセキュリティ修正が同じパッチに含まれている点を見落としたくない。

**開発者目線:** プライベートレジストリを使うCIでは、過去ログの認証情報漏えいを調べるだけでなく、URLに資格情報を埋め込まない構成へ移すことが望ましい。CPU制限のあるコンテナでは更新前後の最大メモリと実行時間を計測する。更新によって並列度が減る場合もあるため、単純に速くなったと判断せず、OOM率や再実行率を含めて評価したい。

[公式リリース](https://github.com/pnpm/pnpm/releases/tag/v12.19.0)

## 7. Claude Code 2.1.321 — MCP OAuthのリダイレクト先への秘密情報送信を修正

**11月9〜10日公開｜公式一次情報**

11月9日公開のClaude Code 2.1.321では、MCP OAuth認証に関する重要な修正が入った。MCPサーバーがHTTPリダイレクトを返した場合、refresh tokenなどの秘密情報を別ホストへ送信し得る経路が修正された。MCPはエージェントが外部の情報源や操作機能へ接続する仕組みだが、ツールの呼び出しだけでなく、認証の開始、トークン更新、リダイレクト追従も信頼境界をまたぐ操作になる。

同じリリースではBashの読み取り専用コマンドが権限確認なしでsandbox外へ出る場合、書き込み先フォルダの誤判定、ディレクトリへcpやmvする際に保護ファイルのdenyルールが適用されない場合も修正された。個別には異なるバグだが、いずれも「エージェントが実行しようとしている操作」と「権限判定が実際に検査した対象」が一致しない問題だ。ツール実行前の許可UIがあっても、実行パスやリダイレクト後の宛先まで正しく評価しなければ安全とは言えない。

またPreToolUse hookで複数のaskやdeferが競合すると、別のhookの理由が表示されたり、確認要求が失われたりする問題にも手が入った。hookを組み合わせて社内ポリシーや監査を実装する場合、単独動作だけでは見つからない競合がある。今回の修正は権限モデルそのものの刷新ではないが、既存の保護を期待通り動かすために重要だ。

**開発者目線:** MCP接続を管理する際は、トークンのスコープを狭くし、認証サーバーとリダイレクト先の許可範囲を監査する。hookやdenyルールを使う場合は、相対パス、シンボリックリンク、ディレクトリへのコピー、並行実行を含む回帰テストを用意したい。セキュリティ修正を取り込んだ後も、実際に拒否されることを確認する負のテストが有効だ。

[公式リリース](https://github.com/anthropics/claude-code/releases/tag/v2.1.321)

## 8. Claude Code 2.1.322 — Vertex AIでfast modeを地域別に利用可能に

**11月9〜10日公開｜公式一次情報**

11月10日公開のClaude Code 2.1.322は、Google Cloud Vertex AI経由のfast modeをglobal、us、euの各リージョンで使えるようにした。fast modeは通常の推論結果をより低い待ち時間で得るための提供経路で、利用するモデルやサービス側の提供状況に依存する。今回の変更ではVertex側が高速モードを拒否した場合、標準速度へフォールバックする動作も明記された。

開発エージェントでは応答時間が少し短くなるだけでも、コードを読む、テストする、修正するという往復が多い作業では体感差が生じる。一方で、fast modeが常に有効になるわけではなく、リージョンや割当量、サービス側の応答によって標準速度へ戻る場合がある。高速経路への対応と、実際のジョブ完了時間の改善は別の指標として扱う必要がある。

同じ週の2.1.321ではfast modeがレート制限や過負荷で失敗した際に、モデルを変えたり長時間リトライしたりする前に同一モデルの標準速度を試す修正も入っている。したがって、fast modeを有効にする判断は速度だけでなく、失敗時にどう復旧するかも含めた運用設計になる。新バージョンは高速化の実測値を保証するものではなく、利用経路とフォールバックの追加として読むのが正確だ。

**開発者目線:** エージェントの実行ログでは「要求したモード」「実際に利用されたモード」「最初のトークンまでの時間」「最終成果物までの時間」を分けて記録したい。フォールバック時の料金、クォータ、リージョン要件は契約環境で確認する。短い質問だけでなく、多段階の修正タスクで比較し、速い応答が総作業時間の短縮につながっているかを評価するのが実務的だ。

[公式リリース](https://github.com/anthropics/claude-code/releases/tag/v2.1.322)

## 9. GitHub ActionsのログもSecret scanning対象へ — 公開プレビュー

**11月9〜10日公開｜公式一次情報**

11月9日、GitHubはSecret scanningがGitHub Actionsのworkflowログに含まれる秘密情報も検出できるようになったと発表した。これまでもコードやIssueなどのテキストを対象にしていたが、CIログはビルド時の環境変数、HTTPレスポンス、デバッグ出力などが混入しやすい場所だ。ソースコードには秘密を置いていなくても、失敗時の詳細ログにトークンが現れることがある。

この機能はGitHub Enterprise CloudでGitHub Secret ProtectionまたはGitHub Advanced Securityを利用する企業向けのpublic preview。企業管理者がPoliciesから有効化する必要があり、既定ではオフになっている。スキャンは有効化後に完了したworkflow runに対して実行され、過去のログをさかのぼって検査するわけではない。検出結果はリポジトリのsecret scanningアラートに表示され、該当するActionsログへ移動できる。

制約も明確だ。generic pattern、custom pattern、AI検出の秘密、すでにActionsによってマスクされた秘密は対象外である。プレビュー期間中はアラート通知も送信されないため、管理画面を見に行かなければ発見できない可能性がある。ログが削除された後もアラートは残る。したがって、ログ削除だけを秘密の失効や事故対応の完了とみなすことはできない。

**開発者目線:** CIでは最初から機密値を出力しない設計が基本だ。今回の検出を追加の防御層として使い、定期的にアラートを確認する運用を作りたい。検出されたトークンはログを消すだけでなく失効・再発行し、影響範囲を調査する。previewの対象外パターンがあるため、secret scanningを有効にしたことを理由にデバッグ出力の監査を省略してはいけない。

[公式発表](https://github.blog/changelog/2026-11-09-secret-scanning-detects-secrets-in-github-actions-workflow-logs/)

## 10. GitHubダッシュボード — PRとIssueを6件表示しAgent欄を条件付きに

**11月9〜10日公開｜公式一次情報**

GitHubは11月10日、Webダッシュボードの情報密度を高めるUI更新を発表した。新しいダッシュボードを既定化した後、余白が大きく一度に確認できる情報が少ないという意見が寄せられていた。今回の更新は新機能を増やすのではなく、既存の作業キューを少ないスクロールで確認できるようにするものだ。日常的にPRレビューやIssueトリアージを行う開発者には、こうした小さな改善も積み重なる。

PR、Issue、Agent sessionのリストで余白が縮小され、長いタイトルは1行で表示し、必要に応じて全文を確認できるようになった。PRとIssueの既定表示数は3件から6件へ増え、利用者が独自に設定した表示件数は維持される。またAgent sessionを持たないアカウントでは、そのセクション自体を非表示にする。空の情報領域を見せないことは、操作を単純化する基本的なUI設計だ。

この変更はエージェントの性能やPRのレビューアルゴリズムを変えるものではない。表示される件数が増えても、重要度順の並び替えや通知の優先度が改善したと断定はできない。長いタイトルを省略すると一覧性は上がるが、似た名前のタスクを取り違える可能性もあるため、全文へのアクセスを残している点が重要になる。

**開発者目線:** 開発ツールのダッシュボードを設計する際は、空のウィジェットを常時表示する必要があるか、既定件数が少なすぎないか、タイトルを折り返すより詳細表示に委ねるべきかを考えたい。UI改善の効果は見た目の好みだけでなく、目的のPRへ到達するクリック数や一覧画面で判断できる割合で測れる。小さな密度改善も頻繁に使う画面では価値が大きい。
