今朝はかなり面白いです。特に **「LLMではないAIモデル」Jev、Plugin4Shell、Anthropic社内で3万Agent同時稼働** の3本が強め。ゲーム開発ではUnity公式のかなり実践的なモバイル最適化事例が出ています。昨日まで扱ったClaude Code Projects、Ubuntu 26.04、TensorRT Edge-LLMなどは外しました。

## 1. 「LLMじゃないAI」Jev — 文字列ではなく“型付き値＋確率”を返す

元OpenAI研究者の Diogo Almeida が設立した [TypeSafe AI](https://typesafe.ai/) の新モデル **Jev** がDeveloper界隈で注目されています。([TechCrunch](https://techcrunch.com/2026/09/18/a-new-kind-of-ai-model-from-a-chatgpt-inventor-is-thrilling-developers/))

発想が普通のLLMとかなり違います。文章を生成するのではなく、入力とSchemaを渡すと、

```text
category: "billing"
confidence: 0.96
urgent: true
```

のような**型付きDecision + calibrated probability**を返します。

VercelがOpenAI LunaからJevへ一部処理を置き換えたテストでは、5〜18倍高速かつ精度も改善したとTechCrunchが報じています。別のメール分類テストではGeminiより若干精度は低かったものの、10〜20倍安価でした。([TechCrunch](https://techcrunch.com/2026/09/18/a-new-kind-of-ai-model-from-a-chatgpt-inventor-is-thrilling-developers/))

**開発者目線:** 今日一番面白いです。

LLMに、

`文章生成 → JSON parse → schema validation → retry`

させるのではなく、最初から**Softwareが扱えるDecisionを返す専用Model**にする。

Agentでも、

`Jev → routing / classification / guardrail`
`↓ 難しい場合だけ`
`GPT / Claude / Gemini`

という構成がかなり合理的です。「すべてをLLMで解く」流れへの面白い反動になりそうです。

## 2. Plugin4Shell — “SHA固定したPluginなら安全”を破るZero-click RCE

今日一番注意したいSecurityニュースです。

**Plugin4Shell**というSupply-chain脆弱性が公開され、Claude Code、Codex、GitHub Copilot、Gemini CLIのPlugin取得処理が影響を受けていたことが判明しました。([Help Net Security](https://www.helpnetsecurity.com/2026/09/18/plugin4shell-ai-coding-agents-vulnerability/))

問題はPluginを特定Commit SHAへPinしていても、Agent側がGit checkoutの結果を十分検証しておらず、Repository Ownerが別コードへすり替えられるケースがあること。

さらにAuto-update時にも処理が走るため、**ユーザー操作なしで既存Pluginへ悪意あるコードが届く可能性**があります。([Help Net Security](https://www.helpnetsecurity.com/2026/09/18/plugin4shell-ai-coding-agents-vulnerability/))

AnthropicはClaude Code **2.1.179**、OpenAIはCodex **0.146.0**で修正済み。一方、公開時点の報告ではCopilotは未修正、Gemini CLIはDeprecatedのためGoogleはAntigravityへの移行を案内しているとされています。([Help Net Security](https://www.helpnetsecurity.com/2026/09/18/plugin4shell-ai-coding-agents-vulnerability/))

**開発者目線:** GitSpawnに続いてかなり重要です。

Agent Pluginは、

> 「便利な設定ファイル」

ではなく、実質的には**Package Managerと同じSupply Chain**です。

特にClaude Code / Codexを使っているなら、古いVersionを固定している環境は更新しておいた方がよさそうです。

## 3. Anthropic内部、約30,000 Agentが同時稼働

[Anthropic公式：Measuring the pace of AI development](https://www.anthropic.com/institute/measuring-pace-of-ai-development)

Anthropic がかなり興味深い社内データを公開しました。

2026年8月時点で、ClaudeがAnthropicのAI R&Dの**26%を「主導」**。90%以上の仕事では少なくともAIが実質的に協働しています。ただし完全自律（人間がLoopにいない状態）になった測定対象はまだゼロです。([Anthropic](https://www.anthropic.com/institute/measuring-pace-of-ai-development))

そして主要な内部Research / Engineering Platformでは、約**30,000のAgentが同時稼働**しているとしています。([Anthropic](https://www.anthropic.com/institute/measuring-pace-of-ai-development))

**開発者目線:** 「EngineerがClaude Codeを1個起動する」の延長ではありません。

```text
Human researcher
       ↓
Agent orchestration
 ├─ Agent
 ├─ Agent
 ├─ Agent
 ├─ ...
 └─ tens of thousands
```

という**Agent Fleet Infrastructure**が既にFrontier Lab内部では現実になっています。

最近、Agent Scheduler / Observability / Identity / Budget / Sandboxのニュースが急増している理由もよく分かります。

## 4. Anthropic、外部評価者を“社員並みAccess”で社内へ入れる

[Anthropic × Accenture Embedded Evaluation](https://www.anthropic.com/news/accenture-embedded-evaluation)

9月18日、Anthropicと [Accenture](https://www.accenture.com/) が **Embedded Evaluation** を発表しました。

通常の外部Benchmarkではなく、独立評価者がAnthropic内部へ入り、**社員に近いAccessでTraining過程・Model Safeguard・社内Decision・Incidentを継続観測**します。([Anthropic](https://www.anthropic.com/news/accenture-embedded-evaluation))

両社はこの領域へ今後5年間でそれぞれ最低10億ドルを投資予定です。

**開発者目線:** Software Securityでいう外部Pen-testより、

> **Security Engineerを開発TeamそのものへEmbedする**

考え方に近いです。

Frontier ModelはRelease後にBenchmarkするだけでは内部で何が起きたか分からないため、**Model Development ProcessそのものをObservability対象にする**という新しい評価方式です。

## 5. Unity公式：Deep Rock Galactic Survivorを3GB iPadまで落とし込んだ方法

[Unity公式：Optimizing Deep Rock Galactic Survivor for mobile](https://unity.com/kr/blog/optimizing-deep-rock-galactic-survivor-for-mobile)

Unity が9月18日、Deep Rock Galactic: Survivor のMobile Port最適化事例を公開しました。

かなり実践的です。

PC版では大量の敵・採掘可能Terrainを同時処理しますが、Mobile版では、

**Pathfinding / Physics Query / Enemy Rendering / Damage Calculation / Environment Rendering**

など、**敵数に比例してCostが増えるSystemを重点的に作り直した**とのこと。さらに3GB RAMのiPadまでTargetにしつつ、開発中のPC版からMobile Branchへの一方向Mergeも維持しました。([Unity](https://unity.com/kr/blog/optimizing-deep-rock-galactic-survivor-for-mobile))

**Unity開発者目線:** 「MobileだからShaderを軽くしました」程度の話ではなく、

> **Nが増えるとCostが増えるGameplay Systemを探す**

というOptimization Strategyが参考になります。

Unity案件なら今日一番読む価値のある記事です。

## 6. npm「Stage-only Token」— AgentはPublishできないが“公開候補”までは作れる

[GitHub公式：Stage-only npm tokens](https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation/)

npmに **Read and write (stage only)** Tokenが追加されました。

Automation / Agentは、

```bash
npm stage publish
```

までは実行できますが、`npm publish`は拒否されます。

最後のReleaseだけPackage Maintainerが2FAでApproveします。([The GitHub Blog](https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation/))

**開発者目線:** Agent Permission設計としてかなり綺麗です。

```text
Agent
  build
  test
  package
  stage
    ↓
Human approval
    ↓
publish
```

つまり「Write権限を全部与える / 与えない」ではなく、**不可逆操作の直前にHuman Gateを置く**。

npmは2027年1月にbypass-2FA Tokenによる直接Publishを廃止予定なので、CI/CD側でも重要な変更です。([The GitHub Blog](https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation/))

## 7. Copilot、GPT-5.5 / 5.4などを10月19日に一斉廃止

[GitHub公式：Copilot model deprecations](https://github.blog/changelog/2026-09-18-upcoming-deprecation-of-selected-github-copilot-models-in-mid-october/)

GitHubが9月18日に新しいModel Retirementを発表しました。

10月19日にCopilotから、

**GPT-5.5 → GPT-5.6 Sol**
**GPT-5.4 → GPT-5.6 Sol**
**GPT-5.4 mini / GPT-5 mini → GPT-5.6 Luna**
**Gemini 3.7 Flash → Gemini 3.8 Flash**
**Grok 4.5 → Grok 4.6**

へ移行します。([The GitHub Blog](https://github.blog/changelog/2026-09-18-upcoming-deprecation-of-selected-github-copilot-models-in-mid-october/))

なおOpenAI自身もChatGPT / Work / CodexでGPT-5.5を**10月14日**に終了予定で、APIは影響を受けません。([OpenAI Developers](https://developers.openai.com/ja-JP/docs/whats-new))

**開発者目線:** Agent ScriptやCustom AgentでModel名をHard-codeしているなら要注意です。

最近のModel Rotation速度を見ると、

> `model = "gpt-x.y"`

をApplication Logicへ直接埋めるより、**Capability / Tier / Alias経由で選択する**設計の価値が上がっています。

## 8. Copilot Code Review、Review自体を“継続状態”として扱うように

[GitHub公式：Improved Copilot code review](https://github.blog/changelog/2026-09-18-copilot-code-review-an-improved-review-experience/)

Copilot Code Reviewの新UIが9月18日にGAしました。

単に毎回新しいReviewを投げるのではなく、過去の指摘を、

**Open / Resolved since last review / New**

として追跡。修正された指摘はCopilot自身が再検証してResolveします。Reviewに使ったEffort LevelやSeverityも表示されます。([The GitHub Blog](https://github.blog/changelog/2026-09-18-copilot-code-review-an-improved-review-experience/))

さらにLite Reviewでも複数Agentの結果を統合し、Shell Toolで変更を検証するようになっています。([The GitHub Blog](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14/))

**開発者目線:** AI Reviewが、

`Diff → コメント生成`

から、

**`PRのLife Cycleを追跡するStateful Agent`**

へ変わっているのが重要です。

AI Reviewでありがちな「直したのに同じ指摘をまたされる」問題への自然な回答です。

## 9. Claude Life Sciences — 「安全Classifierを弱くする代わりにユーザーをVerify」

[Anthropic：Life Sciences Verification Program](https://www.anthropic.com/news/life-sciences-verification-program)

Anthropicが **Life Sciences Verification Program（LSVP）** をBeta公開しました。

通常Claudeでは安全上Blockされる高度なBiology Taskについて、研究機関・製薬企業などを事前審査し、Mythos / Opus / Sonnetへより広いAccessを与えます。([Anthropic](https://www.anthropic.com/news/life-sciences-verification-program))

特に興味深いのがSecurity Architecture。

通常：

`Request → classifier → allow/block`

LSVP：

`Verified organization → broader access → 30-day offline monitoring → anomaly detection`

へ切り替えます。([Anthropic](https://www.anthropic.com/news/life-sciences-verification-program))

**開発者目線:** Agent Security全般にも応用できる考え方です。

Prompt内容だけでRiskを判定するのではなく、

**Identity + declared purpose + behavior over time**

でAccess Controlする。

「何を言ったか」から**「誰が・何の目的で・どんなAction Patternを取っているか」**へSecurity境界が移っています。

## 10. 小ネタ：Copilot AgentをDev Container内でそのまま動かせる

[GitHub Copilot weekly release](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14/)

VS Code 1.138系で、CopilotのAgents Windowから**Local Dev ContainerをAgent実行環境として利用**できるようになっています。DockerとDev Container Configurationがあれば、Projectの依存関係込みのContainer内でAgentが作業します。段階的Rollout中です。([The GitHub Blog](https://github.blog/changelog/2026-09-18-github-copilot-weekly-releases-september-14/))

Agent SessionからそのままPR作成も可能になり、Merge済みSessionを自動でDone → 一定期間後削除するCleanup機能もPreviewされています。

**開発者目線:** 地味ですがAgent UXとしてかなり自然です。

```text
repo
 ↓
devcontainer
 ↓
agent works
 ↓
PR
 ↓
merge
 ↓
session cleanup
```

と、**Agent Session自体がDisposable Development Environment**になっています。

以前から出ている「Coding Agentごとに独立Environmentを持たせる」考え方が、特殊なAgent ToolではなくVS Code標準Workflowへ入り始めています。

実務上は **Plugin4Shell**。Claude Codeは2.1.179以降、Codexは0.146.0以降なら修正済みと報告されているので、古いVersionを固定している環境だけ確認しておくのがおすすめです。([Help Net Security](https://www.helpnetsecurity.com/2026/09/18/plugin4shell-ai-coding-agents-vulnerability/))

ゲーム開発では **Deep Rock Galactic: SurvivorのUnity最適化記事**。大量Entityを扱うゲームで「何をProfileすべきか」が具体的で、特に**敵数Nに比例して悪化するSystemを先に潰す**という視点は、モバイルゲームの性能改善にもそのまま使える内容です。([Unity](https://unity.com/kr/blog/optimizing-deep-rock-galactic-survivor-for-mobile))
