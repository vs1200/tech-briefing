## 1. GitHub AI Scan、20リポジトリを一括スキャン開始可能に

**公開情報：2026年11月16日前後｜公式一次情報**

GitHubは11月16日、AI Scan for repositoriesを最大20リポジトリに対して一括起動できるようにした。組織のコードスキャンアラート画面から対象を選ぶか、組織レベルの設定を有効化するときに開始できる。単一リポジトリのアラート画面からの起動にも対応する。既存のCodeQLを置き換えるというより、CodeQLが対応しない言語や、対応済み言語でも追加の問題を探す補助的な検査として位置づけられる。

結果はCodeQLのアラートと同じコードスキャンのバックログに現れる。これは開発チームにとって重要で、検出器ごとに別の管理画面を見て修正状況を追跡する必要を減らせる。一方、検査対象はリポジトリのデフォルトブランチであり、すべてのPull Requestの変更を自動的に検査するという発表ではない。複数リポジトリの横断的な初回棚卸しと、日々のPRゲートを区別して考える必要がある。

一括起動は公開プレビュー段階。github.comとデータ所在地指定のGitHub Enterprise Cloudで利用でき、Copilotライセンスは不要と明記された。実運用では20件ずつ対象を分けて開始し、既存のCodeQL結果との重複、誤検知、優先度を確認するのが現実的だ。AIによる指摘は再現条件やデータフローを検証しないまま修正すると、かえって不具合を招く場合がある。

**開発者目線:** 組織内の古いリポジトリを棚卸しする際、まず重要度の高い20件を選び、既存の静的解析で拾えなかった指摘を分類したい。指摘ごとに再現テスト、影響範囲、修正PRを紐づけ、AI Scanの検出数だけで品質向上を測らないことが肝心だ。

[公式出典](https://github.blog/changelog/2026-11-16-bulk-start-ai-scan-for-repositories/)

## 2. GitHub Copilot、11月16日に旧モデル3種の提供を終了

**公開情報：2026年11月16日前後｜公式一次情報**

GitHubは11月16日、CopilotでClaude Opus 4.8、Claude Opus 5、GPT-5.6 Terraの3モデルを廃止した。10月15日に予告されていた変更の実施報告であり、11月13日に告知された12月の別の廃止予定とは区別したい。対象はCopilot Chatだけでなく、インライン編集、Ask、Agent、コード補完など大半のCopilot体験に及ぶ。モデル名を固定した設定を放置すると、選択できなくなる可能性がある。

GitHubの推奨代替はClaude Opus 4.8と5に対してClaude Opus 5.5、GPT-5.6 Terraに対してGPT-6.1 SolまたはGPT-6 Luna。例外として年間契約の個人Copilot利用者にはOpus 4.8が引き続き提供される。Claude Opus 5はモデル選択欄から削除されたが、既存の認可に基づくランタイムの拒否時フォールバック用途では残ると説明されている。表示されないことと、すべての内部経路で完全に消えたことは同義ではない。

企業向けでは既定のモデル有効化設定に応じて代替モデルが自動で有効になる場合がある。ただし管理者が既定をオフにしたり個別モデルを禁止したりしている場合、ポリシーの変更が必要になる。新旧モデルの性能、費用、ツール呼び出しの傾向が同一という保証はないため、単純な名前の置換だけで移行完了と判断しない方がよい。

**開発者目線:** IDE、CLI、社内手順、評価スクリプトでモデル名を検索し、失敗時の代替動作を確認したい。代表的なバグ修正やレビューのタスクを新モデルで再実行し、テスト成功率、生成差分、実行時間を比較する。組織ポリシーによる非表示と、提供終了による非表示を切り分けることも重要だ。

[公式出典](https://github.blog/changelog/2026-11-16-github-copilot-models-deprecated-on-november-16-2026/)

## 3. VS Code Copilot 1.146、エージェントのInboxとモデル比較を試験導入

**公開情報：2026年11月16日前後｜公式一次情報**

GitHubが11月16日に公開した週次更新では、VS Code向けCopilot 1.146のエージェント運用機能が紹介された。AgentsウィンドウのInboxモードは、複数ワークスペースのセッションを一覧化し、人間の対応が必要なものを先に見せる。セッションをdismiss、hold、snoozeでき、作業が増えるほど難しくなる「どれを確認すべきか」という問題に取り組む。現時点では実験的機能であり、全利用者に同じ状態で提供されるとは限らない。

もう一つの実験的機能Compare Modelsでは、設定を有効化してエージェント用ツールを許可すると、エージェントが利用可能なモデルを調べ、比較を実行し、結果を要約できる。モデル比較は同じプロンプトでも実行時のリポジトリ状態やテスト環境によって結果が変わるため、単なる回答の好み比べではなく、同じ条件のタスクセットで評価することが必要だ。チャットを独立したウィンドウへ切り離す機能もプレビューとして案内された。

今後の移行として、従来のLocal harnessは2027年2月に削除予定で、Copilot harnessが新規セッションの既定になっている。ここでいうharnessはモデルそのものではなく、モデルに作業環境とツールを提供する実行側の仕組みだ。既存ワークフローがローカル実行前提の設定や拡張に依存していないか、移行ガイドで点検する価値がある。

**開発者目線:** 複数の修正依頼を並行させるなら、セッションの優先度付けを導入するだけでも確認漏れを減らせる。比較機能はテストを含む小さな課題で試し、モデル間の差を主観だけで判断しない。実験的機能は設定変更で戻せる状態を保ちたい。

[公式出典](https://github.blog/changelog/2026-11-16-github-copilot-weekly-releases-november-9/)

## 4. Claude Code 2.1.326、Code Modeとエージェントチームの併用に対応

**公開情報：2026年11月16日前後｜公式一次情報**

11月16日UTCに公開されたClaude Code 2.1.326では、agent teamsを有効にした状態でもCode Modeを利用できるようになった。既にCode Modeをオンにしている環境では、チームを使うセッションもCode Modeで始まる。Code Modeはツール呼び出しをJavaScriptのコードで組み立てる実験的な方式であり、複数のツール結果を加工して次の呼び出しへつなぐような処理を扱いやすくする。単なるモデルの性能向上ではなく、ツール実行の組み立て方の変更だ。

同リリースでは`--allowedTools`、`--disallowedTools`、`--tools`に不完全なルールらしい値が渡されたとき、起動時に警告するようになった。管理者がセッション中に`managed-mcp.json`を追加した場合、MCPサーバーの読み込みが止まる理由を説明するメッセージも追加された。ツール許可は安全性と使い勝手の両方に影響するため、黙って設定を無視するより診断可能な動作が望ましい。

チーム機能とCode Modeを組み合わせると、作業を分担するエージェントが複数のツールを扱う場面が増える。ただし、ツール呼び出しの書き方が柔軟になることと、ファイル競合や権限昇格が自動的に防がれることは別問題だ。実験的機能の組み合わせは、実際のリポジトリでの再現性やログの読みやすさを確かめる必要がある。

**開発者目線:** 読み取り中心の小さなタスクからCode Modeとチームを試し、ツール許可の警告と実際の拒否動作を確認したい。書き込みを伴う場合はworktreeなどで作業領域を分離し、誰がどの変更を担当したか追跡できるようにする。

[公式出典](https://github.com/anthropics/claude-code/releases/tag/v2.1.326)

## 5. Claude Code 2.1.326、バックグラウンド実行と権限表示の不整合を修正

**公開情報：2026年11月16日前後｜公式一次情報**

Claude Code 2.1.326には長時間のバックグラウンド作業で見逃しにくい修正が多数入った。シェルから引き継いだLLMゲートウェイ設定がクラッシュ後や別ディレクトリからの再開時に失われると、従来は意図しない接続状態になり得た。今回の修正では、そのような状態でモデルへリクエストを送る前に処理を停止する。接続先の変更を黙認せず、安全側に倒す振る舞いだ。

さらに、バックグラウンドサービスが再利用されたプロセス番号を誤認し、別の利用者のSSHログインなどのプロセスを終了させてしまう問題を修正した。プロセスIDは時間が経つと再利用されるため、IDだけを長期間保持して停止対象を決める設計には危険がある。ツールの自動化がホストOSのプロセス管理に触れる以上、モデルの出力品質とは別にシステム側の堅牢性が重要になる。

権限面では、`/permissions`や`/add-dir`で保存した設定がファイル書き込み失敗時にも保存済みに見えてしまう問題を修正し、警告に対象ファイル名を出すようにした。PreToolUse hookが直接のツール呼び出しを拒否した際、OpenTelemetryの意思決定イベントや拒否数が残らない問題も修正された。実際に許可された操作と監査記録が食い違うと、運用中のトラブル分析が難しくなる。

**開発者目線:** 常駐エージェントやCIからClaude Codeを使う場合、更新後にゲートウェイ切断、権限ファイルの書き込み失敗、フック拒否を意図的に再現したい。失敗時に処理が止まり、利用者に理由が伝わり、ログに拒否が残ることまで確認して初めて運用品質を評価できる。

[公式出典](https://github.com/anthropics/claude-code/releases/tag/v2.1.326)

## 6. Wrangler 4.163.0、Build Output v1に生成元情報を記録

**公開情報：2026年11月16日前後｜公式一次情報**

Cloudflareは11月16日にWrangler 4.163.0を公開し、ビルド成果物の出力形式を更新した。`vite build`と実験的な`wrangler build --experimental-cf-build-output`は、Build Output v1を`.cloudflare/output/v1/`へ書き込む。ルートの`config.json`ではアカウント設定を`settings`の下に格納し、成果物を書いたツールを示す`producer`も記録する。単なるディレクトリ名の変更ではなく、生成側と利用側が共有するデータ契約の更新だ。

成果物を後段のプレビューやデプロイ処理が読み取る場合、出力フォーマットの世代差は互換性の問題になりやすい。今回の変更では、プレビュー側もアカウント設定の新しい場所を読むように更新された。生成元が記録されれば、複数のビルドツールが同じ成果物形式を扱うとき、エラー表示でどのツールが作成したかを説明できる。ビルドパイプラインを横断する診断情報として価値がある。

関連するcreate-cloudflare 2.74.13では、デプロイ後にWorker名を探す際、v1を優先しながらv0へのフォールバックを残した。移行期にツールのバージョンが揃わないことを前提にした対応だ。ただし、独自スクリプトが旧パスを直接参照している場合は、互換処理がないまま失敗する可能性がある。実験的なコマンドと通常のビルドの対応範囲も区別したい。

**開発者目線:** CIで`.cloudflare/output/v0/`を固定参照していないか検索し、v1とv0の両方を扱える移行期間を設けたい。成果物の生成元、設定の読み込み位置、プレビューと本番の差を検証してからビルドツールを一斉更新するのが安全だ。

[公式出典](https://github.com/cloudflare/workers-sdk/releases/tag/wrangler%404.163.0)

## 7. Cloudflare Workers、ArtifactsイベントからローカルWorkflowを起動

**公開情報：2026年11月16日前後｜公式一次情報**

Wrangler 4.163.0には、Artifactsイベントを使ってローカルのWorkflowを起動する変更も含まれる。`cloudflare.config.ts`の`exports.workflow({ name, events })`でイベントを宣言すると、cf、Vite、Workers Vitestのローカル環境で対応するWorkflowを動かせる。Wranglerの従来形式では引き続き`triggers.events`を利用する。設定の書き方が異なるため、同じ機能でもプロジェクト構成によって確認すべき場所が変わる。

ローカルのArtifacts namespaceが発行するのは、リポジトリの作成、インポート、fork、削除や、トークンの作成・失効などに関する`cf.artifacts.*`メッセージだ。作成・インポート・forkの成功時には初期トークン作成イベントも発行される。イベント配信は元の変更がコミットされた後に行われ、順序は保証されない。配信先が拒否しても元のリポジトリ操作は失敗しないという仕様は、イベント駆動設計で重要な意味を持つ。

注意点として、push、clone、fetchのイベントは現時点でローカル公開されず、ArtifactsからQueueへのローカル購読も提供されない。したがって、すべての本番イベントをローカルで再現できるわけではない。順序保証がないことを前提に、同じイベントを再処理しても壊れない冪等なWorkflowを設計する必要がある。

**開発者目線:** リポジトリ作成後の初期設定やトークン失効時の後片付けをローカルでテストしやすくなる。イベントを重複・逆順で投入するテストも用意し、イベント通知が失敗しても本体操作が成功するケースを観測できるようにしたい。

[公式出典](https://github.com/cloudflare/workers-sdk/releases/tag/wrangler%404.163.0)

## 8. Biome 2.6.8、Node Bufferと動的requireの危険な書き方を検出

**公開情報：2026年11月15日前後｜公式一次情報**

11月15日公開のBiome 2.6.8は、複数の新しいnurseryルールを追加した。`noBufferConstructor`は非推奨の`Buffer()`や`new Buffer()`を検出し、`Buffer.from()`、`Buffer.alloc()`など用途が明確なAPIへの移行を促す。古いBufferコンストラクタは渡す値の型によって振る舞いが変わるため、データから作るのか、サイズを指定して確保するのかを明示することが重要だ。

`noDynamicRequire`はモジュール名を実行時に組み立てる`require()`を検出する。オプションを有効にすると動的な`import()`も対象にできる。実行時の文字列から読み込み先を決める実装は、バンドラーが依存関係を静的に追跡しにくく、意図しないモジュールを読み込む余地を広げる場合がある。ただしプラグインローダーやロケール切り替えなど動的読み込みが必要な設計もあるため、機械的に禁止するのではなく用途を分類したい。

追加ルールはいずれもnurseryで、安定した既定ルールと同じ扱いではない。導入時は対象ルールを明示して、既存コードの検出件数や誤検知を見ながら段階的に適用するのがよい。自動修正を伴う変更では、元の実行時動作を保つかテストで確認する必要がある。

**開発者目線:** Node.jsの長寿命サービスではBufferの古いAPIを棚卸しし、依存ライブラリの警告と自前コードを分けて対処したい。動的requireはビルド対象、プラグイン境界、入力の検証方法を合わせて見直すと、静的解析と実行時の両方で予測しやすい構成になる。

[公式出典](https://github.com/biomejs/biome/releases/tag/%40biomejs/biome%402.6.8)

## 9. Biome 2.6.8、イベントと非同期処理の落とし穴を追加検出

**公開情報：2026年11月15日前後｜公式一次情報**

Biome 2.6.8の`noLateCurrentTargetAccess`は、ブラウザのイベント処理が終わった後に`event.currentTarget`を読むコードを検出する。例えばclickハンドラ内で`await save()`を挟み、その後に`event.currentTarget.disabled = false`とする書き方は危険だ。`currentTarget`はイベントを処理している間に意味を持つ値であり、非同期処理をまたいで同じ値が保持されるとは限らない。処理前に要素をローカル変数へ保存する方が意図が明確になる。

同じリリースの`noMisusedSpread`は、型情報を使って予期しないスプレッドを報告する。例えばPromiseを`{ ...getUser() }`で展開しても、非同期処理の結果のオブジェクトが得られるわけではない。文字列を配列へ展開する場合や、Map、関数、クラスなどをオブジェクトへ展開する場合も、期待したデータ構造と実際の値が違う可能性を指摘する。構文として合法でも意味がずれるコードを静的に見つける方向だ。

Vue向けには`noVueAsyncComputed`と`noVueDefineModelDefault`も追加された。computedに非同期処理を混ぜると依存追跡と結果のタイミングが複雑になり、defineModelのdefaultは親子の状態不一致を招く場合がある。いずれもnurseryルールなので、プロジェクトのフレームワークとコード規約に合うものを選んで試すのが適切だ。

**開発者目線:** 非同期イベント処理やPromiseのスプレッドはテストで見落としやすい。小さな再現コードを用意してルールの警告を確認し、lintを単なる書式統一ではなく実行時の意味の検証補助として使いたい。

[公式出典](https://github.com/biomejs/biome/releases/tag/%40biomejs/biome%402.6.8)

## 10. Next.js Canary 52、型生成の古い成果物とTurbopack永続化を修正

**公開情報：2026年11月15日前後｜公式一次情報**

11月15日UTC公開のNext.js 16.5.0-canary.52では、`next typegen`と`next build`が古い`.next/dev/types`を削除する変更が入った。開発時に生成された型定義が残ると、現在のルーティングや設定と食い違う診断につながり得る。生成ファイルは開発を助ける一方、更新や削除の責任が曖昧になると、ソースを修正してもエラーが消えないという分かりにくい状態を作る。

内部実装では、Turbopackのタスク依存関係をEdgeSetで保持する変更や、永続化データのブロック長をCRCの検査対象へ含める変更があった。CRCはデータの破損を検出するためのチェック値であり、長さ情報を含めることで破損の検出範囲を見直している。中間マージをまたいで使用中のキーを保持する変更も、キャッシュや永続化の整合性に関わる。リリースノートは一般的な速度向上率を示していないため、性能改善と断言すべきではない。

Canaryは安定版より先に変更を試すための系列であり、本番環境への即時適用を推奨する情報ではない。特にTurbopackのキャッシュに依存する開発サーバーでは、アップデート前後の初回起動、増分ビルド、ルート変更時の型生成を比較する価値がある。以前のCanary 50で紹介されたchunk分割やGCとは異なる、成果物の整合性に関する更新だ。

**開発者目線:** 型エラーが環境によって再現しない場合、`.next`を消すだけで済ませず、生成ファイルの寿命とビルド手順を確認したい。Canaryの検証ではキャッシュあり・なしの両方を測り、実装変更による効果とキャッシュの偶然を分離する。
