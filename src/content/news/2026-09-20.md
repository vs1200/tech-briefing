日曜なので大型発表は少なめですが、今日は **Agentの「モデル以外」の部分**がかなり面白いです。特にAWSの新Agent Runtime、Claude Codeの`AGENTS.md`対応、DoorDashが60,000個のFeature Flag整理をMulti-Agent化した実例は、実務へ持ち込みやすい話です。昨日扱ったJev、Plugin4Shell、Anthropicの3万Agent、npm Stage-only Tokenなどは外しました。

## 1. AWS AgentCore Runtime V2 — 2GB ContainerでもCold Start約2秒

[AWS公式：AgentCore Runtime V2](https://aws.amazon.com/about-aws/whats-new/2026/09/new-agentcore-runtime-generally-available/)

[AWS](https://aws.amazon.com/) が9月18日、Amazon Bedrock AgentCoreの次世代Runtimeを公開しました。

Agent SessionごとにHardware-isolatedなmicroVMを使いつつ、Memoryを必要に応じて増減し、不要になった分はSession終了を待たず回収します。さらにContainer Imageを一度準備してSnapshot化し、以後のInstanceはそこからRestoreします。([Amazon Web Services, Inc.](https://aws.amazon.com/about-aws/whats-new/2026/09/new-agentcore-runtime-generally-available/))

AWSの測定では、200MB〜2GBのContainerで**P75 Cold Startが1.9〜2.0秒**。V1では5.4〜30秒でした。東京リージョン`ap-northeast-1`でも利用できます。([Amazon Web Services, Inc.](https://aws.amazon.com/about-aws/whats-new/2026/09/new-agentcore-runtime-generally-available/))

**開発者目線:** Agentは普通のServerless Functionより「Shell + Filesystem + Dependenciesを持つ長時間Session」に近いので、Lambda的なRuntimeをそのまま流用しづらい。この**Agent専用microVM Runtime**というカテゴリは今後かなり重要になりそうです。

## 2. Claude Code 2.1.278 — Auto ModeのClassifierをServer側へ

[Claude Code Releases](https://github.com/anthropics/claude-code/releases)

Claude Code **2.1.278** が9月19日に公開されました。

Auto Modeで「この操作を自動許可してよいか」を判定するClassifierが、Claude API / Enterprise / Bedrock / Vertex / Foundryなどで**Server-side classifierをDefault利用**するようになりました。多くの場合Classifier分の追加課金がなくなります。`/status`から現在Server-sideかも確認できます。([GitHub](https://github.com/anthropics/claude-code/releases))

**開発者目線:** AgentのPermission判定そのものにもInference Costが掛かる、という2026年らしい問題への改善です。

長時間Agentでは、

`Tool実行 → safety判定 → Tool実行 → safety判定…`

が何百回も起こるので、**本体モデル以外の小さなInferenceをどう安くするか**も無視できなくなっています。

## 3. Claude Code、ついに`AGENTS.md`をそのまま読む

同じく9月18日のClaude Code **2.1.277**で、Projectに`CLAUDE.md`が存在しない場合、**`AGENTS.md`をProject Instructionsとして自動読込**するようになりました。([GitHub](https://github.com/anthropics/claude-code/releases))

これは小さな変更に見えますが結構重要です。

```text
AGENTS.md
   ├ Codex
   ├ Claude Code
   └ その他対応Agent
```

という共通Instruction Fileを持ちやすくなります。

**開発者目線:** Agentごとに、

`CLAUDE.md`
`CODEX.md`
`GEMINI.md`

のような同内容ファイルを維持する方向ではなく、**Vendor-neutralなProject Contextへ収束する兆候**です。

Coding Agentを複数併用するProjectなら、今後`AGENTS.md`中心に寄せる判断がかなりしやすくなりました。

## 4. DoorDash、60,000 Feature Flagsの掃除をMulti-Agent化

[DoorDash Engineering：Multi-Agent Feature Flag Cleanup](https://careersatdoordash.com/blog/automating-feature-flag-cleanup-at-scale-with-a-multi-agent-llm-system/)

DoorDash の実運用事例が今週Developer界隈で再び注目されています。

DoorDashには623 Repositoryに**60,000以上のFeature Flag**があり、毎月約2,300個増加。古いFlagを1個消すだけでも人間なら1〜2時間かかっていました。([DoorDash](https://careersatdoordash.com/blog/automating-feature-flag-cleanup-at-scale-with-a-multi-agent-llm-system/))

そこで、

`Experiment data取得`
→ `対象Code探索`
→ `Worktree作成`
→ `複数Agentで変更`
→ `Test / Validation`
→ `PR`

まで自動化。

直近50 Flagの評価では**45件でそのまま使えるPR**を生成し、平均13.8分・$4.79/Flagでした。人間が行うのは対象値の確認と最終Mergeです。([DoorDash](https://careersatdoordash.com/blog/automating-feature-flag-cleanup-at-scale-with-a-multi-agent-llm-system/))

**開発者目線:** Agentのかなり良い使い方です。

新Featureをゼロから作らせるより、**「正解条件が明確で、面倒で、Repository横断的」なMaintenance Task**は現在のCoding Agentと非常に相性が良い。自動化候補を探す際の参考になります。

## 5. Grabでは500以上の社内Agentを共通Platformへ統合

Grab の内部Agent Platform **LLM-Kit**も面白い実例です。

500以上のAgent Serviceが同じFrameworkを利用し、Model Gateway、Tracing、Evaluation、Secret Management、Tool Discoveryなどを共通化。50以上のMCP ServerからToolをRuntime Discoveryします。([InfoQ](https://www.infoq.com/news/2026/09/grab-agent-platform/))

結果として新しいAgent ServiceをProductionへ載せるまでが、**2週間以上 → 約1時間**まで短縮されたとしています。([InfoQ](https://www.infoq.com/news/2026/09/grab-agent-platform/))

**開発者目線:** Agent Loop自体はもう難しい部分ではない、という良い例です。

```text
while:
  model()
  tool()
```

より大変なのは、

**Secrets / Auth / Trace / Eval / Tool Registry / Deployment / Policy**

の方。

最近「Agent Harness」が注目されている理由がよく分かります。

## 6. GodotのRenderer最適化記事 — “GPUを見る前にCPU側の無駄を測る”

[Godot公式：Optimizing CPU-side Rendering Code](https://godotengine.org/article/rendering-cpu-optimizations/)

Godot Engine のRenderer Teamが、今年実施したCPU-side Rendering最適化の具体例を公開しています。

重要なのは「Renderer最適化 = Shader / GPU」ではないこと。Godotでは2D Batchingなど、**GPU側へ多少余分な仕事をさせてでもCPU Callを減らした方が全体では高速になる**ケースがあります。([Godot Engine](https://godotengine.org/article/rendering-cpu-optimizations/))

記事ではProfile → Bottleneck特定 → Data Structure / Call削減という実際の改善過程を解説しています。

**ゲーム開発目線:** Unityでもかなり共通する話です。

Draw Call数だけを見るのではなく、

> **CPU boundなのかGPU boundなのかを最初に判定する**

という基本が重要。ProfilerでRender Thread / Main Threadが詰まっているケースではShaderを弄ってもほとんど意味がありません。

## 7. visionOS 27、外部Accessoryを最大90Hzで直接Tracking

visionOS 27では新しいSpatial Accessories Frameworkにより、第三者製ControllerなどをVision Proで**最大90Hz Tracking**できるようになっています。PS VR2 Sense Controllerも対応対象です。([MIXED Reality News](https://mixed-news.com/en/visionos-27-vision-pro-spatial-accessories-90hz-ps-vr2-unity/))

Accessory側の6DoF PoseをApplicationへ渡せるため、従来のHand Trackingだけでは難しかった低LatencyなGame Inputが可能になります。

**Unity / XR開発目線:** Vision Proを「Hand Tracking中心のSpatial App端末」から、**普通のVR Game Controllerを扱えるXR Platform**へ近づける変更です。

Unity XR側の対応が成熟すれば、既存VR GameのPortabilityにも影響しそうです。

## 8. Go 1.27、小さいHeap Allocationを20〜30%高速化

[Go公式：Size-Specialized Memory Allocation](https://go.dev/blog/size-specialized-allocations)

Go TeamがGo 1.27で入ったAllocator改善の詳細を公開しました。

80 byte以下のHeap Allocationについて、従来の汎用`mallocgc`だけでなく**サイズ特化したAllocation Function**をCompilerが利用します。個々のAllocationは約20〜30%高速化し、Allocation-heavyなProgram全体では最大約1%の改善になるとしています。([Go](https://go.dev/blog/size-specialized-allocations))

**開発者目線:** 1%という数字は地味ですが、Runtime改善なのでApplication Codeを一切変えず全Go Serviceへ効きます。

そして設計として面白いのは、巨大なAllocatorを書き直すのではなく、**CompilerがSizeを知っているケースだけFast Pathへ逃がす**こと。Runtime Optimizationの良い読み物です。

## 9. RustFS 1.0 — MinIO後の「完全OSS S3互換Storage」候補

RustFS **1.0** がGAしました。

Rust製のDistributed Object Storageで、S3-compatible APIを提供し、Apache 2.0で公開されています。([Linuxiac](https://linuxiac.com/rustfs-1-0-s3-compatible-object-storage-reaches-ga/))

注目されている背景には、MinIOのOpen-source製品のMaintenance終了とCommercial版のProprietary化があります。その空白を狙った**Self-hosted S3 Alternative**という位置付けです。([Linuxiac](https://linuxiac.com/rustfs-1-0-s3-compatible-object-storage-reaches-ga/))

**開発者目線:** S3 APIはCloud Storageというより、今や事実上のObject Storage Protocolです。

Local / On-premiseで、

`AWS SDK → S3-compatible endpoint`

を維持したい場合の新しい選択肢として、今後のProduction実績を追う価値があります。

## 10. 小ネタ：Deno公式サイトが「人間向けInstall」よりAgent向けInstructionを置き始めた

[Deno公式](https://deno.com/)

Deno の現在の公式サイトには、通常のInstall Commandと並んでかなり象徴的な項目があります。

**“Or let your agent do it”**

として、Claude Code / Codex / Gemini CLI / OpenCode / Cursor / Piなどへ、

> `Read deno.com/agents.md and set up Deno in this project`

と渡すだけの導線を公式に用意しています。([Deno](https://deno.com/))

**開発者目線:** 昨日までのUnity Pluginとも同じ流れです。

これまでDeveloper Platformの入口は、

`README / Quick Start / SDK docs`

でした。

これからは、

`README for humans`
**`AGENTS.md / skills for coding agents`**

をVendor自身が提供するのが普通になりそうです。

「AIが古いBlogを検索して間違える」より、**公式がAgent-readableな最新手順を配る**方が圧倒的に健全です。

## 👀 今日ならこの3つ

一番実務に持ち込みやすいのは **DoorDashのFeature Flag Cleanup**です。45/50という成功率も興味深いですが、「Agentに何を任せるべきか」という意味で、**大量・反復的・Repository横断・機械的にValidation可能**というTask選定が非常に参考になります。([DoorDash](https://careersatdoordash.com/blog/automating-feature-flag-cleanup-at-scale-with-a-multi-agent-llm-system/))

Agent Infrastructureでは **AgentCore Runtime V2**。Container Sizeが200MBでも2GBでもCold Start約2秒というSnapshot方式は、長時間AgentをServerlessで動かすRuntime設計として面白いです。東京リージョン対応なのも実用上うれしいところです。([Amazon Web Services, Inc.](https://aws.amazon.com/about-aws/whats-new/2026/09/new-agentcore-runtime-generally-available/))

そして地味ながら今後効きそうなのが **Claude Codeの`AGENTS.md`対応**。CodexとClaude Codeの両方を使うProjectなら、Vendor固有Instructionを重複管理せず、**Project固有のAgent Rulesを一つのFileへ寄せる**運用が現実的になってきました。([GitHub](https://github.com/anthropics/claude-code/releases))
