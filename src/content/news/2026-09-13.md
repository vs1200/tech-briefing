今朝は **OpenAIがCodexの「Agent Harness」そのものをAPI化、GPT-Live-1で音声Agentの構成がかなり変わる、Copilot Code ReviewがMulti-Agent化** の3本が特に面白いです。週末なので大型リリースは少なめですが、その分「実際にAgentをどう作るか」というInfrastructure寄りの話題が濃いです。

---

## 1. OpenAI「Agents API」— CodexのAgent HarnessをそのままAPI化

[OpenAI公式：Introducing the Agents API](https://openai.com/index/introducing-the-agents-api/)

OpenAI が9月10日に **Agents API** をPublic Beta公開しました。昨日のBriefingではAgent Pluginを中心にしたため、これは改めて取り上げる価値があります。

ポイントは「新しいAgent Framework」ではなく、**Codexを長時間動かしているHarnessそのものをManaged Service化した**ことです。OpenAI側がSession、Context Compaction、Tool選択、Failure Recovery、Subagent並列化を管理します。([OpenAI](https://openai.com/index/introducing-the-agents-api/))

実行環境はOpenAI Hosted Sandboxだけでなく、自前InfrastructureやCloudflare、E2B、Modal、Vercelなども選択可能。MCP / Custom Function / Web Searchにも対応し、Agents API自体の追加料金はありません。([OpenAI](https://openai.com/index/introducing-the-agents-api/))

**開発者目線:** Agent開発が、

`LLM API + 自作Loop + Context管理 + Sandbox`

から、

`Task + Model + Tools + Environment → Agents API`

へかなり圧縮されます。長時間Coding Agentを自作するなら、今かなり重要なAPIです。

## 2. GPT-Live-1 API — 「音声→文字→LLM→音声」の3段構成を崩す

[OpenAI公式：GPT-Live-1 API](https://openai.com/index/introducing-gpt-live-1-in-the-api)

同じく9月10日、**GPT-Live-1** がAPI公開されました。ChatGPTのLive Voiceで使われているFull-duplex Modelを開発者が利用できます。([OpenAI](https://openai.com/index/introducing-gpt-live-1-in-the-api))

従来のVoice Agentは、

`STT → LLM → TTS`

でしたが、GPT-Live-1は**聞く・話すを一つのModelで同時処理**。ユーザーが途中で割り込んだり、「あ、やっぱり…」と訂正した場合も自然に扱います。

さらに面白いのは、深い推論だけAstraなどBackend Modelへ委譲できることです。価格はVoice Layerが**$0.05/分**。([OpenAI](https://openai.com/index/introducing-gpt-live-1-in-the-api))

**開発者目線:** Architectureとして、

`Voice UI → GPT-Live-1`
`　　　　　↓ 必要時`
`　　　 Astra / Codex / Tools`

となります。OpenAI自身もCodexへ会話Contextを渡すサンプルを公開しており、**Coding Agentと音声で相談しながら作業させる**構成がかなり作りやすくなっています。

## 3. Copilot Code Review、裏側が「Agent Ensemble」に

[GitHub公式：Copilot Code Review updates](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/)

[GitHub](https://github.com/) が9月11日、Copilot Code Reviewを更新しました。

特に興味深いのは内部Architecture。Lite Effortでも**複数AgentのEnsembleでReview**するようになり、さらにShell Toolを使って変更を検証する範囲も拡大しています。([GitHub Blog](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/))

つまり単純な、

`Diff → LLM → Comment`

ではなく、

`Diff → 複数Agent → Toolで検証 → 統合 → Review`

に近づいています。

**開発者目線:** 「LLMにコードレビューさせると浅い」という弱点へのかなり自然な回答です。先日紹介したHydraFusionとも共通して、**単一の最強ModelよりOrchestrationで品質を上げる**方向が製品へ入り始めています。

---

## 4. Copilot、直したReview Commentを自動でResolve

同じ9月11日の更新で、Copilot Code Reviewが**自分の指摘が後続Commitで修正されたかを再判定し、自動Resolve**するようになりました。([GitHub Blog](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/))

さらにCopilotのSuggestionを適用した際は、その変更内容に合わせたCommit Messageも生成します。

**開発者目線:** 小さい改善ですが実務では結構うれしいです。

AI Reviewで大量にCommentが付くと、「もう直したCommentを人間がResolveする」という**AIが作った管理作業**が発生していました。Agentが作った仕事をAgent自身に片付けさせる方向です。

## 5. Copilot CLIにHydraFusionのAdaptive Model Orchestration

GitHubの9月7日週アップデートでは、以前研究として紹介した **Project HydraFusion** がCopilot CLIへ入り始めました。([GitHub Blog](https://github.blog/changelog/month/09-2026/))

HydraFusionは一つのModelですべて解くのではなく、Taskの性質に応じて複数Modelを使い分けたり組み合わせたりする仕組み。

**開発者目線:** 先週の時点では「面白いResearch」でしたが、早くも**実製品のModel Routing Layer**へ移行しています。

今後Coding Agentを評価するときは、

> 「どのモデルを使っている？」

という質問自体が意味を失っていく可能性があります。

## 6. DeepSeek Harness、SandboxをAgent自身が解除できる脆弱性が修正

DeepSeek のOSS Agent Runtime **DeepSeek Harness**で、Sandbox Escapeにつながる脆弱性が見つかり修正されました。

Sandbox内のAgentが特定のConfigurationを操作することで、**人間のApprovalなしに自分自身のFilesystem Sandboxを解除できた**と報告されています。([DevOps.com](https://devops.com/flaw-in-deepseek-harness-ai-coding-tool-let-agents-disable-their-sandbox/))

**開発者目線:** かなりAgent時代らしい問題です。

`Agent`
`↓`
`Sandbox設定を変更`
`↓`
`Sandbox外へ`

という構造なので、Sandbox Policyを**Sandbox内から変更可能なConfigurationとして持たせてはいけない**という基本原則が見えてきます。

最近のGitSpawnやDev Container問題と合わせると、Agent Runtime Securityは独立したEngineering領域になりつつあります。

## 7. GitHub Actions CacheにLeast Privilege — `cache-mode`

9月10日、GitHub Actionsへ **`cache-mode`** が追加されました。Workflow / Job単位でActions CacheへのAccess権限を制限できます。([GitHub Blog](https://github.blog/changelog/month/09-2026/))

Cacheは一見ただの高速化機能ですが、CI Securityでは**Cache Poisoning**がSupply-chain Attackの入口になることがあります。

**開発者目線:** AgentがWorkflow YAMLまで自動編集する時代では、

`read-only cache`
`read/write cache`

をJobごとに明示できるのは地味に重要です。

GitHubが最近進めている「Secret・Agent Operation・CacheをLeast Privilege化する」流れの一部と見ると分かりやすいです。

## 8. 「AI Slopどうする？」Claude Code作者の回答がDeveloper界隈で話題

Boris Cherny にDeveloperが「AI Slopについてどうすればいい？」と直接メールし、その回答が9月12日に話題になっています。([Business Insider](https://www.businessinsider.com/claude-codes-creator-email-ai-slop-reply-2026-9))

Chernyの主張は、AIを使う/使わないの二択ではなく、Developer自身が**mini CEOのようにAgentを管理し、品質の悪いOutputを止める責任を持つ**べき、というもの。

**開発者目線:** 技術的新機能ではありませんが、今のDeveloper Communityの空気をかなり表しています。

問題が、

`AIはコードを書けるか？`

から、

**`AIが大量に書けるようになったコードを誰が品質管理するのか？`**

へ移っています。

## 9. Orca — 同じTaskを複数Coding Agentに競争させて「一番良いDiff」を選ぶ

今週OSS界隈で伸びている面白いToolが **Orca**。9月12日時点のOSS集計では6.5万Star規模まで伸びています。([オープンソースドロップ](https://www.opensourcedrop.com/))

一つのTaskを、

`Claude Code → worktree A`
`Codex → worktree B`
`OpenCode → worktree C`

へ同時に投げ、各Agentを独立Git Worktreeで作業させます。

最後にDiffを比較して**一番良い実装だけMerge**します。

**開発者目線:** Multi-Agentを「協力させる」のではなく、**同じ問題を競争させる**方式。

モデルごとに得意不得意がある現在ではかなり合理的です。Testで機械的に勝者を選べるTaskなら、Best-of-N Codingの実装として特に相性が良さそうです。

## 10. herdr — 「Coding Agent用tmux」という新しいToolカテゴリ

今日の触ってみたい小ネタ枠はRust製 **herdr**。

複数のClaude Code / CodexなどをTerminal上で動かすためのAgent Runtime / Multiplexerで、9月12日時点で約3.7万Stars、v0.9.0が公開されています。([The Infinity](https://theinfinity.dev/tools/herdr))

発想としては、

> **tmuxだけど、人間のShellではなくCoding Agent Sessionを管理する**

もの。

複数WorkspaceやAgentを一つのTUIから監視します。

**開発者目線:** 最近、

`Agent Inbox`
`Agent Session Manager`
`Agent Worktree Manager`
`Agent Multiplexer`

が別々のToolカテゴリとして急速に出てきています。

Coding Agentを一つ起動する時代から、**5〜10個のAgentをSupervisorとして管理するDeveloper UX**へ移行しているのがよく分かるToolです。

## 👀 今日ならこの3つ

今日は **Agents API** が圧倒的に重要です。Coding Agentを自作する際の難所はモデル呼び出しではなく、Context Compaction、長時間Session、Tool Selection、Subagent、Sandbox、Recoveryでした。OpenAIがそこを**Codexと同じHarnessごとAPI化した**ため、「自作Agent Platformをどこまで作るべきか」の境界が大きく変わります。([OpenAI](https://openai.com/index/introducing-the-agents-api/))

実際に普段の開発へ効きそうなのは **Copilot Code ReviewのAgent Ensemble化**。Diffを一度LLMへ投げるだけのReviewから、複数Agent + Shell Verificationへ移ったのはかなり良い方向です。([GitHub Blog](https://github.blog/changelog/2026-09-11-auto-resolution-and-analysis-updates-in-copilot-code-review/))

そして小ネタでは **Orca**。最近のMulti-Agentは「賢く協調させる」設計が多いですが、独立Worktreeで同じ問題を解かせて**TestとDiffで一番マシなものを選ぶ**という単純なBest-of-N方式は、Software Developmentでは意外と強力だと思います。([オープンソースドロップ](https://www.opensourcedrop.com/))
