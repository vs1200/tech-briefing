週末明けなので「新しい巨大モデル」より、**Agentを実運用するための周辺技術**が目立ちます。今日は **OpenClawのLive Plugin、CodeRabbitのPR Triage、runtime-resident npm malware** が特に面白め。ゲーム開発では CD Projekt がなぜ自社Engineを捨ててUnrealへ移ったのかという話が出ています。昨日まで扱った`AGENTS.md`、AgentCore V2、DoorDash Multi-Agentなどは外しました。

---

## 1. OpenClaw 2026.9.5 — Pluginを再起動なしで差し替えるAgent Runtimeへ

OpenClaw **2026.9.5** が9月19日に公開されました。

今回面白いのはModelではなくRuntime。Pluginを追加・更新してもGatewayを再起動する必要がなくなり、**実行中AgentへPluginをLive Load**できます。Update自体もAtomic化され、切替前に新Versionを検証します。さらにGPT LiveをMeeting / Phone Callへ組み込めるようになっています。([iHeartGeek](https://tech.iheartgeek.com/news/openclaw-2026-9-5-release))

**開発者目線:** Agent Runtimeが普通のApplication Serverに近づいています。

`Agentを停止 → plugin更新 → restart`

ではなく、

`running agent → plugin hot swap`

になると、長時間稼働するPersonal Agentや社内Agent Fleetを運用しやすい。Agent Pluginが増えてきた今、**Plugin Lifecycle Management**自体が新しいInfrastructure領域になりそうです。

## 2. CodeRabbit Triage — AI Reviewの次は「PRを読むべき順番」をAIが決める

[CodeRabbit Triageの解説](https://futurumgroup.com/insights/coderabbit-triage-fixing-the-pr-inbox-that-cries-wolf/)

CodeRabbit が9月18日に **Triage** を公開しました。

大量のPRを単純にAI Reviewするのではなく、

**CI失敗 / Merge conflict / Dependency / Reviewer state / Risk**

などを使って、「今、人間が見る価値のあるPR」を分類・優先順位付けします。([Futurum](https://futurumgroup.com/insights/coderabbit-triage-fixing-the-pr-inbox-that-cries-wolf/))

**開発者目線:** AI Code Reviewが普及すると逆に、

> AI CommentとPRが多すぎて何を見ればいいのか分からない

という問題が出ます。

これはAIを**コードを書く側ではなく、人間のAttentionを割り振るScheduler**として使う例。かなり実務的です。

## 3. npm Malwareが進化 — `postinstall`を禁止しても安全ではない

JavaScript Developerには今日一番注意したい話です。

Checkmarxが発見した悪意あるnpm Package **`indexed-btree`** は、従来のSupply-chain Malwareと違って`preinstall` / `install` / `postinstall` Scriptを使いません。

代わりに**Library本体のRuntime CodeへMalwareを埋め込み、ApplicationからImportされたときに動作**します。([Shield53 Threat Wire](https://news.shield53.org/runtime-resident-npm-malware-signals-a-dangerous-shift-in-supply-chain-attacks/))

これは正規Package`sorted-btree`へのTyposquattingです。

**開発者目線:** npmが進めてきた、

> lifecycle scriptをDefaultで実行しない

という対策をそのまま回避できます。

今後は、

`install時の挙動`

だけでなく、

**`dependencyがRuntimeで何をするか`**

を見る必要があります。SBOM / Lockfile / Provenanceに加えてRuntime Egress監視の重要性が上がりそうです。

## 4. Supply-chain攻撃「TeamPCP」へGoogle社員が潜入していた

[Wiredによる詳細レポート](https://www.wired.com/story/an-undercover-google-analyst-infiltrated-a-notorious-supply-chain-hacking-gang)

[Google](https://www.google.com/) Threat IntelligenceのAnalystが、大規模Supply-chain攻撃Group **TeamPCP**へUndercoverで潜入していたことが明らかになりました。

TeamPCPは数百のOSS Toolを侵害し、自己増殖するMini Shai-Huludなどを利用。最終的に**50万件以上のCredential**が盗まれたとされています。Google側は内部Communicationをリアルタイム観測し、Credential失効やProviderへの警告を行いました。([WIRED](https://www.wired.com/story/an-undercover-google-analyst-infiltrated-a-notorious-supply-chain-hacking-gang))

**開発者目線:** 面白いのはCybersecurity側が、

`検出 → Block`

だけでなく、

**`攻撃Infrastructureへ入り込んで事前に妨害`**

する方向へ移っていること。

今年npm Supply-chain事故が異常に多い背景を理解するうえでも興味深いケースです。

## 5. CD Projekt「REDengineを捨てたのはCyberpunkの失敗が理由ではない」

CD Projekt の共同CEO Michał Nowakowskiが、The Witcher IV でREDengineから Unreal Engine 5 へ移行した理由について改めて説明しています。([PC Gamer](https://www.pcgamer.com/games/the-witcher/cd-projekt-says-abandoning-its-in-house-engine-for-the-witcher-4-had-nothing-to-do-with-cyberpunk-2077s-technical-woes-the-dream-of-the-company-was-actually-never-to-make-technology/))

Cyberpunk 2077の技術問題が直接の理由ではなく、

> **会社の夢はTechnology Companyになることではなく、Storyを作ることだった**

という判断。

自社Engineを維持するEngineering CostをStory / Gameplayへ振り向けるため、Epicとかなり深い共同開発関係を結んでいます。([PC Gamer](https://www.pcgamer.com/games/the-witcher/cd-projekt-says-abandoning-its-in-house-engine-for-the-witcher-4-had-nothing-to-do-with-cyberpunk-2077s-technical-woes-the-dream-of-the-company-was-actually-never-to-make-technology/))

**ゲーム開発目線:** Engine内製 vs Unity / Unreal採用の典型的な判断材料です。

Engineを持つと自由度は最大になりますが、

**Engine Engineerを何百人も維持すること自体が会社のCompetitive Advantageなのか？**

という問いが出る。

Unityを使うStudioにもそのまま通じる「Build vs Buy」の話です。

## 6. 「AIを導入した企業の30%でProductivityが逆に低下」という調査

Agent導入に少し冷水を浴びせる話。

McKinseyの調査を引用した報道によると、Agentic AIを導入した企業の一部では、期待したProductivity向上どころか**約30%でProductivity低下**が報告されています。([The Times of India](https://timesofindia.indiatimes.com/business/international-business/productivity-decline-in-30-of-companies-using-agentic-ai-mckinsey-report/articleshow/134364085.cms))

理由として、Agent OutputのReview、修正、Workflow再設計などの追加Costが挙げられています。

またMIT Sloanが紹介した別研究でも、DeveloperはAI利用時に**コード量自体は増える一方、最終的なRelease量は同じ割合では増えていない**という結果があります。([MIT Sloan](https://mitsloan.mit.edu/ideas-made-to-matter/ai-boosts-worker-productivity-does-translate-to-final-outputs))

**開発者目線:** かなり重要です。

測るべきなのは、

`lines of code ↑`

ではなく、

**`Lead time ↓ / bugs ↓ / shipped value ↑`**

です。

Agent導入のKPIを「生成コード量」にすると、むしろ悪いOptimizationが起きます。

## 7. GitHubも「Copilotを本当に使っているのか」をFeature単位で計測

[GitHub公式：Copilot impact dashboard](https://github.blog/changelog/2026-09-17-copilot-impact-dashboard-now-shows-feature-engagement/)

上の話とちょうどつながる更新です。

GitHubのCopilot Impact Dashboardが、単なるSeat数ではなく、

**Completion / Agent Edit / Code Review / Cloud Agent / CLI / Copilot App**

それぞれについて、過去28日で実際に使ったActive User数を表示するようになりました。APIにも同じDataが追加されています。([The GitHub Blog](https://github.blog/changelog/2026-09-17-copilot-impact-dashboard-now-shows-feature-engagement/))

**開発者目線:** 「Copilot Licenseを100人に配った」ではなく、

> **どのAI Workflowが実際に定着したか**

を測れるようになります。

今後はさらに、利用率ではなくPR Lead TimeやDefect Rateとの相関まで見るのが理想でしょう。

## 8. Serverpod App Studio — あえて「AIを内蔵しない」Flutter Builder

今日の変わり種です。

Serverpod App Studio がPublic Betaへ入り、macOSで利用可能になっています。

Visual Builder系Toolですが、特徴的なのは**AI Generatorを組み込んでいないこと**。生成物は通常のFlutter / Dart Projectで、Developerが普通に編集できます。([Pasquale Pillitteri](https://pasqualepillitteri.it/en/news/17077/serverpod-launches-app-studio-flutter-app-builder-no-ai))

**開発者目線:** 2026年は何でもAI化する方向なので、逆に面白い設計です。

`Visual tool → deterministic code`

までに責務を限定し、

`AI → Codex / Claude Code等を好きに使う`

という分離。

Developer Toolが独自AIを抱えるより、**Agent-readableな普通のProjectを出力する方がComposable**という考え方には一理あります。

## 9. OpenClaw周辺で見える「Agent Pluginを止めずに更新したい」という新問題

1番のOpenClaw更新は、もう少し広いトレンドとしても面白いです。

MCP / Skills / Pluginsが増えるにつれ、Agent Runtimeは、

```text
Model
 ├─ Skill
 ├─ MCP
 ├─ Plugin
 ├─ Memory
 └─ Credentials
```

という**動的なApplication Platform**になっています。

OpenClaw 2026.9.5ではPluginのHot Loadingに加えて、Atomic Self-updateも導入されました。([iHeartGeek](https://tech.iheartgeek.com/news/openclaw-2026-9-5-release))

**開発者目線:** Kubernetes以前のWeb Serverと似た段階に来ています。

今後必要になりそうなのは、

**Plugin Version Pinning / Rollback / Canary / Health Check / Permission Diff**

あたり。

Agent Platform EngineerというRoleが本当に成立しそうな領域です。

## 10. 今日のコミュニティ小ネタ：「Personal Brain」Hackathonが示すAgent Stack

今日9月21日、San Franciscoで **Battle of the Personal Brains** という5時間Hackathonが開催されます。

使われるStackがかなり2026年らしく、

**Cognee → Personal Memory**
**AWS Strands → Agent**
**Docker Sandbox → Execution**
**Bright Data → Live Web Data**

を組み合わせ、メール・Document・Meeting・Calendarなどを理解して実際にActionするPersonal Agentを作ります。約200人が参加予定です。([Hackathons USA](https://ushackathons.com/events/battle-of-the-personal-brains-hackathon))

**開発者目線:** 個々の製品よりStackの分離が面白いです。

2025年なら、

`LLM + Vector DB`

だったPersonal Assistantが、

```text
Memory
  ↓
Agent Runtime
  ↓
Sandbox
  ↓
Live Data / MCP
  ↓
Actions
```

という**明確なLayer構造**になっています。

Agent ArchitectureがかなりSoftware Engineeringらしくなってきました。

## 👀 今日ならこの3つ

今日は **OpenClaw 2026.9.5** が技術的には一番面白いです。Agentを長時間動かすと「Pluginを追加するたびAgentを再起動する」という普通のApplication Serverでは解決済みだった問題が再登場します。Hot Loading + Atomic Updateは、Agent RuntimeがToyからInfrastructureへ移る過程として注目したいです。([iHeartGeek](https://tech.iheartgeek.com/news/openclaw-2026-9-5-release))

すぐ実務へ効くのは **runtime-resident npm malware**。`ignore-scripts`を使っているからSupply-chain Attackは大丈夫、とは言えません。特にNode Applicationで外部通信可能なDependencyが多い場合、Runtime Egressまで含めたDefense-in-depthが必要です。([Shield53 Threat Wire](https://news.shield53.org/runtime-resident-npm-malware-signals-a-dangerous-shift-in-supply-chain-attacks/))

ゲーム開発では **CD ProjektのEngine判断**。自社Engineを捨てる判断を「技術力の敗北」ではなく、**Technology Ownershipが会社のCore Competencyなのか**というResource Allocationの問題として説明している点が、Engine選定を考えるうえで参考になります。([PC Gamer](https://www.pcgamer.com/games/the-witcher/cd-projekt-says-abandoning-its-in-house-engine-for-the-witcher-4-had-nothing-to-do-with-cyberpunk-2077s-technical-woes-the-dream-of-the-company-was-actually-never-to-make-technology/))
