## 1. Claude Haiku 5.5登場 — 100万入力Tokenがわずか$0.10に

**発表：10月7日｜AI・LLM**

[Anthropic](https://www.anthropic.com/) が **Claude Haiku 5.5** を正式リリースしました。

最も驚くのは価格です。10万Token以下の入力では、100万Tokenあたり**入力$0.10、出力$0.50**。Haiku 4.5と比較して単価が90%下がりました。

Anthropic公称では、Terminal-Bench 4.0が39.2%、FrontierCode 1.1が46.4%。Sonnet 5.5には及びませんが、小型モデルとしてはかなり強力です。推論のEffort調整にも対応しました。

さらにSonnet 5.5のCache Read料金も半額になり、一般的なAgent処理のコストが約20%低下するとしています。([Anthropic](https://www.anthropic.com/claude-haiku-5-5))

**開発者目線：** Coding AgentのSubagentや要約、Context圧縮、分類処理に非常に魅力的です。例えばSonnetに実装を任せ、Haikuに大量のファイル調査を任せる構成なら、品質を維持しながらコストを削減できそうです。

なお、[GitHub Copilot](https://github.com/features/copilot) にも同日追加されました。Pro、Businessなどで利用でき、順次展開中です。([The GitHub Blog](https://github.blog/changelog/2026-10-07-claude-haiku-5-5-in-github-copilot))

[Anthropic公式発表・性能比較](https://www.anthropic.com/claude-haiku-5-5)

## 2. Google × Unity、「文章からゲームを作る」PlaygroundとUnity Sparkを発表

**発表：10月7日｜ゲーム開発・Unity**

[Google](https://blog.google/) と [Unity](https://unity.com/) が、新しいゲーム制作プラットフォームで提携しました。

今回発表されたのは、性格の異なる2つの製品です。

**Google Playground** はブラウザ上で文章からゲームを作るサービス。ゲームルール、キャラクター、物理挙動などを自然言語で変更できます。制作したゲームはURLで共有でき、ランキングや一部ジャンルのマルチプレイにも対応します。

10月7日から米国の18歳以上向けに提供されています。

一方、**Unity Spark** はUnity Runtimeを利用する、より本格的なゲーム制作環境です。

- 高品質な3D表現
- Unity Asset Storeのクリエイター制作アセット
- ブラウザ上での編集と共同制作
- Google Playgroundへの公開

といった機能を目指しています。2026年後半にクローズドベータ開始予定で、現在は参加登録を受け付けています。([blog.google](https://blog.google/innovation-and-ai/technology/ai/playground-experimental-gaming-platform/))

**Unity開発者目線：** これは単なるAI機能追加より大きな話です。

Unityが従来の「ゲームエンジンを開発者に提供する会社」から、**制作環境と作品公開プラットフォームをセットで提供する方向**へ進んでいます。

ただし現時点では、Sparkのプロジェクトを通常のUnity Editorへ自由に移行できるかなど、重要な仕様が明確ではありません。

開発者コミュニティでも、公開デモのゲーム品質や独創性に対する厳しい意見が出ています。([Kotaku](https://kotaku.com/unity-spark-space-corridor-vibe-coding-ai-trailer-game-development-2000741912))

## 3. Microsoft eXecution Containers — Agentの権限をOS側から制限

**発表：10月7日｜AI Agent・Security**

[Microsoft](https://www.microsoft.com/) が **Microsoft eXecution Containers（MXC）** を発表しました。

Agentが実行するShell Command、Tool、Pluginなどを、OS側のSandboxで隔離する仕組みです。

特徴は、**Windows・macOS・Linuxで共通のポリシーを使える**こと。

例えば、

```text
Coding Agent
  ├─ ./repository   読み書き許可
  ├─ ~/.ssh         アクセス禁止
  ├─ ~/Documents    アクセス禁止
  ├─ npm registry   通信許可
  └─ その他の通信    禁止
```

のような制限を宣言できます。

内部ではWindows Sandbox、LinuxのBubblewrap、macOSのSeatbeltなど、環境に応じた隔離技術を使用します。([Windows Blog](https://blogs.windows.com/windowsdeveloper/2026/10/07/microsoft-execution-containers-policy-driven-containment-for-ai-agents/))

**開発者目線：** 今日最も重要な技術発表の一つです。

従来のCoding Agentは、実行権限を持つユーザーの権限を広く利用する構成が一般的でした。

MXCでは**Agent自身が変更できない場所に権限ポリシーを置く**ため、Prompt InjectionなどでAgentが意図しない操作を試みても、OS側で阻止できる設計です。

同日、GitHub CopilotのローカルSandbox機能もGAになりました。Copilot CLI、Copilot App、対応するVS Code環境で利用できます。([The GitHub Blog](https://github.blog/changelog/2026-10-07-local-sandboxing-for-github-copilot-now-generally-available/))

ただし、公開MXCリポジトリのコードはまだ初期Previewで、現段階では完全なセキュリティ境界として信頼しないよう注意書きがあります。独自組み込み時には重要な点です。([GitHub](https://github.com/microsoft/mxc))

[MXC公式GitHub](https://github.com/microsoft/mxc)

## 4. Windowsが「ローカルLLMとCloud LLMを自動で使い分けるOS」へ

**発表：10月7日｜Windows・Local AI**

MicrosoftがWindows向けに **Hybrid Intelligence** を発表しました。

これは、AI処理をすべてCloudへ送るのではなく、Taskに応じてローカルモデルとCloudモデルを使い分ける仕組みです。

例えば、

```text
簡単なコード修正 → Local LLM
要約・分類       → Local LLM
複雑な設計変更   → Cloud Frontier Model
```

のような振り分けを想定しています。

GitHub Copilotにも、この自動ルーティングを10月末までに導入する予定です。([Command Line](https://commandline.microsoft.com/local-models-sandboxed-tools-github-windows/))

同時に発表された **Surface Laptop Ultra** は、NVIDIA RTX Sparkを搭載し、最大128GBのUnified Memoryを備えます。

価格は$2,599から。10月16日発売予定です。([Windows Blog](https://blogs.windows.com/devices/2026/10/07/pre-order-our-most-powerful-surface-devices-ever/))

**開発者目線：** ローカルLLMが「Cloud APIの代替」から、**Cloudモデルと組み合わせる普通の実行環境**へ変わってきました。

今後Coding Agentを比較するときは、Model性能だけでなく、ローカルとCloudを切り替える判断の精度も重要になりそうです。

[Windows公式：Hybrid Intelligence](https://blogs.windows.com/windowsexperience/2026/10/07/building-windows-for-hybrid-intelligence/)

## 5. Mistral Large 4 — 1兆パラメータのOpen-weightモデルを予告

**発表：10月6日｜LLM・Open-weight**

[Mistral AI](https://mistral.ai/) が **Mistral Large 4**、通称 *Le Chonk* を公開Previewとして発表しました。

規模は非常に大きく、

**総パラメータ：約1兆**
**Active Parameters：約490億**
**Context Window：100万Token**

というSparse Mixture-of-Expertsモデルです。

Coding、Agent、画像理解、Cybersecurity、金融などを重視しています。

重要なのは、**現時点ではまだWeightが一般公開されていない**こと。API Previewは利用できますが、Weightの公開は10月下旬を予定しています。

Mistral公称では、欧州の自社データセンターにある約3,800基のNVIDIA Grace Blackwell GPUで学習しています。([Mistral](https://mistral.ai/news/mistral-large-4/))

**開発者目線：** 昨日まで紹介していたReflection Beamに続く、大規模Open-weightモデルの話題です。

ただし490億Activeでも、1兆パラメータ全体のWeightを保持する必要があります。**一般的なMacで手軽に動かせるモデルではありません。**

ローカル実行を考える場合は、Weight公開後の量子化や必要メモリを確認したいところです。

[Mistral Large 4公式発表](https://mistral.ai/news/mistral-large-4/)

## 6. Microsoft Agent Lightning 1.0 — 既存Agentを作り直さず強化学習

**技術解説公開：10月7日｜AI Agent・研究**

[Microsoft Research](https://www.microsoft.com/en-us/research/) が、Agent Lightning 1.0の設計を詳しく解説しました。

研究・実装自体は8月に公開されていますが、今回の技術記事はかなり読み応えがあります。

Agent Lightningは、**既存のAgent Harnessをそのまま強化学習へ利用する**ためのFrameworkです。

従来のAgent RLでは、Training Frameworkの内部へAgent Loopを再実装する必要がありました。

Agent Lightningでは、

```text
Existing Coding Agent
        ↓
     LLM Proxy
        ↓
   RL Training
        ↓
  Improved Model
```

という構成を採用します。

Agent Harnessを変更せず、LLM EndpointをProxyへ向けることで、実際のTool CallやContext Managementを含めて学習できます。

実験では約6,000件の学習サンプルを使用し、Qwen3.5-9BのSWE-bench Verified Pass@1を**41.8%から56.4%へ改善**しました。([Microsoft](https://www.microsoft.com/en-us/research/blog/agent-lightning-v1-0-a-3500-line-lightweight-agentic-rl-framework-for-training-agents-with-real-harnesses/?lang=zh-cn))

**開発者目線：** 特に面白いのは、Agentの性能を上げる対象がPromptやHarnessだけではなくなっていることです。

実際のCoding Agentが失敗したTaskを学習に戻し、**自分のHarnessに適応したモデルを育てる**方向です。

約3,500行という比較的小さな実装なので、Agent RLの仕組みを理解する教材としても良さそうです。

[Agent Lightning公式GitHub](https://github.com/microsoft/agent-lightning)

## 7. GitHub Copilot CLI、Ollamaのローカルモデルを自動検出

**発表：10月7日｜開発ツール・Local LLM**

これは小さいですが、かなり実用的な更新です。

[GitHub Copilot](https://github.com/features/copilot) CLIの**1.0.94-0**から、`/model`で起動中のOllamaにあるモデルを自動検出できるようになりました。

従来よりもモデルの切り替えが簡単になります。

```text
/model
  ├─ Cloud Models
  │    ├─ Claude
  │    └─ GPT
  │
  └─ Local Ollama
       ├─ model A
       └─ model B
```

検出したモデルを選び、そのSessionですぐ利用できます。CLIの再起動は不要です。

ただし、Ollamaとモデルの事前インストールが必要で、Tool CallingとStreamingに対応したモデルが対象です。

**注意点として、ローカルモデルの選択だけではOffline Modeになりません。** GitHub Telemetryを含む通信を制御するには別途設定が必要です。([The GitHub Blog](https://github.blog/changelog/2026-10-07-discover-local-models-in-github-copilot-cli))

**開発者目線：** ローカルモデルを試す際に、専用のAgent Harnessを新しく導入する必要が減ります。

Copilotの使い慣れた操作体系を維持したまま、Local Modelの品質を比較できるのが良いところです。

[GitHub公式Changelog](https://github.blog/changelog/2026-10-07-discover-local-models-in-github-copilot-cli)

## 8. GitHub、秘密情報の検出に専用AIモデルを導入

**発表：10月7日｜Security・Developer Tools**

[GitHub](https://github.com/) がSecret Scanning向けの専用AIモデルを発表しました。

従来のSecret Scanningは、API Keyなどの特徴的な文字列を検出する方式が中心でした。

今回のモデルは**周囲のコードも読んで秘密情報らしさを判断**します。

例えば、

```typescript
const servicePassword = "some-secret-value";
```

のように、決まったToken形式を持たないPasswordも検出対象になります。

今後はPush時の検出やCopilotの`/security-review`にも統合されます。なおPush ProtectionへのAI検出追加は現在Private Previewです。([The GitHub Blog](https://github.blog/changelog/2026-10-07-purpose-built-model-for-leaked-secret-detection/))

**開発者目線：** Coding Agentが`.env`や設定ファイルを変更する機会が増えた今、重要な改善です。

また、ここでも興味深いのは**生成AIではなく専用の分類モデル**を使っていること。

Agentを安全にするための処理までFrontier LLMへ任せず、特定用途のモデルで高速に判断する方向が進んでいます。

[GitHub公式：AI Secret Detection](https://github.blog/changelog/2026-10-07-purpose-built-model-for-leaked-secret-detection/)

## 9. Atlassian AMP — 人間とAgentが同じチームで働くための基盤

**発表：10月6日｜AI Agent・開発プロセス**

[Atlassian](https://www.atlassian.com/) が **Agentic Multiplayer Protocol（AMP）** を発表しました。

名前にProtocolとありますが、単純な通信仕様というより、**人間とAI Agentが同じ仕事を進めるための仕組み全体**を指しています。

AgentごとにIdentityと権限を与え、Jira、Confluence、Rovoなどで作業状況を共有します。

さらに興味深いのが、Teamwork Graphによるコード検索です。

GitHubやBitbucketのRepositoryを、関数・Class・Symbol単位まで検索し、Issueや設計上の判断と関連付けられます。

これによりCoding Agentは、

> 「この関数は何をしている？」

だけでなく、

> 「なぜこの設計になった？ 関連するIssueは？」

といった情報も取得しやすくなります。([Atlassian](https://www.atlassian.com/blog/company-news/team26-europe-ai-platform))

**開発者目線：** Agentに必要なのはコードだけではなく、**過去の意思決定や要求仕様を含むContext**だという考え方です。

特に長期運用のゲームでは、実装だけ見ても分からない仕様や例外処理が大量に存在します。

そうした情報をAgentが参照できるようにする仕組みは、実務への効果が大きそうです。

[Atlassian AMP公式紹介](https://www.atlassian.com/platform/agentic-multiplayer-protocol)

## 10. Silicon Labs、組み込み機器の開発までCoding Agentへ開放

**発表：10月7日｜IoT・Embedded・AI Agent**

最後は少し変わった分野のニュースです。

[Silicon Labs](https://www.silabs.com/) が **Simplicity AI SDK** のPublic Betaを開始しました。

これはCopilot、Cursor、CodexなどのCoding Agentから、Silicon LabsのSDKや開発ツールを利用できる仕組みです。

最初の対象はBluetooth Low Energyで、

**Project作成 → Build → Deviceへの書き込み → Debug → 消費電力解析**

まで扱えます。

さらに開発中の「Hardware Intent」では、回路図や仕様書を解析してPinの競合やPeripheral設定の問題を検出する機能も予定されています。こちらは2027年1月にAlpha版を公開予定です。([Embedded Computing Design](https://embeddedcomputing.com/technology/ai-machine-learning/ai-dev-tools-frameworks/silicon-labs-expands-ai-developer-platform-to-simplify-iot-development-and-scale-edge-intelligence))

**開発者目線：** Unityの公式Agent Skillsと同じ流れが、組み込み開発へ広がっています。

Agentがコードを書くだけでなく、**実機へ書き込み、動作を検証し、問題を修正する**ところまで扱うようになる。

Coding Agentの対象がソフトウェアからハードウェア開発へ拡張している好例です。

## 👀 今日ならこの3つ

**最も注目したいのはGoogle × UnityのPlayground / Unity Sparkです。** ゲームエンジンにAI機能を追加するだけでなく、制作から公開までの仕組みを作り直そうとしています。今後はゲームを作る人の裾野が広がる一方、生成されたゲームの品質や独創性をどう高めるかが課題になりそうです。

**すぐに実用上のメリットがありそうなのはClaude Haiku 5.5。** 100万入力Tokenが$0.10という価格なら、大量の軽量Subagentを使う設計の経済性が大きく変わります。Coding Agentの内部処理をどこまで小型モデルへ委譲できるか、試す価値があります。

**技術設計として最も重要なのはMicrosoft MXC。** Agentに与える権限をPromptやAgent FrameworkではなくOS側で制御する設計は、今後のCoding Agentで標準的になる可能性があります。特にローカルPCで複数Agentを並列実行する場合、ファイル・Credential・Networkの隔離は重要です。

### 今朝の全体傾向

今日のニュースを横断すると、3つの流れが見えてきます。

**AIモデルは役割分担が進み、Agentの実行環境はOSレベルで整備され、開発ツールはAgentを正式な利用者として扱い始めています。**

モデルの性能競争は続いていますが、それ以上に「モデルをどのような環境で、どんな権限を与えて、どう使い分けるか」が開発者にとって重要になってきています。
