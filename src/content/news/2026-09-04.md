今朝は **NVIDIAによるHugging Face買収、ローカルAIの分散実行、ゲーム開発Agent、CI/CDのAgent化** が特に面白いです。昨日まで扱ったFable 5.1 / Gemini 3.8 / GitSpawnなどは、続報が薄いものは外しています。

---

## 1. NVIDIA、Hugging Faceを約129億ドルで買収へ

今日最大のニュースです。NVIDIAが **Hugging Faceを129.3億ドルで買収**する計画を発表しました。NVIDIAはHugging Faceを引き続きオープンなプラットフォームとして運営し、NVIDIA以外のHardwareも選択可能にすると説明しています。([Reuters](https://www.reuters.com/business/nvidia-buy-hugging-face-nearly-13-billion-big-bet-open-ai-models-2026-09-03/))

Hugging Faceは単なるモデル配布サイトではなく、Model / Dataset / Inference / Libraryを含む**Open AI ecosystemの中心的インフラ**です。

**開発者目線:** NVIDIAはGPUだけでなく、ついに「開発者がOpen Modelを探して使う入口」まで握ることになります。CUDA最適化などがさらに便利になる一方、AMD・Apple・CPU向けモデルの中立性が維持されるかは継続して見たいポイントです。

## 2. NVIDIA PAIR — 家のPCをまとめて「ローカルAI Cluster」にする

9月3日、NVIDIAがOSSの **PAIR（Personal AI Router）** をBeta公開しました。

PAIRはOllama / LM StudioのInference Requestを、LAN上の複数PCへ自動的に振り分けます。Agent側はAPIを変更する必要がなく、対応するMacも **Apple M4以降** とされています。([NVIDIA Developer](https://developer.nvidia.com/blog/nvidia-pair-virtual-inference-router-expands-available-compute-on-your-local-network/))

NVIDIAの5-Subagentデモでは、単一RTX Sparkで18分だった処理が、RTX Spark + DGX Spark + RTX 5090の3台構成で**8分48秒**になりました。ただしNVIDIA自身も「構成依存の非公式デモであり一般Benchmarkではない」と明記しています。([NVIDIA Developer](https://developer.nvidia.com/blog/nvidia-pair-virtual-inference-router-expands-available-compute-on-your-local-network/))

**開発者目線:** これはかなり面白いです。

`Agent → Ollama API → PAIR → 空いているPC`

という構成で、**家に余っているPCをMulti-Agent用Computeとして使える**ようになります。VRAMを結合する仕組みではなく、独立したInference Callを分散する点には注意です。

## 3. OpenAI × Playco：AIがUnityを「編集→プレイ→テスト」する

OpenAIが9月3日、Playcoによる **GPT-6 Astraを使ったゲームPrototype開発**の事例を公開しました。

Playcoの「Playbot」はUnityやGodotへ直接接続し、AgentがSceneを編集するだけでなく、**ゲームを実行・操作・テストし、自分の変更を検証**できます。1つのGreyboxから3種類のTheme Prototypeを作り、Playcoによれば従来モデル比でManual Fixが50%減ったとのことです。([OpenAI](https://openai.com/index/playco-game-prototyping-with-astra/))

**Unity開発者目線:** 最近紹介したCompose MCPと同じ流れです。

`Agentがコードを書く`
↓
`Engineを操作する`
↓
`実際にプレイする`
↓
`見た目やGame Feelを判断する`
↓
`修正する`

ここまで回り始めると、Unity向けCoding Agentの価値が一段変わります。今日のゲーム開発枠では一番おすすめです。

## 4. TeamCity 2026.2 — CI/CDそのものをMCPから操作可能に

JetBrainsが **TeamCity 2026.2** を公開しました。Pipeline機能がGAになったほか、AI関連がかなり増えています。([The JetBrains Blog](https://blog.jetbrains.com/teamcity/2026/09/teamcity-20262/))

特にAgentから、

`teamcity_pipeline_get`
`teamcity_pipeline_post`
`teamcity_pipeline_delete`

をMCP経由で呼べるようになりました。変更・削除系は事故防止のため明示的に **Brave mode** を有効化する必要があります。OAuth/PKCEにも対応しています。([The JetBrains Blog](https://blog.jetbrains.com/teamcity/2026/09/teamcity-20262/))

さらにAI AssistantはBYOKに対応し、Anthropic / OpenAI / Geminiなど任意の対応Modelを利用できます。([The JetBrains Blog](https://blog.jetbrains.com/teamcity/2026/09/teamcity-20262/))

**開発者目線:** Coding AgentのToolが、

`Editor → GitHub → CI/CD`

までつながってきました。「AgentにPRを書かせる」の次は、**AgentがBuild Pipelineを調査・修正する**ところまで普通になりそうです。

## 5. Kotlin Toolchain 0.12 — Gradleの外側からKotlin Projectをシンプルに

JetBrainsの **Kotlin Toolchain 0.12** が9月3日に公開されています。Multiplatform Library Publishing、Wasm App Preview、CLIからCompose Hot Reloadなどが追加されました。([The JetBrains Blog](https://blog.jetbrains.com/category/releases/))

Kotlin Toolchain自体は、JVM / Android / iOS / Wasm / Multiplatformなどを簡潔なDeclarative Configurationで構築するAlpha段階の新Toolchainです。例えば最低限のJVM Applicationなら設定はほぼ `product: jvm/app` だけ、という思想です。

**開発者目線:** Kotlin界隈でも「巨大なBuild Scriptを手書きする」より、**高レベルなProject DefinitionからToolchainを生成する**方向が強くなっています。

AgentにProjectを操作させる場合も、複雑なGradle DSLよりこうした構造化設定の方が扱いやすそうです。

## 6. GitHub Copilot、Agentにも「このファイルは絶対読ませない」がGA

Copilot AppとCopilot CLIが、Enterprise / Organization / Repository管理者による **Content Exclusion Policy** を正式に尊重するようになりました。

除外されたFileはAgent Contextへ入りません。Copilot Business / Enterprise向けです。([The GitHub Blog](https://github.blog/changelog/2026-09-02-content-exclusions-generally-available-in-copilot-app-and-cli/))

**開発者目線:** IDE補完だけだった時代より重要度が上がっています。

AgentはRepository全体を探索するため、

`Secrets周辺`
`契約上外部AIへ送れないSource`
`Security-sensitive code`

などを**Agent Context Layerで禁止する**必要があります。

「AgentにはRepository Read権限を渡すけれど、このDirectoryだけは見せない」というPolicyがようやく現実的になっています。

## 7. GitHub Copilot、Teamごとに「標準モデル」を変えられる

GitHubはEnterprise Managed Settingsを拡張し、CopilotのDefault Modelを企業側から指定できるようにしました。さらにTeam Mappingを使って、**Teamごとに異なるDefault Model**を設定できます。([The GitHub Blog](https://github.blog/changelog/2026-09-02-enterprise-managed-settings-support-any-default-model/))

例えば、

`Backend → 高性能Coding Model`
`Documentation → 安価なFast Model`
`Security → 専用Model`

のような運用ができます。

**開発者目線:** この1週間ずっと見えている流れですが、Coding Agent運用が「好きなモデルを選ぶ」から、

**Task / Team / Costに応じたModel Policy**

へ進んでいます。

## 8. Rust 1.98.1、Miscompile修正のため緊急Point Release

Rust **1.98.1** が9月3日に公開されました。

1.98.0には、特定条件下でTrait Objectのvtableに本来Function Pointerが入る場所へNULLが生成される**Miscompilation Bug**がありました。Segfaultだけでなく、Undefined Behaviorになる可能性があります。([Rustブログ](https://blog.rust-lang.org/2026/09/03/Rust-1.98.1/))

Rust 1.98.0を使っている場合は、

`rustup update stable`

で更新できます。([Rustブログ](https://blog.rust-lang.org/2026/09/03/Rust-1.98.1/))

**開発者目線:** 普通の「細かいBug Fix」ではなくCompilerが誤ったMachine Codeを生成する種類なので、1.98.0を導入済みならアップデート優先度は高めです。

## 10. Microsoft Execution Containers — Agent専用Sandbox Layerが育っている

今日の「追っておきたい小ネタ」。

MicrosoftのOSS **MXC（Microsoft eXecution Container）** は、AI Modelの出力・Plugin・ToolなどのUntrusted CodeをWindows / Linux / macOSで実行するためのCross-platform Sandboxです。OS Native SandboxからVMまでを同じJSON Configuration / TypeScript SDKで扱う設計になっています。([GitHub](https://github.com/microsoft/mxc))

ただし現時点では**Early Preview**で、Microsoft自身も「現在のProfileをSecurity Boundaryとして扱うべきではない」と警告しています。([GitHub](https://github.com/microsoft/mxc))

**開発者目線:** GitSpawnのような問題を見ると、

`Agent → Shell`

の間へSandbox Runtimeを挟むことはほぼ必須になりそうです。

Dockerを無理やりAgent Sandboxとして使うのではなく、**Agent Code Execution専用の標準Layer**が育っているのは注目しておきたいです。
