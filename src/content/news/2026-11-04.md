## 1. DependabotがAgent Package Managerに対応 — AI指示も依存更新の対象へ

**11月3日公開｜技術アップデート**

11月3日、GitHubはDependabotのバージョン更新対象にAgent Package Manager（APM）を追加した。APMはAIエージェントが使うSkill、Prompt、Instructionを依存物として管理する仕組みだ。これまでエージェント向け指示はMarkdownをコピーして置きっぱなしにしやすく、上流で改善や修正が入っても各リポジトリに伝わらない問題があった。今回の対応は、AIの振る舞いを決めるファイルにも通常のソフトウェア依存と似た更新経路を用意するものだ。

Dependabotは`apm.yml`で宣言された対応Git依存を検出し、更新Pull Requestを作る。`apm.lock.yaml`が存在すればロックファイルも再生成する。導入時は`.github/dependabot.yml`へ`apm`のエントリを追加し、定義ファイルがあるディレクトリと更新スケジュールを指定する。GitHub.comの全プランで一般提供され、GitHub Enterprise Serverでは3.24に入る予定だ。ただし現時点で対応するのはバージョン更新であり、セキュリティアラートや脆弱性修正の自動検知ではない。 [公式出典](https://github.blog/changelog/2026-11-03-dependabot-version-updates-support-agent-package-manager/)。

指示ファイルの更新はアプリケーションのライブラリ更新と異なり、同じテストが通ってもエージェントの判断を変える可能性がある。たとえばコードレビューの観点が増えたり、外部ツールの使用方針が変わったりすると、従来の実行結果との比較が必要になる。依存の出所と更新差分をレビューする工程を維持することが重要だ。

**開発者目線:** APM導入の効果を確かめるなら、更新PRでSkillの差分を読み、固定されたタスク集合に対するエージェントの出力を比較するとよい。セキュリティ更新が自動で保証されると誤解せず、外部リポジトリの信頼性確認も別に続けたい。

## 2. CopilotがJetBrains Airへ統合 — ACPでローカルとクラウドを切り替え

**11月3日公開｜技術アップデート**

11月3日、GitHub CopilotをJetBrains Airのエージェント選択画面から利用できるようになった。統合にはAgent Client Protocol（ACP）が使われる。これはエージェントと操作画面の接続を標準化する方向性を示すもので、IDEに組み込まれた単一のチャットだけでなく、複数のエージェント作業を並行して管理する体験につながる。既存のGitHub Copilotサブスクリプションで利用する点も特徴だ。

ローカルタスクはJetBrains IDEにAirを導入し、Copilotアカウントを接続して開始する。クラウドタスクはAir Teams対応のビジネス組織、Copilot契約、管理者による有効化が必要になる。クラウド実行では新しい仮想マシン上のDockerコンテナが使われ、通信はプロキシを通り、タスク間で状態を引き継がない。ローカル環境を変更せずに依存導入やテストを試せるが、手元の未コミット差分が自動で共有されると考えるべきではない。 [公式出典](https://github.blog/changelog/2026-11-03-github-copilot-is-now-available-in-jetbrains-air/)。

運用面には制約がある。個々のタスクで個人契約と組織契約のどちらを使うかは選べず、Air側のガバナンス・分析にはCopilotの利用量が含まれない。管理者はCopilotの使用を禁止できる一方、Air内でCopilotの支出上限を設定できない。プロトコル統合と課金統合は別問題であることがよく分かる。

**開発者目線:** 複数エージェントを使う開発チームでは、ACPによって画面の選択肢が増える一方、実行場所・権限・請求の可視化を別途設計する必要がある。試験導入では同じタスクをローカルとクラウドで実行し、成果物の差分、秘密情報へのアクセス、費用の追跡可能性を確認したい。

## 3. CodeQL 2.27.3 — Python 3.15とAI入力の独自脅威モデルを追加

**11月3日公開｜技術アップデート**

11月3日に案内されたCodeQL 2.27.3は、GitHubのコードスキャンで利用する静的解析エンジンの更新だ。Python 3.15の新構文に加え、C23のビット精度整数、C#の位置パターンにおけるデータフローなど、言語の進化に追随した。静的解析では構文を解析できるだけでは不十分で、入力値がどこから来てどこへ到達するかを正しく追えることが検出精度を左右する。

注目は、LLMが生成したデータを想定する`ai`脅威モデルがオプトインで追加された点だ。初期状態でAI由来の入力ソースが自動登録されるわけではなく、利用者がデータ拡張でソースを定義する必要がある。データ拡張には従来のYAMLに加えてJSON構文を使えるようになり、JSONではJavaScript形式のコメントも許容される。拡張子に応じてパーサーが切り替わるため、生成ツールで拡張ファイルを作る構成も選びやすい。 [公式出典](https://github.blog/changelog/2026-11-03-codeql-2-27-3-adds-python-3-15-features-and-json-data-extensions/)。

解析の精度改善も実務的だ。C#の真偽式簡略化は型情報が不足する場面の誤検知を減らし、Java/KotlinのSSRF・不正リダイレクト検出は`URI.getHost()`と固定許可リストの大文字小文字を無視した比較を認識する。GitHub Actionsの制御フローグラフは共通ライブラリへ移り、独自クエリが旧ノード構造や`Completion`クラスに依存している場合は修正が必要になる。

**開発者目線:** AI生成テキストを検索やコマンドへ渡すアプリでは、入力を信頼できないデータとして追跡するモデルを自分で定義できる点が有用だ。既存のカスタムCodeQLクエリは新バージョンで回帰テストし、警告数の増減を単純に品質改善と判断せず、実際のソース・シンクの追跡結果を確認したい。

## 4. DependabotがPython 3.15に対応 — 新ランタイムへの更新監視を継続

**11月3日公開｜技術アップデート**

11月3日、GitHubはDependabotがPython 3.15のプロジェクトに対応したと発表した。Pythonの新しいバージョンを試すとき、アプリ本体のテストが動いても依存更新の自動化が止まると、後から保守負荷が増える。今回の発表はPython 3.15を利用するリポジトリでもDependabotによる更新を継続できることを示す。GitHub.comの全ユーザーに提供され、GitHub Enterprise Serverでは3.24に含まれる予定だ。

重要なのはランタイムの対応とパッケージの対応を区別することだ。DependabotがPython 3.15を理解していても、各ライブラリがPython 3.15用のWheelを公開しているか、ネイティブ拡張がビルドできるか、アプリのテストが成功するかは別の問題である。特に画像処理、科学計算、暗号化のようなネイティブ依存があるプロジェクトでは、更新PRの作成成功だけでは移行完了といえない。 [公式出典](https://github.blog/changelog/2026-11-03-dependabot-now-supports-python-3-15/)。

Pythonの依存関係にはバージョン制約と実行環境の条件がある。`requires-python`の指定、複数Python版を対象とするCIマトリクス、Lockfileの再生成を一緒に管理しないと、ある環境だけで解決結果が変わる。今回の変更はDependabot側のサポート追加であり、すべてのパッケージに3.15互換性を保証するものではない。

**開発者目線:** 開発者は新しいPythonを試すブランチで依存解決とテストを実行し、既存の安定版との結果を比較したい。Dependabotの更新PRを自動マージする場合も、最低限の統合テストと脆弱性検査を必須にする。新しい言語版の採用速度を上げつつ、更新自動化の盲点を減らすための地味だが重要な改善だ。

## 5. GitHub REST APIでCost Center所属を直接照会 — 請求管理の探索コストを削減

**11月3日公開｜技術アップデート**

11月3日、GitHubは企業のCost Centerにどのリソースが所属するかを直接取得するREST APIを公開した。対象はユーザー、組織、リポジトリ、Enterprise Team。従来はすべてのCost Centerを列挙してから、それぞれのリソース一覧を走査する必要があった。組織やチームが増えると、単に一つのリポジトリの請求先を知るためにも多数のAPI呼び出しが発生する構造だった。

新しいエンドポイントはリソースの種類と名前を渡し、所属するCost CenterのIDと名前を返す。未所属なら`memberships`配列が空になる。呼び出し権限は役割によって異なり、Enterprise OwnerやBilling Manager、Enterprise Billingの読み取り権限を持つGitHub Appは企業内の任意リソースを照会できる。一方、Organization Ownerやカスタムロール利用者は自分に可視のリソースとCost Centerに限られる。 [公式出典](https://github.blog/changelog/2026-11-03-look-up-a-resources-cost-center-with-the-github-rest-api/)。

この違いは管理画面や社内ダッシュボードを作る際に重要だ。未所属を示す空配列と、権限がないために見えない状態を混同すると、費用の付け替えや監査で誤った判断につながる。APIの応答を使う側では認証主体と可視範囲を記録し、エラーと空の結果を別々に扱う必要がある。バッチ処理では不要な全件取得を減らせる可能性があるが、実際のレート制限や権限要件はAPI仕様に従って確認したい。

**開発者目線:** 複数組織にまたがる開発基盤を運用する場合、リポジトリ作成時のCost Center確認や月次の費用配賦監査を自動化しやすくなる。導入時は代表的な権限ロールごとに同じリソースを照会し、期待した可視性かをテストすることが有効だ。

## 6. GitHub Desktop 3.6.10 — 短命トークンの自動更新を段階導入

**11月2日公開｜技術アップデート**

11月2日、GitHubはGitHub Desktop 3.6.10以降で短い有効期限の認証トークンを使う仕組みを段階的に展開すると案内した。長期間有効なトークンは漏洩すると悪用可能な時間も長くなる。短命化は漏洩そのものを防ぐわけではないが、悪用可能な時間を縮める防御策だ。DesktopはGitHub APIへの要求とGit操作でトークンを自動更新するため、日常の操作で利用者が毎回認証し直す必要はない。

対象はGitHub.comとGitHub Enterprise Cloudの適格なアカウントで、段階展開のため全員がすぐに使えるわけではない。GitHub Enterprise Serverは今回の対象外。既存セッションはアップグレード後もログイン状態を維持し、既存トークンが自動的に短命トークンへ置き換わるわけではない。新方式のトークンは対象環境でサインインした際に発行される。 [公式出典](https://github.blog/changelog/2026-11-02-github-desktop-adds-short-lived-authentication-tokens/)。

この仕様は、アプリのバージョンだけで新方式の適用を判断できないことを意味する。3.6.10を入れたからといって全アカウントで同じ認証フローになるとは限らない。特に組織のセキュリティ監査では、トークン寿命、失効時の挙動、端末の紛失時の対処を区別して扱いたい。自動更新に失敗した場合の再ログイン手順もサポート手順に含める必要がある。

**開発者目線:** 開発ツールの認証を設計する際にも参考になる。短命アクセストークンと更新処理を分けることで利便性と被害軽減を両立できるが、更新用資格情報の保護が弱ければ意味が薄れる。実装時は安全な保存先、更新の競合、ネットワーク切断、サーバー側失効を含めた試験が必要だ。

## 7. Kody 2026.11.03 — 署名付きDesktop配信とWorker安定性の改善

**11月3日公開｜技術アップデート**

11月3日に公開されたKodyのリリースでは、Desktop更新の署名と自動配信、アクセス制御の柔軟化、Workerのメモリや公開処理の信頼性改善がまとめて案内された。AIを組み込んだ開発ツールは、モデルの回答品質だけでなく、ローカルアプリの配布経路やバックグラウンド処理の安定性が利用体験を左右する。今回の更新は派手なモデル追加よりも、運用で問題になりやすい部分を扱っている。

Desktopの署名付きリリースは、配布したバイナリが期待する発行元のものかを検証するための基盤になる。ただし署名があればソフトウェアの中身が安全だと証明されるわけではない。配布チャネル、鍵の管理、更新時の検証、ロールバック可能性と合わせて評価する必要がある。自動更新では配信途中の失敗や署名不一致の扱いも重要だ。 [公式出典](https://github.com/kody-hq/kody/releases/tag/v2026.11.03)。

Workerのメモリ使用量や公開処理の耐久性、ホストされた実行環境のタイムアウトへの対処もリリースの焦点となっている。長時間動くエージェント処理では、一度のネットワーク切断やタイムアウトがタスク全体の失敗に直結しやすい。リトライ時に同じ成果物を二重に公開しないか、途中状態をどこまで保存するか、失敗理由をログから追えるかが実務上の確認点になる。

**開発者目線:** 新しい開発支援ツールを評価するときはデモの成功率だけでなく、異常終了後の復旧、更新失敗時の安全性、アクセス権限の粒度を試したい。特に自動公開を伴う処理では、同じ操作を繰り返しても結果が壊れない設計を優先する。

## 8. Cloudflare Workersのベストプラクティス — Binding型と互換日付を運用の中心へ

**最近の公式ガイド｜技術アップデート**

Cloudflareの開発者向けChangelogでは、Workersのベストプラクティスガイドが紹介されている。直近のModule RegistryやRequest.signalの互換性変更とは別に、日常的な設定と検証をどう組み立てるかという実装面の指針だ。エッジ環境はNode.jsに似たAPIを提供する一方、利用できる機能や実行制限が通常のサーバープロセスと同じとは限らない。移植時には設定を明示し、実環境と開発環境の差を減らすことが重要になる。

ガイドはCompatibility Dateを新しく保ち、Node.js互換機能を活用する方針を示している。また、Bindingの型を手書きせず`wrangler types`で生成することを勧める。BindingとはWorkerからデータベース、ストレージ、サービスなどにアクセスするための環境側の接続設定であり、コードの型定義とデプロイ設定がずれると実行時の障害になりやすい。生成した型をCIで確認すれば、設定変更に伴う食い違いを早めに検出できる。 [公式出典](https://developers.cloudflare.com/changelog/34/)。

ただしCompatibility Dateの更新は新しい実行時挙動を有効にする操作でもある。過去の記事で扱ったModule Registryや切断通知のように、日付を進めることで既定値が変わる機能がある。単に最新の日付へ機械的に書き換えるのではなく、変更履歴を読み、ステージングでリクエストや例外処理を回帰テストするべきだ。

**開発者目線:** Workersを採用するプロジェクトでは、型生成、依存更新、Compatibility Date更新を別々のPRとして扱うと原因を切り分けやすい。新規プロジェクトでは推奨設定を初期値にしつつ、既存サービスは変更による影響を計測してから段階的に移行したい。
