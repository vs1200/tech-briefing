## 1. MCP公式Server v2.1.0 — 3種類のServerで計8件の脆弱性を修正

**10月25日｜MCP・Agent Security**

[MCP公式Server群のv2.1.0 Release Notes](https://github.com/modelcontextprotocol/servers/releases/tag/v2.1.0)が公開されました。今回の中心は新機能ではなく、**Filesystem・Everything・Fetchの3種類のServerにある計8件の脆弱性の修正**です。AI AgentにToolを提供するMCP Serverは、Agentが渡したPathやURLを実際のFile System・Network操作へ変換する境界に位置します。そこでの検査漏れは、モデルの応答品質とは別のSecurity問題になります。

Filesystem Server 2.0.1では、許可Directory内かどうかを確認してから書き込むまでの間に、親DirectoryがSymbolic Linkへ差し替えられる競合を対策しました。さらに末尾の空白・Quoteの扱い、Case-insensitiveなVolume上のLink検査、Directory一覧から外部FileのSizeや更新日時が漏れる問題も修正しています。Everything Server 2.0.1ではHTTP/SSE Transportの`Origin`を検査し、Web Pageから意図せずToolへアクセスできる経路を塞ぎました。

Fetch Server 2026.10.24では、IDNA Hostnameの検査と接続先が食い違う問題、NAT64で包んだPrivate IPv4 Addressの検査、Redirect後に`robots.txt`を再確認しない問題を修正。これらは**入力の見かけと実際に操作する対象を一致させる**という共通課題です。Version移行にも注意が必要で、以前の`2026.x`形式からSemantic Versioningの`2.0.1`へ移る場合、Package Managerは自動で新しい番号を上位と判断できません。

| 対象Server | 修正版 | 主な防御 |
| --- | --- | --- |
| Filesystem | `2.0.1` | Path・Symlink・競合の検査 |
| Everything | `2.0.1` | Cross-origin Requestの拒否 |
| Fetch | `2026.10.24` | URL・IP分類・Redirect検査 |

> [!WARNING]
> Filesystemの競合対策は**Windowsで一部未解決**です。単にVersionを上げれば全Platformで同じ保護が得られるわけではありません。該当[Security Advisory](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-53mr-w429-c597)を確認してください。

**開発者目線:** MCP Serverは「便利なAPI」ではなく、Agentに委譲する**実行権限そのもの**です。ServerのVersionをLockし、許可Path・許可Host・Transportの公開範囲を棚卸しし、入力検査後の対象が変わらない設計まで見ることが重要です。

## 2. Codex CLI 0.164.0 — Preset保存・Model指定・MCP認証を改善

**10月23日｜Coding Agent・CLI**

[Codex CLIの公式Release 0.164.0](https://github.com/openai/codex/releases/tag/rust-v0.164.0)では、Terminal上で繰り返す作業を扱いやすくする機能が増えました。最大10個の番号付き`/presets` SlotにPromptやSlash Commandを保存でき、Keyboard Menuから呼び出せます。毎回同じ指示文を貼り付けるのではなく、**作業の入口を再利用できる**更新です。

`/model`と`/permissions`のInline Argumentから、Model・Reasoning Effort・Speed・Permission Profileを指定する機能も加わりました。Terminalでの操作では、同じTaskでも「素早く調べる」「慎重に設計する」「File編集を許可する」といった条件を切り替えたくなります。新しい指定方法は、設定画面を往復する手間を減らします。またKittyまたはSixel Graphicsを扱えるTerminalでは、閲覧・生成した画像をFullscreen Transcript内でPreviewできます。

Enterprise MCP接続の認証も拡張され、対象となるCodex AccountのGrantや専用Sign-in、Secretを必要とするOAuth Clientに対応しました。Remote Bash CommandやZsh Snapshot SessionでCredentialをMaskする処理も追加。修正面では、会話の圧縮が失敗した際に**途中までの要約を履歴へ残さない**、再開時に圧縮済み履歴とThread固有設定を復元する、WindowsのProxy認証を扱う、といった運用上の問題が改善されています。

> [!NOTE]
> 画像PreviewはTerminalの対応方式に依存します。すべてのTerminalで画像が直接表示されるわけではありません。またCredential MaskingはRelease Notesに記載された対応経路に限られ、任意の外部ToolへのSecret漏洩を全面的に防ぐ保証ではありません。

**開発者目線:** Presetは便利ですが、共通化すべきなのは単なるPromptだけではありません。**Model・権限・入力範囲・確認手順**をTaskに合わせて揃えると、同じ手順を複数人・複数Repositoryで再現しやすくなります。長時間Sessionでは履歴圧縮と復元の信頼性も実用性を左右します。

## 3. Biome 2.6.3 — Playwright・React Query・Vueまで新しいLint Ruleを拡張

**10月24日｜Lint・Formatter・Frontend**

[Biome CLI 2.6.3の公式Release Notes](https://github.com/biomejs/biome/releases/tag/%40biomejs%2Fbiome%402.6.3)では、多数の**Nursery Rule**が追加されました。Nurseryは実験的なRule群で、すべてが既定で有効になるという意味ではありません。今回面白いのは、JavaScriptの一般的な書き方だけでなく、PlaywrightのTest、TanStack QueryのRendering、VueのLifecycleといった**Framework固有の失敗パターン**を検出する方向に広がったことです。

例えば`noPlaywrightNthMethods`は、`first()`・`last()`・`nth()`など位置依存のLocatorを検出します。画面にButtonが増えると意図しないElementを押すTestになりやすいため、RoleやLabelで対象を特定する設計を促します。`noTanstackQueryRestDestructuring`は、Query Resultに対するRest Destructuringが全Propertyを読むことになり、不要な再描画を誘発する可能性を警告します。`noVueWatchAfterAwait`は`setup()`内の`await`後にWatcherを作り、自動Cleanupが効かなくなるPatternを検出します。

基本的なJavaScriptでも、最小・最大値を取るためだけにArrayをSortする`noArraySortForMinMax`、Sort ComparatorがNumberでなくBooleanを返す`noBooleanSortComparator`、Loop Headerで`map()`や`filter()`を実行して一時Arrayを作る`noEagerArrayMethodsInLoops`などが追加されました。Formatterの修正では、TypeScriptのInstantiation Expressionの括弧を消してSyntaxを壊す問題や、Markdownの段落とListの空行を消す問題が改善されています。

| Rule例 | 検出する問題 | 得られる効果 |
| --- | --- | --- |
| `noPlaywrightNthMethods` | 要素の順序に依存したTest | Testの耐変更性 |
| `noTanstackQueryRestDestructuring` | 不要なProperty参照 | Renderingの安定性 |
| `noEagerArrayMethodsInLoops` | 一時Array生成 | Allocationの削減 |

**開発者目線:** Ruleを一度に大量導入すると既存Codeが警告だらけになります。**Bugに直結しやすいRuleから段階的に有効化**し、False Positiveと修正Costを計測するのがよさそうです。特にUI TestとState管理のRuleは、Style統一より具体的な障害予防に結び付きます。

## 4. pnpm 10.34.9 — packageManagerとLockfileの不整合を修正

**10月25日UTC／26日JST｜Package Manager・CI**

[pnpm 10.34.9の公式Release](https://github.com/pnpm/pnpm/releases/tag/v10.34.9)は、`package.json`の`packageManager`が固定したpnpm Versionを、新規作成する`pnpm-lock.yaml`へ正しく記録する修正を含みます。pnpm 10に切り替えたProjectで、初回のLockfile生成と、その後の`pnpm install --frozen-lockfile`の判定が食い違い、CIが失敗する問題を解消するものです。大きな新機能ではありませんが、**LocalではInstallできるのにCIだけ止まる**という種類の障害に直結します。

前段の[pnpm 10.34.8](https://github.com/pnpm/pnpm/releases/tag/v10.34.8)では、Frozen InstallでPackageを削除するときにHoistされたDependencyのLinkを再計算する修正と、Direct Dependencyを削除・置換した際の`node_modules/.bin`に壊れたShimが残る問題の修正が入りました。Monorepoや複数Versionを扱う環境では、Fileを消した後のLink先がどのPackageになるかも正しく管理する必要があります。

Security面では、Standalone版pnpmに埋め込むNode.jsが**24.22.1**へ更新されました。以前のNode.js 20はSupportが終了しており、10月に信頼を外されたCertificate Authorityの中間証明書を引き続き信頼する状態だったためです。Package ManagerのExecutable自体がTLSを扱う以上、ProjectのNode.js Versionとは別に、**Package Managerに内蔵されたRuntime**の更新も重要になります。

この修正の背景には、依存関係を固定する情報が複数箇所に存在する問題があります。`packageManager`はToolのVersionを、Lockfileは解決結果を、CIはFrozen Modeで再現性を確認します。いずれかの書き込みが欠けると、再現性を守るための検証がかえってInstallを止めます。

**開発者目線:** Package Managerを更新した直後は、`pnpm install --frozen-lockfile`を**新規Cloneした環境で実行**し、Lockfile差分とExecutableのRuntime Versionを確認したいところです。Dependencyの脆弱性だけでなく、Install Toolそのものの証明書Trust StoreもSupply Chainの一部です。

## 5. Electron 46 Alpha 1 — Preload互換性とOS連携に変更

**10月23日｜Desktop Application・Chromium**

[Electron 46.0.0-alpha.1の公式Release Notes](https://github.com/electron/electron/releases/tag/v46.0.0-alpha.1)が公開されました。**Alpha版**であり、安定版への移行を促す発表ではありません。今回は、Sandboxed PreloadのAPI整理、暗号化Storageの非同期化、Window CaptureのScale扱いなど、既存Desktop Applicationに影響し得るBreaking Changeが複数あります。

大きな変更は、`safeStorage.isEncryptionAvailable()`、`encryptString()`、`decryptString()`の同期APIが削除され、対応するAsync APIへの移行が必要になったことです。さらにSandboxed Preload Scriptから`events`・`timers`・`url` Moduleと`Buffer`・`setImmediate`・`clearImmediate`などのGlobalが削除されました。従来のNode.js的な前提でPreloadを書いているApplicationは、Bridgeの実装を見直す必要があります。

描画・Captureでは、`webContents.capturePage()`やOffscreenの`paint` Eventなどが、PageのDevice Scale Factorを考慮したImageを返すよう変更されました。HiDPI環境では`nativeImage.getSize()`がPixelではなく**DIP（Device-independent Pixel）**を表す点が重要です。画像を実Pixel数で保存する処理や座標を使った操作は、Scale Factorとの換算を再確認する必要があります。

OS連携も進み、LinuxのWayland Global Shortcut登録結果を知らせるEvent、WindowsのCrash Report Helper、Windowsで権限を下げて再起動するAPI、macOSのDock表示に関する機能などが追加されました。`session.registerPreloadScript`にはURL PatternでのFilterが入り、適用範囲を絞れます。機能追加と同時に**Process・Origin・Permissionの境界を明示する**方向が見えます。

> [!WARNING]
> Alphaは互換性が変わる可能性があります。正式導入前にPreload、暗号化Storage、Capture画像の座標系、Windows・macOS・Linuxごとの挙動を分けて回帰テストしてください。

**開発者目線:** Desktop AppのMigrationでは、UIが表示されるかだけでは足りません。**Preload Bridgeの権限境界・暗号化API・HiDPI座標・OS固有のShortcut**を重点的に確認するChecklistを用意すると、破壊的変更を早期に検出できます。

## 6. Zed 1.25.2/1.25.3 — ACP Agentの会話管理とSecret保護を改善

**10月21〜23日｜Editor・Agent Client**

[Zed 1.25.2のRelease Notes](https://github.com/zed-industries/zed/releases/tag/v1.25.2)では、Agent Client Protocol（ACP）経由のExternal Agentに**Context CompactionとSession Notice**が追加されました。外部のCoding AgentをEditorから使う場合、会話が長くなってContextを圧縮したことや、Session状態が変わったことをEditor側で把握できるようになる更新です。Agentを切り替えても操作状況が見えない、という課題を減らします。

同じReleaseではAmazon Bedrock ProviderにGPT-6 Astra、Claude Fable 5.1、Claude Opus 5.5の選択肢が追加されました。またInlay HintのText EditをDouble Clickで適用でき、SSH Remote接続時にRemote Shell・Platform・OS Versionを一つのCommandで検出することで、接続処理を簡略化しています。Zed本体のBinary SizeはRelease Notesによれば**macOSで約33%、Windowsで約28%、Linuxで約7%削減**。これは公式の公称値であり、利用者の起動時間が同率で短縮するという意味ではありません。

特に重要な修正として、Remote ProjectでExternal AgentやMCP Serverへ渡す**Environment Variable（Secretを含む）がLocal MachineのProcess Listから見える問題**が修正されました。Processの起動Argumentや環境情報は、同じ端末上の別Processから観測され得るため、Credentialをどの経路で渡すかはEditorとAgentの連携における基本的なSecurity要件です。

10月23日の[Zed 1.25.3](https://github.com/zed-industries/zed/releases/tag/v1.25.3)では、Software Ecosystemの最近の脆弱性に対応するためDependencyを更新しました。こちらは小規模なSecurity寄りのMaintenance Releaseです。機能面は1.25.2、Dependency更新は1.25.3と分けて捉えると、Upgrade判断がしやすくなります。

**開発者目線:** Agentの使いやすさはModel選択肢だけでなく、**Sessionの状態表示、長いContextの扱い、Credentialの渡し方**で決まります。Remote環境でMCP Serverを起動する際は、Process ListやLogにSecretが露出しないかを実際のOS上で確認したい更新です。

## 7. Next.js 16.4.3 — Stable系へTracingとBundlerの修正をBackport

**10月23日｜React・Web Framework**

[Next.js 16.4.3の公式Release Notes](https://github.com/vercel/next.js/releases/tag/v16.4.3)が公開されました。今回のReleaseは**BackportされたBug Fixが中心**で、Canary Branchの新機能がすべて入ったわけではないと明記されています。FrameworkのReleaseを追う際、Stable系のPatchとCanaryの変更を同じものとして扱わないことが重要です。

具体的には、Extensionを持たないGoogle Fonts URLの扱いを両Bundlerで修正、`proxy.ts`でApp Page Runtimeを不要に読み込まない修正、Standalone ReactをServer Bootstrapで不要に読み込まない修正が含まれます。さらにTurbopackのLoader変更に関するInvalidationの変更をRevertしました。これはCacheが更新されるべきタイミングを誤る問題に関わる領域で、開発時に「変更したのにBuild結果が変わらない」類の不具合と接点があります。

**OpenTelemetryのRequest Traceをまとめて扱う**修正も入っています。Web Applicationで一つのRequestが複数の内部処理へ分かれるとき、Traceが分断されると原因調査が難しくなります。Observabilityの修正は画面に直接現れなくても、ProductionでLatencyやErrorを追跡する際に価値があります。Release AutomationではCredentialをGitHub Environmentsの制御下へ置く変更もBackportされました。

一方、10月24日UTCの[16.5.0-canary.27](https://github.com/vercel/next.js/releases/tag/v16.5.0-canary.27)では、TurbopackのChunk Group管理や大量Batch Lookupの並列Decodeなど、より実験的な改善が進行しています。StableのPatchとCanaryの内部最適化を分けて評価することが、Migrationのリスクを減らします。

**開発者目線:** Framework更新で最初に見るべきなのは新APIだけではありません。**Cache Invalidation、Runtimeの二重読み込み、Tracingの連続性**はPerformanceやDebuggabilityへ直結します。Patch適用後はBuild ArtifactとRequest Traceを比較し、Canaryの変更を不用意に混ぜない運用が堅実です。

## 8. TypeScript 7.1 Beta — Go製Compiler APIとContent Mapperを公開

**10月20日｜TypeScript・Tooling／週末の見逃し記事**

[Microsoft公式のTypeScript 7.1 Beta発表](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)は、型Checkerの高速化だけでなく、**外部ToolがTypeScriptの解析機能を利用する新API**を大きく前進させました。`typescript/sync`・`typescript/async`・`typescript/fs`・`typescript/ast`など役割ごとにEntry Pointを分け、Compilerの解析やProgram生成をToolから呼べます。TypeScript 7系のGo実装とJavaScript側の間でResourceを保持するため、`API`や`Program`は`using`または明示的な`dispose()`で解放する必要があります。

新APIには**Snapshot**の仕組みがあります。変更前のProject状態を保持し、更新したFileだけをLayerとして重ねて次のSnapshotを作ることで、全Fileを読み直すより効率的に差分解析できます。Virtual File Systemを使えばDisk上に存在しないFileも解析できるため、Editor・Code Generator・AI Coding Toolなど、実Fileを保存する前に型検査したい用途に向きます。

もう一つの注目は**Content Mapper**です。VueやSvelteのSingle File Component、Astro、MDXのようにHTMLとTypeScriptが一つのFileに混在する形式を、仮想的なTypeScript表現へ変換し、診断位置を元Fileへ対応付けられます。CLIから外部Mapperを実行する際は`tsc --runExternalCode`が必要で、VS Code側もWorkspace Trustと許可が前提です。外部Codeを実行する機能であることを明示している点が重要です。

言語機能ではImport Attributesを考慮したAmbient Module宣言、`import source`、`--target es2026`が加わりました。Microsoftは複数のCodebaseで7.0から7.1 Betaへの高速化を測定し、例えば`mui-docs`で22.2秒から11.9秒と報告しています。ただし**公式の測定条件に基づく値**であり、すべてのProjectが同じ倍率で速くなるわけではありません。

> [!WARNING]
> 7.1は**Beta**です。Content Mapperの実行にはSecurity上の許可が必要で、外部Toolの互換性やAPIの安定性は本番導入前に確認してください。

**開発者目線:** 単なる`tsc`の高速化より、**型情報を持つ開発Toolを作るためのAPIが整う**点が面白い更新です。Editor Plugin、静的解析、Code Generation、AI Agentの検証工程などで、保存前のCodeを高速に型検査する用途が広がります。

## 9. uv 0.13.5 — Python配布物と証明書Trust Storeを更新

**10月21日付Release／22日公開｜Python・Package Security**

[uv 0.13.5の公式Release Notes](https://github.com/astral-sh/uv/releases/tag/0.13.5)では、管理対象のCPython Buildが更新され、**Python 3.15.1・3.14.9・3.13.17**などのSecurity Patchが利用できるようになりました。前の0.13.4でuv自身のCertificate Storeから問題のあるeMudhra/emSign Rootを削除した流れを受け、今回はuvが配布するPython Buildと、その中に含まれるpip側のTrust Storeも更新する対応です。

重要なのは、ToolをUpgradeしただけでは**すでに作成済みのPython環境が自動更新されない**ことです。Release Notesでは、uvの更新後に`uv python upgrade`を実行して新しいManaged Pythonを導入するよう案内しています。既存のVirtual Environmentで古いPython Patch Versionを固定している場合、そのInterpreterは自動では切り替わりません。既存Environment内のpipも別途更新が必要です。

更新されたBuildにはpip 26.2.2がPreinstallされ、`ensurepip`に同梱されるpipも同じVersionです。どちらも`certifi 2026.10.19`を利用し、影響のあるRootを除外しています。uv本体も`rustls-webpki 0.103.16`によって問題のある中間証明書を拒否します。つまり**uv本体、Managed Python、Virtual Environment、pip**は別々に更新状態を持つことになります。

ほかに、複数EnvironmentをまたぐDependency解決時のPeak Memory削減、複雑なExtrasを持つDependency GraphのExport高速化、Android Wheelだけで配布されるPackageのLock改善などが含まれます。なおuvは、Support終了済みPython 3.9・3.10を基盤とするDocker Imageの配布停止も案内しています。

**開発者目線:** Supply Chain対策では「Package Managerを最新版にした」だけで完了しません。**実際にTLS接続するProcessが使うCA Bundle**を確認し、Interpreter・pip・Container Imageを分けて棚卸しすることが必要です。再現性を保つLockと、Security Updateの取り込みを両立する運用が問われます。

## 10. Vite 8.3.5 — HMR・Chunk Import Map・Source Mapの不具合を修正

**10月21日｜Frontend Build・Development Server**

[Vite 8.3.5の公式Release Notes](https://github.com/vitejs/vite/releases/tag/v8.3.5)はBug Fix中心のPatch Releaseです。注目は、**Chunk Import MapのHash計算へPreload Dependencyを含める**修正と、Chunk Import Mapが欠けている場合のBuild処理の修正です。Build Toolでは出力されるJavaScriptだけでなく、どのChunkを事前に読み込むかというMetadataが正しく更新されないと、古いAssetを参照する可能性があります。

Development Serverでは、`server.origin`をAsset URLに反映する修正、User定義の`import.meta.env.*`をObjectへ正しく含める修正、ForwardされたError StackをBundleのSource Mapへ対応付ける修正が入りました。Errorが発生した場所をOriginal Sourceへ戻せるかどうかは、開発中のDebug速度に大きく影響します。Error Messageが出ても生成Code上の位置しか分からないと、原因の特定に時間がかかります。

HMR（Hot Module Replacement）では、すでにImportされなくなったModuleでPropagationを止める修正が入りました。不要なUpdateが連鎖すると、変更したComponent以外の再評価が起き、Stateの再初期化や開発体験の不安定さにつながり得ます。Dependency Optimizerでは`yarn.lock`を使うFallback、`oxc.jsxInject`のImport Scan、Subpath Importの`#`の扱いなども改善されています。

Source MapやHMRは「開発時だけ」の機能と思われがちですが、複雑なFrontend ProjectではBugの再現性と切り分けに直接関係します。特にBuild OutputをCDNでCacheする環境では、Import MapやPreloadのHashが正しく更新されることが重要です。今回の変更は、派手なAPI追加より**Build結果とDebug情報の整合性**を高める内容です。

**開発者目線:** ViteのPatch適用時は、`pnpm build`などのBuild成功だけでなく、**Chunkを跨ぐDynamic Import、Preload、HMR、Error StackのSource Map**を確認したいところです。生成物のHashが変わる理由を理解すると、CDN Cacheの不具合も追いやすくなります。
