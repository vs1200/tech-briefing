今朝は「新モデル祭り」というより、**Agentを本番運用するための権限・Security・Observability**が主役です。ちょうど東京ではAGNTCon + MCPCon Japanも開催中。ゲーム開発ではUnity/Unreal向けMulti-Agent Tool、純Developer ToolではSelenium 4.49とCodeQL 2.27を拾いました。

---

## 1. Anthropic最新Threat Report — サイバー攻撃が「AI支援」から「AI主導」へ

Anthropic が9月10日に最新Threat Intelligence Reportを公開しました。1〜9月に検出したClaude悪用事例を分析すると、人間が一つ一つ攻撃するのではなく、**AI Frameworkが攻撃工程をOrchestrateし、人間はSupervisorになる**ケースが増えているとしています。ロシア系攻撃者によるEspionageでは、PhishingからMalware改変までAIが複数工程で使われました。([Reuters](https://www.reuters.com/legal/litigation/anthropic-disrupts-russian-chinese-ai-campaigns-targeting-its-claude-models-2026-09-10/))

一方、中国系AI Labによる大規模なModel Distillationも報告され、最大のCampaignではClaudeへの不正Interactionが**1億5,100万回超**に達したとAnthropicは主張しています。([Reuters](https://www.reuters.com/legal/litigation/anthropic-disrupts-russian-chinese-ai-campaigns-targeting-its-claude-models-2026-09-10/))

**開発者目線:** Agent Securityを考えるとき、もう「危険なPromptをBlockする」だけでは足りません。**Tool Callの連鎖、Credential、Network Egress、Agent間通信まで一つのAttack Chainとして観測する**必要があります。

## 2. 東京でAGNTCon + MCPCon Japan開催中 — MCPの次は「Governance」が話題

[AGNTCon + MCPCon Japan](https://events.linuxfoundation.org/agntcon-mcpcon-japan/) は9月10〜11日に東京で開催中です。Linux Foundation傘下のAgentic AI Foundation系イベントで、MCPだけでなくAgent Architecture、Orchestration、Security、Interoperabilityなどが中心テーマです。([AI What's On](https://aiwhatson.com/event/agntcon-mcpcon-japan-2026))

特に面白いSessionの一つが「**Governing AI Agent Actions: MCP and Beyond**」。MCP Serverだけを管理しても、AgentはCLI、Skill、生成したコード経由でAPIを直接叩けるため、それら全部にPolicy / Allowlist / Human Approvalを適用すべき、という内容です。([Obot AI](https://obot.ai/blog/agntcon-mcpcon-japan-2026/))

**開発者目線:** これはかなり本質的です。MCPにPermissionを付けても、

`Agent → shell → curl → API`

なら迂回できる。今後のAgent Governanceは**Protocol単位ではなく「Agentが起こせる副作用」単位**で考える必要がありそうです。

## 3. GitHub Copilot、Agent操作ごとにEnterprise側で権限設定

[GitHub Changelog](https://github.blog/changelog/month/09-2026/)

昨日のGitHub更新で、Copilot Business / Enterprise管理者が**Agent Operation単位でPermissionを中央管理**できるようになりました。([The GitHub Blog](https://github.blog/changelog/month/09-2026/))

操作ごとに、

`Block`
`Human approval required`
`Allow without prompt`

を指定できます。

**開発者目線:** `dontAsk`的に全部自動化するか、毎回Approveするかの二択ではなくなります。

例えば、

`Read / Test → 自動許可`
`Package install → Approval`
`Deploy / destructive operation → Block`

のような**Risk-based Permission Model**をチームで統一できます。長時間Coding Agentを会社で使うならかなり重要な機能です。

## 4. Aura 1.0 — Unity / Unreal向けMulti-Agent開発環境が正式版へ

ゲーム開発では **Aura 1.0** が9月9日に正式リリースされました。UnityとUnreal Engine向けのAI Development Agentです。([FinancialContent](https://markets.financialcontent.com/pennwell.hydroworld/article/bizwire-2026-9-9-aura-10-launches-today-pushing-the-frontier-of-agentic-ai-in-game-development))

単一Agentではなく、生成した変更を別の **Verification Agent** が検証するMulti-Agent構成。Persistent Project Memory、複数Project、Mac、Unreal Blueprint生成などにも対応しました。

**ゲーム開発目線:** 昨日のUnity公式Claude Code Pluginとは違うアプローチです。

`Claude Code + Unity公式Skill`

対

`ゲームEngine特化Multi-Agent`

という競争になってきました。特に**実装AgentとVerification Agentを分離する設計**は、ゲームのように「Compileが通れば正解」とは限らない領域では相性がよさそうです。

## 5. CodeQL 2.27 — Linux ARM64対応 + Rust Security Query追加

[GitHub CodeQL 2.27 announcement](https://github.blog/changelog/month/09-2026/)

GitHubが **CodeQL 2.27.0** を9月9日に公開しました。Linux ARM64で動作するようになり、新しいRust Security Query、Java/Kotlin・C# Framework Coverage、各言語のAnalysis Accuracy改善が入っています。([The GitHub Blog](https://github.blog/changelog/month/09-2026/))

**開発者目線:** ARM64対応は地味に便利です。Apple SiliconだけでなくARM Cloud Runnerも増えているので、Security Analysisのためだけにx86 Runnerを維持する必要性が下がります。

そしてRust利用がInfrastructure / Agent Runtimeで急増しているため、**Rust向けSASTが成熟していくこと自体**も重要です。

## 6. Selenium 4.49 — WebDriver BiDiがさらに実用段階へ

[Selenium公式：Selenium 4.49 Released](https://www.selenium.dev/blog/2026/selenium-4-49-released/)

Selenium 4.49が9月9日に公開されました。JavaScript / Ruby / Python / .NET / Java / Gridが一斉更新されています。([Selenium](https://www.selenium.dev/blog/2026/selenium-4-49-released/))

特にWebDriver BiDi周辺の修正が多く、.NETではBrowsing ContextのScreencast、PythonではBiDi ErrorをTyped WebDriver Errorとして扱えるようになりました。JS / Python / Rubyでは共通SchemaからField Name / Enum Typeを生成する方向へ整理されています。([Selenium](https://www.selenium.dev/blog/2026/selenium-4-49-released/))

**開発者目線:** Browser Agentでも重要です。従来のWebDriverより双方向Eventを扱いやすいBiDiが成熟すると、**AgentがDOMだけでなくBrowser Event / Network / Contextをリアルタイム観測する**基盤としても使いやすくなります。

## 7. IntelliJ IDEA、Dev ContainerからHost RCEにつながる脆弱性

JetBrains IntelliJ IDEA **2026.2.2より前**には、Dev ContainerをBuildする前のProject Trust確認が不足しており、悪意あるProjectからHost上で任意コードを実行できる **CVE-2026-86504** が報告されています。CVSSは7.8です。([CyberRota](https://www.cyberrota.com/cve/CVE-2026-86504))

2026.2.2で修正済みです。

**開発者目線:** Coding Agent時代には特に注意したい種類です。

「怪しいRepositoryだからContainerで開こう」

という安全策自体がAttack Surfaceになる。先日のGitSpawnと同じく、**Untrusted Repositoryを開くだけでどこまで処理が走るか**をDeveloper Tool側でも見直す必要があります。

## 8. d-Matrix、NVIDIA NVLink Fusionへ参加 — AI推論専用ChipをNVIDIA Rackへ混載

d-Matrix がNVIDIAの **NVLink Fusion**を採用し、同社のInference向けRaptor ChipをNVIDIA Data Center Systemへ直接接続します。2027年の提供予定です。([Reuters](https://www.reuters.com/business/media-telecom/chip-startup-d-matrix-use-nvidia-chip-linking-tech-ai-servers-2026-09-10/))

ここで重要なのはTrainingではなく**Inference専用**であること。Coding Assistant、Voice Agent、Chatbotなど大量のInferenceを低Latencyで処理する用途を狙います。([Reuters](https://www.reuters.com/business/media-telecom/chip-startup-d-matrix-use-nvidia-chip-linking-tech-ai-servers-2026-09-10/))

**開発者目線:** GPU vs ASICという単純な競争ではなく、

`NVIDIA GPU + Custom Inference ASIC + NVLink`

という**異種Acceleratorを同一Rackに組み合わせる**方向が現実になっています。Agentが大量のModel Callを発生させるほどInference Infrastructureの比重は大きくなります。

## 9. Agent界隈で「共有Memory Layer」が急浮上

今日のOSS Community枠。

GitHubのAI Memory系Repositoryでは、**複数Agentから同じLong-term Memoryを共有する**Toolがかなり伸びています。9月10日時点では、memmy-agentが1日で約+350 stars、OpenVikingが+230、Rust製ai-memoryが+180ほど伸びています。([GitTrend](https://gittrend.io/trending/ai-memory))

発想は、

`Claude Code ─┐`
`Codex ──────┼→ Shared Memory`
`OpenClaw ───┘`

というもの。

**開発者目線:** Coding Agentを乗り換えるたびにProject Contextや過去の判断が消える問題への回答です。ただし、Memoryを共有すると**古い判断・誤情報・秘密情報までAgent間で伝播する**ので、TTL・Provenance・Scope設計が次の課題になります。

## 10. 今日の小ネタ：rtk — CLI出力を圧縮してAgentのTokenを60〜90%削減

今日の「ちょっと試したいDeveloper Tool」はRust製 **rtk**。

Coding Agentが実行する`git`、test、buildなどのCLI OutputをProxyで圧縮し、LLMへ送るContext Tokenを削減するToolです。公開情報では一般的なDeveloper Commandで**60〜90%程度のToken削減**を狙っており、9月10日時点で約8万GitHub starsまで伸びています。([RepoRadar](https://reporadar.spreix.com/repos/rtk-ai/rtk))

例えば大量のTest Logを丸ごとAgentへ渡すのではなく、失敗箇所や重要部分だけを残します。

**開発者目線:** Agent OptimizationというとModel Routingばかり注目されますが、

**「モデルへ渡すTool Outputそのものを小さくする」**

のは非常に素直な最適化です。長時間Coding AgentではCostだけでなくContext Pollutionも減らせるので、この手の**Agent-aware CLI Middleware**は今後増えそうです。

## 👀 今日ならこの3つ

一番実務的なのは **CopilotのOperation単位Permission**。Coding Agentを長時間動かすなら、毎回Approveするのは邪魔、全部Allowは危険。その中間となる**「操作のRiskごとに自動許可を決める」**仕組みがようやく製品側に入り始めました。([The GitHub Blog](https://github.blog/changelog/month/09-2026/))

ゲーム開発なら **Aura 1.0**。昨日のUnity公式Claude Code Pluginと合わせて見ると、ゲーム開発AIが「C#生成」から、**Engine操作 + Project Memory + Verification Agent**へ急速に広がっています。([FinancialContent](https://markets.financialcontent.com/pennwell.hydroworld/article/bizwire-2026-9-9-aura-10-launches-today-pushing-the-frontier-of-agentic-ai-in-game-development))

小ネタでは **rtk** がかなり好みです。高価なモデルを安価なモデルへ変える前に、`git diff`やTest Logの無駄な数千Tokenを消す。こういう**地味なHarness改善が実際のAgent性能・コストに効く**という流れは、今後も注目です。
