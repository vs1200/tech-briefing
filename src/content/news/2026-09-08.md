今朝は大型モデル発表より、**「Agentをどう組み合わせるか・評価するか・安全に使うか」**の実装側が面白い日です。特にGitHubのマルチモデル研究、GoogleのSecurity Agent、PFNのRustunaは技術的に読み応えがあります。昨日まで扱ったAstra、OpenClaw、Project Zenithなどは外しました。

---

## 1. GitHub「HydraFusion」— 1つの最強モデルより、複数モデルを組み合わせる

[GitHub公式：Project HydraFusion](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/)

[GitHub](https://github.com/) が9月4日に公開した **Project HydraFusion** がDeveloper界隈で注目されています。

発想は面白く、難しいCoding Taskを全部Opus 5のような大型モデルへ投げるのではなく、**複数モデルを動的に組み合わせる**方式です。GitHubのControlled Evaluationでは、選択的なCoding WorkflowでOpus 5単体と同等以上の品質を出しつつ、推論コストを削減できたとしています。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/))

つまり、

`Task → Router → Model A / Model B / Model C → 統合`

という構造。

**開発者目線:** 最近の「Flashは通常実装、Opus級は難問」という単純Routingからさらに一歩進み、**1タスクの中でも複数モデルを協調させる**方向です。Coding Agentの性能競争が「どのモデルが最強か」からOrchestrationへ移っています。

## 2. Google「Mantis」— Coding Agentに脆弱性を発見→再現→修正までさせる

[Google Mantis](https://github.com/google/mantis)

GoogleのOSS **Mantis** が今週Developer Security界隈で注目されています。

Mantisは単体のSecurity Scannerではなく、既存Coding Agentへ追加する**Security Review Skill群**。Agent自身が、

`脆弱性候補を発見`
→ `Exploit / Reproducerを作る`
→ `本当に再現するか確認`
→ `Patchを作る`

というLoopを回します。([GitHub](https://github.com/google/mantis))

Google自身も、生成コードを実行するため**隔離環境でのみ使用し、人間のSecurity Expertが結果を検証すること**を強く警告しています。

**開発者目線:** Static Analyzerが「怪しい」と言うだけなのに対し、Agentが**実際に再現してFalse Positiveを落とす**ところが重要。将来的なAI Code Reviewのかなり有力な形です。

## 3. PFN「Rustuna」— OptunaをRustで再実装

[Preferred Networks公式発表](https://www.preferred.jp/en/news/pr20260907)

日本の Preferred Networks が9月7日、**Rustuna**を公開しました。

有名なHyperparameter Optimization Framework **Optuna** のRust実装で、同時にOptuna 5.0もリリースされています。従来のOptunaはPython製ですが、用途がMachine Learning以外のMaterials Scienceなどにも広がり、大規模探索でPerformance / Memory Efficiencyが問題になるケースが増えていました。([株式会社Preferred Networks](https://www.preferred.jp/en/news/pr20260907))

そこで、

**使いやすいPython → Optuna**
**Performance / Memory重視 → Rustuna**

という選択肢を用意します。

**開発者目線:** Python AI ecosystemのHot PathをRustへ逃がす流れのかなり分かりやすい実例。Python Packageを全部捨てずに、重いCoreだけRust化する設計はTool開発でも参考になります。

## 4. Optuna 5.0も同時リリース

Rustunaだけでなく **Optuna 5.0** も9月7日に公開されています。2018年から続くプロジェクトのMajor Updateです。([株式会社Preferred Networks](https://www.preferred.jp/en/news/pr20260907))

Hyperparameter OptimizationはLLM時代でも、

`Learning Rate`
`Model Configuration`
`Inference Parameter`
`Pipeline Parameter`

など大量の探索問題に使われます。

**開発者目線:** AI研究ToolはLLM Frameworkばかり注目されがちですが、実際のExperiment Automationではこうした**Optimization Infrastructure**がかなり重要です。Rustunaとの組み合わせも含めてPFNらしいリリースです。

## 5. UiPath「LLM as Judge」をAgent Guardrailとして製品化

[UiPath公式Release Notes](https://docs.uipath.com/agents/automation-cloud/latest/release-notes/september-2026)

UiPath が9月7日、Agent向け **LLM as Judge Guardrail** をPreview公開しました。

通常のGuardrailは、

`個人情報`
`暴力`
`Prompt Injection`

など固定Classを検出します。

新機能では自然言語で、

> 「このAgentは顧客に確定的な法律判断をしてはいけない」

のようなRuleを書き、**別LLMがAgentのPrompt / Response / LLM Callを評価**します。([UiPath](https://docs.uipath.com/agents/automation-cloud/latest/release-notes/september-2026))

当然Judge側にもLLM Callが発生するため追加Costが掛かります。

**開発者目線:** AgentのSafetyを`if`文で書くのではなく、**Policyそのものを自然言語 + Model Evaluationにする**設計。柔軟ですが、Judge自体の誤判定・Cost・Latencyという新しい問題も生まれます。

## 6. Qwen Code、Agentの「今何してる？」をかなり可視化

Qwen Code **0.23.1-preview.2**では、Dynamic WorkflowのVisualization、SubagentのLive Status、Session Resource Catalog、Worktreeで隔離されたNamed Taskなどが追加されています。([AIビジネス変革コンサルティング](https://aisengtech.com/AI-research-open-source-LLM-model-Brief-2026-09-07/))

特に、

`Main Agent`
`├ task A [running]`
`├ task B [testing]`
`└ task C [done]`

のようにMulti-Agent処理を人間から追いやすくする方向です。

**開発者目線:** この数日の流れとも一致しています。Agent性能が上がるほど重要になるのはPrompt UIではなく、**Observability / Interrupt / Session Management**。Coding AgentがTerminal Chatから「Process Manager」へ変わっています。

## 7. Asahi Linux、Apple M3 Macを正式サポート

[Asahi Linux公式Blog](https://asahilinux.org/blog/)

Asahi Linux が **M3シリーズMacの正式サポート**をInstallerへ追加しました。

プロジェクトによれば、M1/M2で対応済みだった機能のほぼすべてがM3でも動作する状態まで到達しています。([Asahi Linux](https://asahilinux.org/blog/))

Apple Siliconは公式Linux Driverが存在しないHardwareが多く、Asahi側がReverse EngineeringしてDriverを作っています。

**開発者目線:** M3 MacをLinux Machineとして再利用できる選択肢が現実的になりました。Apple SiliconのGPU / Hardware Reverse Engineeringという意味でも技術的にかなり面白いプロジェクトです。

## 8. Blender、Remote Asset LibraryをMulti-file化へ

9月7日に公開されたBlender Asset System Meetingでは、**Multi-file Remote Assets Support**の開発状況が共有されました。([Blender Devtalk](https://devtalk.blender.org/t/2026-09-04-asset-system-module-meeting/45774))

現在の課題は、一つのAssetに複数ResolutionやDependencyがある場合。すべてを同じ`.blend`へ詰め込むのではなく、必要なFile群をRemote Libraryから取得できる仕組みを作っています。

複数FileのDownload自体はすでに動いており、Dependency Listing周辺が開発中です。([Blender Devtalk](https://devtalk.blender.org/t/2026-09-04-asset-system-module-meeting/45774))

**ゲーム開発目線:** UnityのAddressablesにも近い問題です。Remote Assetを扱うと「Asset = 1 file」という前提がすぐ崩れるため、**Dependency GraphとResolution Variantをどう表現するか**という設計が参考になります。

## 9. Agent UIの細かい進化：「何をしているか」を具体的に表示

今日の小ネタ。

Agent Collaboration Tool **Briar 1.2** が9月7日に更新され、AgentのProgress Messageをかなり具体化しました。([Briar](https://briar.wordbricks.ai/changelog))

以前の、

> Working...

ではなく、

> Searching...
> Researching code...
> Running tests...
> Using computer...

のように、**実際のTool Stepに合わせて状態を表示**します。

Computer Use終了時には最終Screenshotも添付されます。

**開発者目線:** 地味ですが非常に重要です。Agentが10〜30分働く世界ではSpinnerだけでは不安になります。

**「AIが賢いか」より「何をしているか理解できるか」**

がDeveloper UXの差別化要因になり始めています。

## 10. 今日の変なDeveloper Tool：1KBのPython Interpreter

最後はDeveloper Communityで話題になっている実験枠。

**「1024 bytes以内でFunctional Python Interpreterを作る」**という技術記事がHacker Newsで150pt超まで伸びています。([CodingSalt](https://www.codingsalt.com/))

もちろんCPython互換を1KBに押し込む話ではなく、Python的Syntax / Executionの最小Subsetを、Extreme Code Golf的な制約の中で実装する試みです。

**開発者目線:** 実務Utilityはほぼありません。ただ、Parser / Runtime / Evaluationの「本当に必要な最小構造は何か」を考える教材として面白い。

最近AI Agentばかりなので、こういう**純粋なProgramming HackがまだDeveloper Communityで盛り上がる**のはちょっと嬉しい枠です。

## 👀 今日ならこの3つ

今日は **HydraFusion** が一番面白いです。「Opus 5 vs Astra vs Gemini」のようなモデルランキングから一段進んで、**複数モデルをどう組み合わせれば品質/Cost Paretoを改善できるか**というEngineering Problemへ移っています。([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/))

実際に試したいのは **Google Mantis**。Coding AgentにSecurity Skillを与え、脆弱性を「指摘」するだけでなく**Reproducerを書いて実証してからPatchする**構成は、AI Code ReviewのFalse Positive問題へのかなり自然な回答です。([GitHub](https://github.com/google/mantis))

そして日本発では **Rustuna + Optuna 5.0**。AI ToolingのPython ecosystemを維持しながらPerformance-sensitiveな部分をRustへ持っていく、という最近のDeveloper Tool設計を象徴するリリースです。([株式会社Preferred Networks](https://www.preferred.jp/en/news/pr20260907))
