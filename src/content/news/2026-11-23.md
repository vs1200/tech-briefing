## 1. GitHub Dashboard、最大25件のリポジトリをお気に入り固定

**発表日：2026年11月20日｜公式一次情報**

GitHubは11月20日、新しいDashboardに「Favorite repositories」を追加した。従来のTop repositoriesは利用状況などによって表示される対象が変わり得るが、お気に入りは利用者が明示的に選ぶ。新しいDashboardを有効にしている場合、EditまたはAdd repositoriesから検索して追加・削除し、Saveで反映する。選択中に検索語を変えても選択状態が保持されるため、多数の組織を横断して対象を探す作業に向く。新しいDashboardを使っていない場合、従来のTop repositories表示が残る。今回の変更はリポジトリの権限や可視性を変更する機能ではない。

GitHub Mobileでピン留めしたリポジトリと同期することもポイントだ。両方を合わせて上限は25件で、超過する保存操作はエラーになり、既存の選択は変更されない。モバイルとWebの変更は更新後に相互反映されるため、即時の画面一致を前提にしない方がよい。お気に入りを登録するときは、頻繁にコミットするリポジトリだけでなく、レビュー待ちや障害対応で定期的に監視するリポジトリも候補になる。逆に25件すべてを埋めると一覧性が落ちるため、目的別に選別することが重要だ。

**開発者目線:** 複数プロダクトの保守を担当するチームでは、現在の開発対象と共通基盤のリポジトリを固定しておくと、直近の閲覧履歴に左右されずに移動できる。GitHub Mobileでも同じ対象を開けるため、外出先でCIやIssueを確認する場面にも便利だ。ただしお気に入りは通知の優先順位や権限設定ではない。レビューの見逃し対策はNotificationsやPull requestsのフィルターと併用する。導入後は、探しているリポジトリへ到達する操作回数が減ったかを実際に確認したい。

[公式出典](https://github.blog/changelog/2026-11-20-pin-your-favorite-repositories-to-your-dashboard/)

## 2. GitHub Desktop 3.7.0、同一ホストで複数アカウントに対応

**発表日：2026年11月19日｜公式一次情報**

GitHubは11月19日、GitHub Desktop 3.7.0で同じホストに複数アカウントでログインできるようになったと発表した。GitHub.comだけでなくGitHub Enterprise ServerとGHE.comも対象となる。従来は同じホスト上で個人用と組織用のアカウントを切り替える際、再認証や別のGitクライアントへの移動が必要になる場合があった。今回の機能では同一ホストに登録するアカウント数に固定上限がなく、リポジトリ単位で使用するアカウントを関連付けられる。

cloneやpublish、Git操作では、関連付けられたアカウントの認証情報を自動的に使う。複数のアカウントからアクセス可能なリポジトリを追加するときは選択でき、アクセス可能なアカウントが一つならDesktopが推定する。既存リポジトリは以前使用していたアカウントへ自動移行され、単一アカウントだけの環境は原則として挙動が変わらない。リポジトリの設定や一覧のコンテキストメニューから関連付けを後で変更することもできる。ただし認証アカウントの選択と、コミットに記録されるauthor名・メールアドレスは別の設定である。

**開発者目線:** 複数組織のコードを扱う場合、最初にテスト用リポジトリでclone、fetch、pushを行い、期待するアカウントが選択されるか確認したい。誤った組織の資格情報を使うと権限エラーや意図しない公開先の選択につながる。さらにGitのuser.name、user.email、署名設定もリポジトリ単位で点検する。GUIでアカウントを切り替えられても、コミットの帰属やリモートURLの整合性まで自動で保証されるわけではないためだ。

[公式出典](https://github.blog/changelog/2026-11-19-github-desktop-now-supports-multiple-accounts-per-host/)

## 3. GitHubのPR Overviewプレビュー、マージ判定と履歴表示を改善

**発表日：2026年11月19日｜公式一次情報**

GitHubは11月19日、11月5日に公開プレビューを開始した新しいPull Request Overview画面を改善した。特に重要なのは、失敗した任意チェックがマージ可能なPRをブロック済みのように見せなくなったことだ。CIには必須チェックと参考用の任意チェックが混在する。従来の表示では任意チェックの失敗だけで、マージできないと誤解する可能性があった。新しい表示では不足しているマージ要件も示され、レビュー担当者が次に何をすべきか判断しやすくなる。

レビューやコメントの操作も更新された。ChecksとApprovalsはクリック時に展開され、解決済みスレッドは折りたたまれる。Copilotへのメンションを含むコメントは、送信前に実行するアクションと選択モデルの説明が改善された。さらにforce-push履歴から変更前後のコミットへ移動でき、コミット活動には時刻が表示される。これらはコードの内容そのものを変える機能ではないが、レビュー判断の根拠を見失わないためのUI改善である。画面はまだ公開プレビューで、ヘッダーから新旧表示を切り替えられる。

**開発者目線:** 必須・任意のCIが混在するPRで、新しい表示が実際のブランチ保護ルールと一致するか確認したい。特に失敗した任意チェックを無視してよいかはプロジェクトの運用方針次第であり、UIがマージ可能と表示しても品質上の問題がないことを意味しない。force-pushが多いレビューでは新旧コミットの比較リンクを活用し、レビュー済み差分が書き換わっていないか点検する。プレビュー中は従来画面へ戻せることもチームに共有したい。

[公式出典](https://github.blog/changelog/2026-11-19-improvements-on-the-pull-request-overview-in-public-preview/)

## 4. Azure DevOpsからGitHubへのLive Migrationsが一般提供

**発表日：2026年11月19日｜公式一次情報**

GitHubは11月19日、Azure DevOps Servicesからデータ所在地指定のGitHub Enterprise Cloudへ移すEnterprise Live Migrations（ELM）の一般提供を発表した。一般的なリポジトリ移行では、移行中の変更を止めるコードフリーズが問題になる。ELMは移行元の更新を継続的に同期し、開発チームが作業を続けながら、都合のよい時点で短い切り替え作業を実施する方式だ。今回の対象はAzure DevOps Servicesからの移行であり、以前に案内されたGitHub Enterprise Serverからの移行と混同しないようにしたい。

管理方法はポータルのガイド付き操作とAzure DevOps CLIの自動化に対応する。事前検証や移行ライフサイクルの追跡によって、切り替え前に問題を見つけやすくする。移行対象にはGit履歴、ブランチ、タグ、Pull Requestのタイトル・本文・コメント・ユーザー履歴が含まれる。Azure DevOpsのブランチポリシーはGitHubのrulesetsへ移される。一方、Azure Boardsの作業項目とAzure Pipelinesの定義は移行先へ複製されるのではなく、Azure側に残して接続先を付け替える運用が案内されている。

**開発者目線:** まず小さな非重要リポジトリで、PRコメント、レビュー履歴、ブランチ制限、パイプラインの参照先が期待通りになるか照合したい。切り替え時に誰がどのブランチへpushできるかを決め、移行元への新規書き込みをいつ止めるか明文化する。移行完了の判定はGitオブジェクト数だけでは不十分だ。CIのシークレット、外部サービスのWebhook、Issue連携、保護ルールまで確認して初めて運用可能な状態になる。

[公式出典](https://github.blog/changelog/2026-11-19-enterprise-live-migrations-from-azure-devops-generally-available/)

## 5. GHE.comのS3監査ログ配信、OIDC認証に対応

**発表日：2026年11月19日｜公式一次情報**

GitHubは11月19日、データ所在地を指定するGitHub Enterprise Cloud（GHE.com）でも、Amazon S3への監査ログストリーミングでOpenID Connect（OIDC）認証を利用できるようにした。github.comでは既に提供されていた方式がGHE.comへ拡大した形だ。従来のように長期間有効なAWSアクセスキーをGitHub側へ保存する必要を減らせる。監査ログは管理者操作や組織設定の変更を追跡する重要な記録であり、配信経路の資格情報が漏えいすると、ログの欠落や外部からの不正操作のリスクにつながる。

OIDCでは信頼関係に基づいて短命な認証情報を取得する。固定キーを定期的に更新する運用と比べて、漏えい時に長期間悪用されるリスクを小さくできる。ただしOIDCを有効化するだけで安全になるわけではない。AWS側のIAMロールの信頼ポリシーで発行主体と対象を絞り、S3バケットへの権限も必要最小限にする必要がある。また、監査ログを保存することと、ログの完全性・保存期間・検知ルールを管理することは別の問題だ。GitHubの発表は認証方式の提供拡大であり、監査分析機能そのものの追加ではない。

**開発者目線:** 既存のアクセスキー方式から移行する場合は、まずテスト用のログ配信先でOIDCのロール引き受けとオブジェクト生成を確認したい。切り替え後にログが途切れていないか、イベントの時刻とS3への到着時刻を比較する。S3側では暗号化、保持ポリシー、アクセスログ、削除権限を点検する。認証の更新をきっかけに、監査ログの欠損を検知する仕組みまで整備すると実務上の効果が大きい。

[公式出典](https://github.blog/changelog/2026-11-19-s3-audit-log-streaming-with-openid-connect-expands-to-ghe-com/)

## 6. GitHub Team、セキュリティリスク評価を自動実行

**発表日：2026年11月18日｜公式一次情報**

GitHubは11月18日、GitHub Teamプランの組織に対してセキュリティリスク評価を自動実行するようになったと発表した。組織の管理者とセキュリティマネージャーは、無料の評価結果を確認し、公開された認証情報やコードの脆弱性を把握できる。これまで高度なセキュリティ機能を導入する前に、そもそも何が危険なのかを調べる作業が必要だった。今回の変更は、最初の棚卸しを始めるための障壁を下げるものといえる。

重要なのは評価結果を「すべての脆弱性を検出した証明」と受け取らないことだ。シークレットの検出対象やコード解析の対応範囲には限界があり、検出されなかったことは安全性の保証ではない。評価には既存の保護状況を踏まえて優先順位を付ける必要がある。例えば外部に公開された認証情報が見つかった場合、コードから文字列を削除するだけでは不十分で、資格情報そのものを失効・再発行し、使用履歴を調べるべきだ。コードの問題も影響する経路が実際に到達可能かを確認したい。

**開発者目線:** 組織で最初に評価結果を確認したら、検出件数だけでなく影響範囲、外部公開の有無、既存の保護機能を記録する。シークレット漏えいは優先して無効化し、修正PRと再発防止策を紐付ける。コードの指摘は再現テストを作り、CIで継続検査できる状態へつなげたい。自動評価は入口として便利だが、修正の担当者と期限を決めなければ、リスク一覧が増えるだけで終わってしまう。

[公式出典](https://github.blog/changelog/2026-11-18-security-risk-assessments-run-automatically-on-github-team/)

## 7. GitHub Copilot Evals公開プレビュー、SkillsやMCPを反復評価

**発表日：2026年11月17日｜公式一次情報**

GitHubは11月17日、CopilotのSkills、カスタムエージェント、MCPツールを評価する「GitHub Copilot Evals」を公開プレビューとして発表した。エージェントの回答は同じ指示でも毎回同一になるとは限らず、プロンプトやツールを変更した後に一度成功しただけでは改善を判断できない。Evalsは現実的な作業課題と期待する成功条件を定義し、繰り返し実行して結果を比較する仕組みだ。モデルのベンチマーク順位を眺めるのではなく、自分たちの実際の作業環境における振る舞いを測ることに焦点がある。

Copilotに自然言語で依頼するか、/evalコマンドから評価を作成できる。実行前には利用者の承認が必要で、成功・失敗したチェックと失敗理由を調べ、カスタマイズ前後の結果を比較できる。評価エンジンには拡張可能なローカルツールVallyを採用する。VS Codeでは拡張機能、Copilot CLIではプラグイン、Copilotアプリではマーケットプレイスから導入する方式が案内された。対象プランはCopilot Individual、Business、Enterpriseで、現時点では正式提供ではない。

**開発者目線:** 例えば「指定したAPIにテストを追加する」「誤ったファイルを変更しない」「機密情報を外部へ送らない」といった具体的な成功条件を用意したい。正答率だけでなく変更ファイル数、テスト実行、不要なツール呼び出しも評価する。SkillsやMCPの更新前後で同じ課題を複数回実行すれば、見た目の回答品質では気づきにくい退行を検出しやすい。公開プレビューのため評価自体の安定性も確認し、重要なCIゲートへ直ちに組み込むのは避けたい。

[公式出典](https://github.blog/changelog/2026-11-17-github-copilot-evals-is-now-in-public-preview/)

## 8. JetBrains版Copilot、クラウド隔離実行とリモート継続をプレビュー

**発表日：2026年11月17日｜公式一次情報**

GitHubは11月17日、JetBrains IDE向けCopilotのIgnite更新を発表した。クラウドサンドボックスはGitHubがホストする隔離環境でエージェントセッションを実行し、コード変更やコマンド、テストをローカルマシンの外で処理する。複数セッションを並行させる場合に端末の資源を空けられる一方、ローカル環境にしか存在しないファイルや認証情報へのアクセスは同一ではない。機能は公開プレビューで段階的に展開されるため、全ユーザーが同時に利用できるとは限らない。

リモートアクセスも公開プレビューで、JetBrainsで開始したCopilotの会話をVS CodeやCopilotアプリなど別のクライアントから参照・再開できる。ブラウザ操作プラグインはWebページを開いて内容を読み、リンクやフォームを操作する。音声入力は対応するネイティブプラグインで端末上のモデルをダウンロードして使い、文字起こし結果を送信前に編集できる。JetBrainsのsplit modeリモート開発にも対応するが、ローカルクライアントとリモートバックエンドの両方にプラグインが必要だ。

**開発者目線:** クラウドサンドボックスは依存関係の多いリポジトリでテストし、ローカルとの差分、キャッシュ、実行時間、成果物の取得経路を比較したい。ブラウザ操作は便利だが、認証済み画面での操作範囲と確認手順を限定する。音声入力では送信前の編集を必須とし、誤認識したコマンドがそのまま実行されないようにする。なおJetBrains IDE 2025.2のサポートは終了し、2025.3以降への更新が必要と案内されている。

[公式出典](https://github.blog/changelog/2026-11-17-github-copilot-in-jetbrains-ignite-releases/)

## 👀 今日ならこの3つ

### 🥇 Copilot Evals

エージェントの設定変更を感覚ではなく反復可能な評価で比較できる点が重要。導入前後の退行を見つけるための実践的な仕組みだ。

### 🥈 GitHub Desktopの複数アカウント

個人用と組織用を同じホストで扱う際の認証切り替えを減らせる。Gitのコミット作成者設定との違いも確認したい。

### 🥉 Azure DevOpsのLive Migrations

移行中の開発停止を短くする仕組みが一般提供となった。CIや保護ルールを含む切り替え手順の検証に価値がある。
